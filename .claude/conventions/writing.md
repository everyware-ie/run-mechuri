# 문서 작성 컨벤션

**AI에게 문서를 맡길 때 적용하는 규칙이다.** 사람이 직접 쓸 때도 같은 기준으로 본다.

`CLAUDE.md`의 "기획 문서 정합성"이 **문서끼리 어긋나지 않게** 하는 규칙이라면, 여기는 **한 문서를 사람이 읽을 수 있게** 하는 규칙이다.

## 1. 사람이 읽는 글로 쓴다

2026-08-24에 셋이 합의했다.

> 지민: "FRD나 문서 쓸 때 너무 AI스럽다고 해야 하나? 가독성이 떨어져서. **FRD 본래 문서만으로도 인간이 읽기 편하게 유지되어야 한다**고 생각해서"
> 지응: "인정인정. 나도 느꼈어"

**전체를 다 읽은 사람만 이해할 수 있는 글은 안 된다.** 처음 보는 사람이 그 문단만 읽어도 무슨 말인지 알아야 한다.

| | |
|---|---|
| 전 | 애플이 앱에게 알려주지 않는다. 거부 여부를 알려주면 그 자체로 건강 정보가 새기 때문이다. 앱이 보는 것은 "기록이 안 온다" 뿐이고, 거부한 것인지 진짜로 기록이 없는 것인지 구분할 수 없다 |
| 후 | HealthKit은 사용자의 읽기 권한의 거부 여부를 앱에 알려주지 않는다. 권한을 거부한 경우와 권한은 있지만 기록이 없는 경우가 똑같이 0건으로 조회된다 |

**줄 수를 줄이는 것이 목표가 아니다.** 내용을 쉽게 파악할 수 있게 하는 것이 목표다. 그것만 되면 길어도 된다.

## 2. 긴 줄표를 쓰지 않는다

`—`(em dash)는 **AI가 쓴 티가 난다.** `-`, `( )`, `:`로 바꾼다.

## 3. 조사한 것에는 검증할 수 있는 출처를 단다

2026-08-25에 합의했다.

> 지민: "기술 조사 같이 외부 자료 토대로 뽑아내는 글은 검증할 수 있는 링크를 달라고 해야 신뢰도가 높아집니다. **실제로 AI가 존재하지 않는 출처를 만들거나, 실제 존재하는 글을 엉뚱한 주장에 붙이는 문제도 있어서**"
> 지응: "다음번엔 출처 넣을게"

외부 자료를 근거로 쓴 문단에는 **원문 링크**를 단다. 링크를 못 찾으면 "출처를 못 찾았다"고 적는다. **찾은 척하지 않는다.**

## 4. 모르는 것은 모른다고 적는다

확인되지 않은 것은 `[확인 필요]`로 남긴다. 추측으로 메우지 않는다.

**누가 무슨 말을 했는지 적을 때는 실제로 한 말만 적는다.** 맥락으로 짐작한 것은 짐작이라고 밝힌다.

## 자주 나오는 AI 티

위 규칙을 어기는 구체적인 형태들이다. 고칠 때 이것부터 본다.

| | 예 |
|---|---|
| 번역투 | "~를 통해", "~에 있어서", "그/그녀" 남용 |
| 기계적 나열 | "첫째, 둘째, 셋째", 뜻 없이 이어지는 불릿 |
| 맺음말 상투구 | "결론적으로", "시사하는 바가 크다" |
| 같은 리듬 | 문장 길이가 다 비슷해서 밋밋함 |
| 얼버무림 | "~할 수 있을 것으로 보인다" |
| 접속사 남발 | 문단마다 "또한", "따라서"로 시작 |
| 형식명사 | "~하는 것이다", "~할 필요가 있다" |
| 장식 과다 | 볼드가 너무 많아서 어디가 중요한지 안 보임 |

> 분류는 [im-not-ai](https://github.com/epoko77-ai/im-not-ai)(MIT)의 것을 참고해 추렸다. 그 플러그인을 따로 설치해서 써도 된다.

## 고칠 때

**내용은 건드리지 않는다.** 사실, 수치, 고유명사, 인용은 그대로 둔다. 문체만 고친다.

**많이 고쳤다 싶으면 멈추고 확인받는다.** 문체만 다듬으랬는데 내용까지 바뀌는 일이 잦다.

## 5. 문장과 문단의 줄바꿈을 검토한다

초안을 쓴 뒤에는 줄바꿈도 편집한다.\
화면 너비에 따른 자동 줄바꿈에 전부 맡기거나, 빈 줄을 늘린 것만으로 읽기 좋게 다듬었다고 판단하지 않는다.

하나의 설명이 끝나고 다음 문장에서 적용 조건, 예외, 다른 주체나 별도 동작을 설명하면 문장 끝에서 줄을 나눈다.\
같은 주제 안에서 이어지는 설명은 같은 문단에 두고 줄만 바꾼다.\
주제 자체가 달라질 때 새 문단을 만든다. 짧고 밀접한 두 문장은 함께 두어도 된다.\
모든 마침표에 기계적으로 줄바꿈을 넣지 않는다.

예를 들어 다음 두 문장은 샘플 기능의 적용 범위와 내부 테스트 빌드의 예외를 각각 설명하므로 한 줄로 이어 쓰지 않는다.

샘플 체험은 해당 기능이 제공되는 버전에 적용됩니다.\
별도로 안내받는 내부 측정 테스트 빌드는 기능과 처리 범위가 다를 수 있습니다.

문장 중간의 어절이나 조사 앞에서 임의로 끊지 않는다.\
연결된 의미를 읽기 어렵게 만든다면 문장을 나누거나 표현을 다듬는다.\
화면 너비가 달라져도 모든 자동 줄바꿈을 통제하려고 하지는 않는다.\
특히 모바일 화면에서 짧은 문장마다 빈 문단을 넣어 글을 지나치게 늘리지 않는다.

Notion에서는 같은 문단 안의 줄바꿈에 `<br>`을 사용한다. 문단 사이의 실제 빈 줄이 필요할 때만 `<empty-block/>`을 사용한다.\
Markdown은 사용하는 뷰어에서 줄바꿈이 실제로 표시되는 방법을 확인한다. 두 형식의 줄바꿈 표기를 서로 그대로 복사하지 않는다.

## 작성 완료 전 검토

문서를 쓴 에이전트가 아래 순서로 검토한다. 사용자의 문체 교정을 기본 작업 흐름으로 넘기지 않는다.

1. 사실과 수치, 날짜, 고유명사, 조건과 예외가 원문 또는 근거와 같은지 대조한다.
2. 처음 읽는 사람이 주체와 동작을 이해할 수 있는지 읽어 본다. 번역투, 중간점으로 이어진 긴 나열, 불필요한 강조와 반복을 다듬는다.
3. 문장마다 다음 문장과의 관계를 확인한다. 설명이 끝나는 곳, 조건과 예외가 시작하는 곳을 기준으로 줄바꿈과 문단을 정한다.
4. 공개 문서는 실제 게시 화면에서 문서 전체를 확인한다. 긴 설명이 있는 곳을 포함해 데스크톱과 모바일 너비에서 줄바꿈, 문단 간격, 목록과 링크를 확인한다. 화면을 볼 수 없었다면 내용 검증과 구분해서 보고한다.
5. 저장소에서 요구하는 정합성 검사를 수행한다. 스킬 사용 여부나 API 수정 성공만으로 문체와 화면 검토를 완료했다고 보고하지 않는다.

스킬이 없어도 이 검토를 수행한다.\
스킬을 사용했다면 지침을 실제로 읽고 적용하며, 설치된 스킬 실행과 공개 지침 참고를 구분해서 알린다.

# 결과물 생성 속도 개선 조사와 검토안

2026-09-28 · 검토 초안 · 코드 기준 `98ce5c8`

사용자 요청: 결과물 품질을 유지하거나 높이면서 생성 시간을 크게 줄인다. 조사 → 검토 → 기획 → 구현 착수 순서로 진행한다. **이 문서는 조사 결과와 제안이며 팀 결정이나 구현 승인이 아니다.** 제품 코드·FRD는 변경하지 않았다.

후속 진행: [사전 준비 측정 결과](../product/features/export-preparation.md)에서 Release 실기기 3회 측정을 완료했다. 준비 비용이 전체의 0.25~0.44%여서 해당 캐시 구현은 중단했다. 아래 조사는 측정 전 검토이며 후속 수치는 링크한 구현 노트가 기준이다.

## 1. 결론

우선순위는 영상 압축기 교체보다 **프레임을 그리고 옮기는 비용을 줄이는 것**이다. 현재 코드와 기존 측정이 그 방향을 지지한다. 현재 Release 빌드에서 다시 측정하기 전에는 몇 배 빨라진다고 약속할 수 없다.

권장 검토 순서는 다음과 같다.

1. 최신 Release 빌드의 단계별 시간을 측정해 기준선을 확정한다.
2. 현재 그림 방식·내부 배율을 유지하면서 경로·문자 배치와 정적 레이어를 재사용하는 안을 실험한다.
3. 큰 폭의 개선이 부족하면 GPU 합성과 버퍼 직접 출력을 실험한다. 앱 전환·잠금 지원을 함께 검증한다.
4. 내부 배율 변경은 별도 품질 비교 후보로 둔다. 1080p 출력이 같다는 이유만으로 동등 품질이라고 판단하지 않는다.

## 2. 확인된 사실과 아직 모르는 것

근거: [기존 인코딩 성능 노트](../product/features/encoding-performance.md), [내보내기·공유 FRD](../specs/frd/export-and-share.md) §2 인코딩, [경로 렌더링 FRD](../specs/frd/route-rendering.md) §9 출력 규격.

2026-09-13 iPhone 11 Pro / iOS 26.6.2 **개발 빌드**에서 합성 좌표 1,000개, 불빛 러너·글래스·동적 페이스·한글 문구로 측정했다.

| 기존 기록의 항목 | 시간 |
|---|---:|
| 최초 방식의 JS 요청~완료 응답 | 56.357초 |
| 완성 화면 재사용 후 JS 요청~완료 응답 | 40.329초 |
| 개선판 네이티브 내부 총시간 | 40.146초 |
| 프레임 래스터화 | 26.976초 |

| writer 준비 대기 | 0.411초 |

기존 개선은 약 28.4% 단축했고, 그 입력의 디코딩된 전체 360프레임이 동일했다. 마지막 3초 정지 구간은 이미 재사용한다. 현재 코드는 271프레임을 그리고 360프레임을 인코딩하므로 이것을 새 개선안처럼 계산하면 안 된다.

현재 구현의 확인 위치:

- [RouteRendererModule.swift](../../frontend/modules/route-renderer/ios/RouteRendererModule.swift): `prepareBackground`, `drawFrame`, `writeClip`, `pixelBuffer`, `RenderBackgroundLease`.
- [share.tsx](../../frontend/src/app/share.tsx): 공유 화면 진입 시 네이티브 요청, 성공 후 보관함 등록과 백그라운드 작업 완료 신호.

`writeClip`은 H.264·1080×1920·30fps·12초로 출력한다. 압축 비트레이트·프로파일은 코드에 명시하지 않고 AVFoundation 기본값을 사용한다. 현재 어떤 하드웨어 인코더가 선택되는지는 측정하지 않았다. writer 대기 시간이 짧다는 것은 이 입력에서 프레임 공급이 주요 병목이라는 근거이지, 압축 자체가 0.411초라는 뜻은 아니다.

`UIGraphicsImageRenderer`의 내부 배율은 화면 배율을 따르며 기존 측정은 3배였다. 이 경우 1080×1920 포인트를 **3240×5760 픽셀**로 그린 뒤 출력 크기로 축소한다. 픽셀 수가 9배라는 뜻이지, 배율을 낮추면 전체 시간이 9배 줄어든다는 뜻은 아니다. 기본 배율은 [Apple scale 문서](https://developer.apple.com/documentation/uikit/uigraphicsimagerendererformat/scale)에 명시되어 있다.

배경의 크롭·스케일은 이미 한 번 준비한다. 다만 각 프레임에서 그 배경과 정적인 전체 경로, 문자 배치, 글로우 등을 다시 합성한다. 진행 중 변하는 거리·시간·페이스와 구간 반짝임은 정적 캐시에 그대로 넣을 수 없다.

[확인 필요] 현재 TestFlight와 같은 Release 구성의 실제 시간, 프리셋·사진·기기별 분포, 열·저전력 영향. 기존 화면 잠금 테스트의 223.819초는 입력이 달라 40초와 비교할 수 없다. 이번 조사에서 실기기 재측정은 하지 않았다.

## 4. 추천 기술 방향과 주의점

### 반복 계산을 먼저 줄인다

동일 입력에서 변하지 않는 경로 구간·폰트·날짜·레이아웃을 작업 시작 시 준비한다. 배경과 고정 경로는 기존 내부 해상도로 캐시하되, 레이어를 묶어 그릴 때 알파·그림자 합성 결과가 달라지는지 확인한다. 숫자가 바뀌는 러닝 데이터는 동적으로 유지한다. 이미 완료 화면 버퍼와 renderer, 배경 준비를 재사용하는 부분은 그대로 둔다.

과거 측정에서 변환 비용 12.136초를 전부 없애도 다른 비용이 같다면 전체 단축은 약 30%에 그친다. 실제로 축소·변환 비용을 모두 없앨 수 있다는 뜻은 아니다. **2배 이상을 목표로 하려면 26.976초의 그리기 비용도 함께 줄여야 한다.**

### GPU는 UIImage를 옮기는 데서 끝내지 않는다

현재 CPU `drawFrame`을 그대로 두고 마지막 변환만 GPU로 바꾸면 가장 큰 래스터화 비용이 남는다. 배경·고정 글자를 한 번 준비하고, 진행 경로·글로우·동적 값을 GPU에서 합성해 영상용 버퍼에 쓰는 구조를 실험한다. Core Image는 합성·블러 후보이며 자체적으로 모든 벡터 경로와 문자 배치를 해결하지 않는다. Metal 경로 또는 CPU에서 준비한 텍스처와 결합하는 설계가 필요하다.

[Apple CVMetalTextureCache 문서](https://developer.apple.com/documentation/corevideo/cvmetaltexturecache-q3j)는 Core Video 이미지 버퍼를 Metal에서 직접 읽고 쓰는 경로를 제공한다. 이것만으로 인코더 내부 변환까지 모두 사라진다는 보장은 없다. GPU 완료 전에 버퍼를 인코더에 전달하거나, 인코딩 중인 버퍼를 덮어쓰지 않도록 수명·동기화를 설계해야 한다.

[Apple Core Image 최적화 세션](https://developer.apple.com/videos/play/wwdc2020/10008/)은 컨텍스트 재사용과 Metal을 함께 쓸 때의 명령 큐 정리를 설명한다. 기존 고배율·블러·색공간을 보존한 GPU 합성을 먼저 비교하고, 배율·색상 정책 변경은 섞지 않는다.

### 화면 잠금 기능과 함께 검증한다

현재 `RenderBackgroundLease`는 GPU 리소스를 요청하지 않는다. GPU로 전환한다고 기존 백그라운드 실행 권한이 GPU 실행까지 허용하는 것은 아니다.

Apple의 [requiredResources](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtaskrequest/requiredresources)와 [장시간 작업 안내](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)는 지원 여부 확인 후 GPU 리소스를 요청하도록 안내한다. [Apple DTS 답변](https://developer.apple.com/forums/thread/794072)은 실행 시 `supportedResources` 확인과 별도 Background GPU Access entitlement가 필요하다고 설명한다.

[확인 필요] 대상 아이폰의 실제 지원 여부. 미지원 기기에는 CPU 방식 유지가 필요하다. 실행 도중 잠금 시 전환한다면 마지막으로 인코더에 전달한 프레임부터 이어갈 수 있는 상태 관리와 두 방식의 시각적 일치를 검증해야 한다. 무조건 처음부터 다시 만드는 방식은 대기를 악화시킨다. 이 복잡도가 크면 작업 시작부터 안전한 CPU 방식을 선택하는 안과 비교한다.

## 5. 검토 후 기획할 성능·품질 기준 제안

**목표 수치는 아직 합의 전이다.** 동일 Release 빌드·동일 기기·동일 입력에서 총 생성 시간 중앙값 50% 이상 감소를 1차 후보 목표로, 12초 영상의 10초 이내 완성을 도전 목표로 제안한다. 둘 다 보장값이 아니며 최신 기준선 측정 후 현실성을 판정한다. 성공 기준은 사용자가 완료를 누른 순간부터 정상 mp4와 보관함 등록이 모두 끝난 순간까지다.

측정 계획:

- 합성 입력으로 기본 경로 그림·불빛 러너·구간 점등, 짧고 긴 경로, 기본 배경·고해상도 사진을 포함한다. 기본·글래스·작은 원라인·긴 한글 문구 등 품질 취약 조합을 함께 선정한다.
- 기존 iPhone 11 Pro와 최근 기기 한 대를 우선 대상으로 한다. 동일 기기·OS에서 준비 실행 후 5회씩 측정해 중앙값·최댓값을 보고한다. 발열·저전력·잠금 조건은 일반 전경 조건과 섞지 않는다.
- 준비/전처리, 경로, 글로우, 문자, 버퍼 변환, writer 대기·append, 종료, 보관함 저장을 나눈다. 최대 메모리·열 상태도 기록한다.
- 외부 서버에 개인 GPS·사진을 전송하지 않는다. 대표 사진은 공개·합성 자료 또는 사용자가 해당 테스트에 허용한 자료를 사용한다.

품질과 동작 판정:

- 1080×1920·30fps·12초·360프레임, 프레임 시각과 마지막 평균값 고정을 유지한다. 누락·중복 진행·순서 뒤바뀜·검은 프레임을 확인한다.
- 캐시 등 동일 출력을 의도한 개선은 [전체 프레임 비교 도구](../../frontend/scripts/check-rendered-clips.swift)로 픽셀 일치를 확인한다.
- GPU·배율 변경으로 픽셀 차이가 생기면 자동으로 통과시키지 않는다. 인코딩 전 프레임과 디코딩 후 프레임을 모두 비교해 렌더링 변화와 압축 차이를 분리한다. 영상 전체 점수뿐 아니라 작은 글자·경로 경계·글로우·그라데이션의 확대 비교와 실제 크기 재생을 검토한다. 숫자 유사도만으로 품질 동일을 선언하지 않는다.
- 취소·작업 대체·앱 전환·잠금·저장 공간 부족·시스템 만료·보관함 등록을 확인한다. 미완성 파일을 완성품으로 등록하면 실패다.

## 6. 다음 단계와 문서 정합성

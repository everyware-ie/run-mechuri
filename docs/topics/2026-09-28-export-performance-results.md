# 결과물 생성 속도 개선 실험 결과 보고서

2026-09-28 · Runary · 기준 코드 `98ce5c8`

## 후속 상태

9/29 회의에서 두 프레임 병렬 생성을 제품에 적용해 배포하기로 [결정](../decisions/2026-09-29-export-parallel-rendering.md)했다. 10/3 적용·검증 상태는 [제품 적용 노트](../product/features/export-parallel-rendering.md)에서 확인한다. 아래는 9/28 실험 당시의 기록이며 당시의 보류 상태를 보존한다.

## 결론

네 가지 후보를 작은 실험으로 비교했다. **두 프레임 병렬 생성만 약 30%의 단축을 보였고, 해당 입력에서 영상 픽셀이 동일했다.** 다만 메모리 증가가 있어 일반 앱 기본 적용은 보류했다. 편집 중 재료 준비, 고정 요소 비트맵 재사용, GPU 축소·변환 단독 방식은 중단했다. 아직 10초 이내 생성이나 실제 앱 전체의 안정성을 달성한 상태는 아니다.

## 팀이 알아둘 핵심

영상 생성은 재료를 준비하고, 매 장면을 그리고, 영상 크기로 변환해 파일로 만드는 작업이다. 이번 측정에서는 재료 준비보다 매 장면 그리기와 복사·축소가 대부분의 시간을 차지했다. 먼저 준비하는 아이디어만으로 큰 폭의 단축이 어려웠던 이유다.

병렬 생성은 두 장면을 동시에 만들어 시간을 줄이지만, 두 장면의 작업 공간을 함께 유지해 메모리가 늘어난다. 메모리가 부족하면 앱이 종료될 수 있으므로 실제 편집 화면이 켜진 앱에서 검증해야 한다. 이번 결과는 제품 적용 승인이 아니다.

**TestFlight에는 미반영이다.** 저장소에 남기는 것은 보고서, 재현용 실험 스크립트와 단계별 측정 로그다. 보고서 PR을 머지해도 병렬 처리·캐시·GPU 후보가 앱에서 활성화되지는 않는다.

회의에서 고를 선택지와 담당·기간 등 정할 항목은 [다음 회의 안건 후보](../ideation/phs00/2026-09-28-meeting-agenda.md)에 있다.

## 비교 결과

| 후보 | 해당 실험의 기준선 | 결과 | 영상·메모리 | 판단 |
|---|---|---|---|---|
| 편집 중 재료 준비 | 전체 44.49~48.90초 | 미리 처리할 비용이 0.12~0.20초, 전체의 0.25~0.44% | 캐시 구현 전 비용만 분해 | 효과가 작아 구현 중단 |
| 두 프레임 병렬 생성 | 직렬 평균 43.18초 | 평균 30.13초, 약 30.2% 단축 | 두 비교 쌍 모두 360프레임 픽셀 동일. 최대 resident 평균 약 145MiB 증가 | 후보 유지, 제품 기본 적용 보류 |
| 고정 요소 비트맵 재사용 | 직렬 44.14초 | 45.32초, 단축 관찰 안 됨 | 최대 resident 약 90MiB 증가. 360프레임 픽셀 차이 발생 | 이번 방식 미채택 |
| GPU 축소·변환 단독 | CPU 42.99초 | GPU 49.80초, 단축 관찰 안 됨 | 변환 구간 11.81초 → 16.61초. 백그라운드 GPU 미검증 | 이번 방식 미채택 |

행마다 별도로 측정한 기준선이다. 병렬 처리와 고정 요소 재사용은 결합하지 않았다. 각 방식의 개선율을 더해서 전체 효과를 계산할 수 없다.

## 개선안 조합 가능성

하나만 골라야 하는 것은 아니다. 중간 이미지 복사를 줄이는 개선과 두 프레임 병렬 생성처럼 서로 다른 비용을 줄이는 방법은 함께 적용할 후보가 된다. 그러나 같은 작업을 줄이는 방식은 효과가 겹칠 수 있고 메모리 부담도 달라진다. 단독 효과를 확인한 뒤 조합을 다시 측정한다. 이번 네 가지 실험은 각각 비교했으며 조합 효과를 검증하지 않았다.

현재 효과가 입증된 후보는 병렬 생성 하나다. 다른 방식이 느렸다는 결과만으로 모든 GPU·재사용 설계를 배제하지 않지만, 효과가 없던 이번 구현을 그대로 조합할 근거도 없다.

## 조건과 품질 판정

같은 iPhone 11 Pro(iOS 26.6.2)의 Release 빌드, 미러링을 종료한 전경 네이티브 렌더링을 사용했다. 합성 경로 1,000점·고해상도 합성 배경·불빛 러너·글래스·동적 숫자·한글 문구로 비교했다. 개인 기록과 사진은 쓰지 않았다.

1080×1920·30fps·12초·360프레임, 내부 렌더 배율 3, 폰트·그림자와 인코딩 설정을 유지했다. 단순 해상도 확인에 더해 전체 프레임 시각과 디코딩 RGB 픽셀을 비교했다. 고정 요소 재사용과 GPU 변환은 각각 360프레임 모두 픽셀 차이가 있어 일치 검사를 통과하지 못했고, 육안 동등 품질도 확정하지 않았다. GPU 변환의 평균 절대 채널 차이는 0.856/255, 최대 차이는 99/255였다. 픽셀 차이만으로 화질 저하를 단정하지 않는다.

시간에는 JS 요청 전달·보관함 등록이 포함되지 않는다. 네이티브 단독 프로세스의 메모리로, 실제 편집 화면·JS가 살아 있는 앱의 최대 사용량을 대신하지 않는다. 이번 실험에서는 화면 잠금과 앱 전환 성능을 검증하지 않았다.

## 다음 판단

1. 병렬 처리를 제품에 넣으려면 실제 앱의 메모리 여유, 취소·작업 교체·잠금 동작과 여러 입력의 품질을 먼저 검증한다. 필요하면 자원 상황에 따라 직렬로 처리하는 방식을 설계한다.
2. 더 큰 폭 단축은 반복적인 고배율 프레임 생성과 복사·축소를 줄이는 구조에서 찾아야 한다. CPU에서 그린 이미지를 마지막 변환 단계에서만 GPU에 넘기는 이번 방식은 느려졌다. 경로·글로우 자체를 처음부터 GPU에서 그려 중간 이미지를 줄이는 구조와 CPU 버퍼 직접 재사용은 아직 실험하지 않은 후보다. 지원 기기의 백그라운드 GPU 조건과 CPU 대체 경로가 함께 검토되어야 한다.
3. 성과가 작은 후보를 계속 확대하지 않고 각 단계의 속도·품질·메모리 결과로 채택 여부를 정한다.

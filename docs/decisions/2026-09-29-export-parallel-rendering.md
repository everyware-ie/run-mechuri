# 결과물을 장면 둘씩 동시에 그려 생성 시간을 줄인다

> 9/28에 실험한 네 가지 중 효과가 있던 하나를 앱에 넣는다.
> 배경과 논의 과정: [2026-09-29 회의 종합](../meetings/2026-09-29/synthesis.md)

## 결정

**두 프레임 병렬 생성을 앱에 넣어 배포한다. 현수가 맡는다.** 네 가지 중 가장 효과가 컸던 것을 일단 도입하기로 했다. 이 실험을 해 온 사람이 현수라서 이어서 맡는다.

영상에 들어갈 장면을 하나씩 차례로 그리던 것을 **둘씩 동시에** 그린다.

| | |
|---|---|
| 실험에서 | 약 43초 → 30초 (약 30% 단축) |
| 화질 | 두 비교 쌍 모두 360프레임 픽셀이 같았다 |
| 대가 | 최대 메모리가 약 145MiB 늘었다 |

수치는 [결과 보고서](../topics/2026-09-28-export-performance-results.md)의 것이다. iPhone 11 Pro 한 대에서 합성 입력으로, 화면을 켜 둔 상태로 쟀다.

## 왜 이것인가

**네 가지 중 빨라진 것이 이것 하나였다.**

| 방법 | 결과 |
|---|---|
| 편집하는 동안 재료를 미리 준비 | 준비에 드는 시간이 전체의 0.5%도 안 돼 효과가 없었다 |
| **장면을 둘씩 동시에 그리기** | **43초 → 30초** |
| 매번 같은 배경·글자를 한 번만 그리기 | 44초 → 45초. 빨라지지 않았다 |
| 크기 줄이는 일을 GPU에 맡기기 | 43초 → 50초. 오히려 느려졌다 |

## 정하지 않은 것

| | |
|---|---|
| 목표 시간 | 안건에서 "화면 켜고 30초"인지 "잠갔을 때 1분"인지 물었으나 정하지 않았다 |
| 화면을 잠갔을 때 | 9/13 기록에 약 224초가 있다. 이번 실험은 화면을 켜 둔 경우만 쟀다 |
| 정지 이미지 먼저 | 영상이 만들어지는 동안 정지 이미지로 먼저 공유하게 하는 안이다. PRD §12 리스크와 폴백에 있다. 다루지 않았다 |
| 다음 성능 작업 | 성능 리서치는 [9/8에 지응·지민이 맡았다](2026-09-08-scope-and-roles.md). 이번 적용 뒤 누가 이어 갈지는 정하지 않았다 |

## 알고 가는 것

**실험 보고서가 제품에 넣기 전에 확인하라고 적어 둔 것이다.** 회의에서 조건으로 정한 것은 아니고, 적용할 때 참고한다.

- **실제 앱의 메모리.** 실험은 네이티브 렌더러만 따로 돌린 프로세스에서 쟀다. 편집 화면과 JS가 살아 있는 실제 앱은 더 쓸 수 있고, 메모리가 모자라면 앱이 꺼질 수 있다
- **취소, 앱 전환, 화면 잠금** 때의 동작
- **여러 입력에서의 화질**

보고서는 필요하면 자원 상황에 따라 한 장씩 그리는 방식으로 돌아가는 설계도 제안했다.

## FRD와의 관계

[내보내기·공유 FRD](../specs/frd/export-and-share.md) §2-5 앱 전환·화면 잠금 중 인코딩은 속도를 개선해도 1080×1920·30fps·12초와 인코딩 품질 설정을 유지하라고 한다. 이 방식은 출력 영상이 같으므로 **FRD 규칙을 바꾸지 않는다.**

실험 기록은 [프레임 병렬 생성 보고서](../product/features/export-frame-parallel.md)에 있다. 적용할 때는 구현 노트에 이 결정과 FRD를 연결한다.

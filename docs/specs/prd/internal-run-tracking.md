# 자체 러닝 측정 내부 검증

## 1. 왜 먼저 내부에서 측정하나

다른 측정 앱의 기록은 건강 앱에 GPS 경로까지 저장되지 않을 수 있다. 파일 가져오기는 외부 앱에서 파일을 준비하는 과정이 필요하다. Runary가 직접 측정하면 앞으로 뛰는 기록을 앱 안에서 만들 수 있다.

2026-10-05 사용자는 최소 측정 기능을 먼저 도입하고 내부에서 검증하자고 요청했다. 검증 대상은 잠금·백그라운드에서의 기록 유지, GPS 정확도, 배터리 소모, 앱 종료 후 기록 복구다. 2026-10-05 사용자는 연결된 [FRD](../frd/internal-run-tracking.md)와 지표·실패 복구 추천안을 확인하고 구현 착수를 승인했다.

## 2. 범위

홈과 첫 실행 안내에서 내부 테스트 진입 경로를 제공한다. 2026-10-05 사용자는 첫 버전의 추천 범위를 채택했다. 아이폰 측정·기기 내 보관·복구와 선택적으로 사용하는 Runary 워치 연동을 구현 범위에 포함한다. 측정 시작·일시정지·재개·종료와 기기 안의 측정 기록 목록·상세·삭제를 만든다. 상세에는 경로와 진단 정보를 보여준다. 심박을 사용하지 않는 아이폰 단독 GPS 측정은 건강 데이터 권한 없이 테스트할 수 있어야 한다.

2026-10-05 사용자는 내부 테스트용이라도 실제 서비스에 맞는 러닝 UI를 요청했다. 시작·측정·완료가 분명한 화면, 같은 중요도의 네 지표, 쉽게 접근하는 제어를 우선하고 진단은 보조 영역에 둔다. 내부 접근 제한과 측정 범위는 유지한다.

이번 단계는 측정의 신뢰성을 검증한다. 기존 건강 앱 기록 선택·편집·영상 생성은 유지한다. 자체 측정 기록을 기존 편집에 연결하는 기능, 내비게이션, 자동 일시정지, 훈련·음성 코칭, 계정·서버 업로드는 이번 내부 검증에서 제외한다. 2026-10-05 사용자가 지도 추가 착수를 승인했다. 준비·측정 화면의 현재 위치와 지나온 경로, 완료·이전 기록의 전체 경로를 Apple 지도에 표시한다. 지도 화면과 GPS 수집은 분리하며 기존 수집·계산·보관을 재사용한다. 지도 탐색 후 현재 위치 따라가기로 복귀할 수 있게 한다. 길 찾기·코스 추천·위성 전환·오프라인 다운로드·워치 지도는 이번 범위에 넣지 않는다.

### 2-1. 2026-10-05 사용자 보완

사용자는 운동 중 심박을 확인하며 유지하는 것을 중요한 요구로 밝혔다. Apple Watch의 실시간 심박과 측정 화면, 케이던스 등 기본 러닝 항목을 범위에 추가한다. 추가로 다른 운동 앱을 시작하지 않고 Runary만으로 심박을 측정할 수 있어야 한다고 명확히 했다. Apple Watch를 착용하고 Runary 워치 앱에 필요한 권한을 허용한 상태가 심박 측정의 조건이다. 이 요구는 워치 연동 기능을 제공해야 한다는 뜻이며 모든 러닝 기록에 심박을 필수로 수집한다는 뜻은 아니다. 워치 미착용·연동 미사용·심박 미수신이어도 아이폰으로 러닝을 시작·종료·저장할 수 있어야 한다. 아이폰만 사용하는 GPS 테스트나 다른 앱의 심박 읽기 실험을 워치 연동 기능의 완료로 보지 않는다.

| 범위 | 담는 것 | 검증 방식 |
|---|---|---|
| 아이폰 측정 | GPS 경로·거리·측정 시간·현재/평균 페이스·걸음 수·현재/평균 케이던스 | Runary 단독 사용과 다른 아이폰 측정 앱의 병행 비교 |
| 워치 연동 (기능 제공 필수, 사용 선택) | Runary 워치 앱과 자체 운동 세션, 현재/평균/최대 심박, 워치의 시간·거리·페이스·케이던스 화면, 시작·일시정지·재개·종료 동기화 | 다른 워치 운동을 시작하지 않고 Runary만으로 심박을 측정·표시·보관 |
| 병행 심박 읽기 실험 (선택) | 기존 워치 운동이 건강 데이터에 남기는 심박의 시각·전달 지연·출처 확인 | Runary 자체 운동 세션을 사용하지 않는 비교 실험. 필수 기능의 대체나 착수 조건이 아님 |
| 추가 기본 항목 후보 | 칼로리·고도·상승고도·심박 구간·구간별 기록 | 센서·지원 기기와 실제 효용을 확인해 범위 확정 |

**2026-10-07 개정: 건강 앱 심박 불러오기를 기능으로 넣는다.** 10/6 회의 뒤 사용자가 정했다([결정](../../decisions/2026-10-06-second-sprint-app-store.md)). 나이키 런처럼 애플 운동 같은 다른 운동 앱과 동시에 측정할 수 있게, 건강 앱에 저장된 심박을 불러온다. 위 표의 병행 심박 읽기는 선택 실험이 아니라 제공할 기능이 된다. Runary 워치로 직접 재는 방식을 같이 둘지와 세부 동작은 FRD를 고치면서 정한다.

케이던스는 분당 걸음 수로 표기한다. 아이폰에서는 지원되는 기기의 Core Motion으로 측정하고, 워치에서는 걸음 수·운동 데이터로 검증할 산출 방식을 정한다. 센서가 없거나 권한·수신이 없으면 값을 만들어 넣지 않는다. 현재 페이스·심박·케이던스는 최신값인지 확인하며 오래된 값을 현재값처럼 보여주지 않는다. 시간·거리·페이스·심박은 같은 중요도로 읽을 수 있게 배치한다. 심박만 크게 강조하지 않는다. 목표 심박 범위·진동 알림은 첫 버전에 포함하지 않는 추천안이며, 지표 계산의 상세 제안은 FRD §3-1 지표 계산 추천안에 둔다.

사용자는 기본 워치 운동 앱과 Nike Run Club을 함께 사용하면 Nike에도 심박이 표시된다고 알렸다. Nike가 어떤 API로 받는지와 표시되는 값의 지연은 아직 확인하지 않았다. 다른 앱과 병행하는 심박 읽기는 선택적인 비교 실험으로 검토한다. 단일 워치 세션 제한을 이유로 다른 앱의 저장된 심박을 읽는 것까지 불가능하다고 판단하지 않는다.

추가로 사용자는 Nike Run Club을 아이폰에서 실행하고 워치에서 심박을 확인한다고 설명했다. 아이폰에서 시작해도 워치에 잘 나타나지 않을 때가 있어 불편하다고 알렸다. 따라서 아이폰에서 시작한 측정을 워치에서 쉽게 확인하는 흐름과 연결 실패를 알아차리고 복구하는 동작을 워치 단계의 요구에 넣는다. 워치에서 심박을 보는 화면이 어떤 앱인지와 Nike의 내부 연동 방식은 이 설명만으로 확정하지 않는다.

첫 내부 버전의 완료 범위에는 Runary 자체 워치 운동 세션으로 심박을 수집하고 아이폰에 전달하는 기능을 포함한다. 개발 순서는 아이폰 GPS와 워치 연동으로 나눌 수 있지만 아이폰 GPS만 끝내고 요구를 완료 처리하지 않는다. 기존 운동 앱 실행을 심박 측정의 전제 조건으로 두지 않는다. 워치가 없거나 연동을 사용하지 않거나 심박 권한을 허용하지 않으면 아이폰 GPS 측정은 가능하며 심박은 미측정으로 표시한다. 심박 유무를 기록 저장의 조건으로 두지 않고, 없는 값을 0으로 채우거나 평균 계산에 포함하지 않는다. 운동 저장·중복 방지·권한과 연결 복구 정책은 승인된 FRD에 정의했다.

Apple Watch는 동시에 운동 세션 하나만 실행한다. 기존 워치 운동 앱과 Runary 워치 운동을 함께 시작하면 세션이 충돌한다. 이 제약과 건강 데이터 읽기는 별개다. 저장소의 새 심박을 관찰할 수 있지만 워치에서 아이폰으로 전달되는 주기까지 앱이 정하지는 못한다. 운동 중의 안정적인 실시간 전달은 실제 기기에서 확인해야 한다. [Apple 운동 세션 안내](https://developer.apple.com/documentation/healthkit/hkworkoutsession), [기기 간 운동 연동](https://developer.apple.com/videos/play/wwdc2023/10023/), [새 건강 데이터 관찰](https://developer.apple.com/documentation/healthkit/hkanchoredobjectquery), [Core Motion 케이던스](https://developer.apple.com/documentation/coremotion/cmpedometerdata/currentcadence).

## 3. 기존 제품 범위와의 관계

[MVP PRD](running-drawing-mvp.md) §5 제외는 공개 제품의 범위로 유지한다. 자체 측정은 개발 빌드와 팀 내부 TestFlight 빌드에서 진입하는 내부 검증 기능이다. 사용자는 기능 구현 후 TestFlight에서 사용하겠다는 설치 방향을 정했다. 개발 서버 없이 실행되는 아이폰 앱에 Runary 워치 앱을 함께 포함하고, 일반 외부 테스터·공개 링크에는 이 내부 빌드를 배정하지 않는다. 공개 빌드에는 내부 진입 경로와 위치 추적 설정을 기본 제공하지 않는다. 구현·검증 후 내부 배포를 진행하는 계획이며 현재 배포된 상태는 아니다.

사용자는 위치·동작 및 피트니스·건강 데이터·카메라·사진 저장 등 서비스의 권한을 모아 확인하는 별도 화면도 요청했다. 내부 측정 진입점에서 `앱 권한` 화면으로 연결하고 기존 기능의 실패 안내에서도 접근할 수 있게 하는 방안을 제안한다. 권한 변경은 OS의 설정·건강 데이터 관리에서 수행하며 앱은 확인·안내 역할을 맡는다. 이는 공개 MVP의 설정 화면 제외에 대한 내부 테스트용 추가 범위다. [공통 규칙 FRD](../frd/common-rules.md) §2-1 기록이 하나도 없을 때의 공개 제품 규칙을 이번 내부 검증으로 변경하지 않는다.

기존 출시 결정을 뒤집거나 새 측정 기능의 출시를 확정한 문서가 아니다. 공개하기 전에는 MVP PRD·관련 결정문·기록 선택 FRD·개인정보 처리방침·스토어 권한 안내를 함께 개정해야 한다.

## 4. 성공의 기준

**최소 기준은 나이키 런, 스트라바 같은 유명 러닝 앱과 같은 방식이다** (2026-10-07 사용자). 측정에 기능적인 하자가 없어야 한다. GPS가 끊긴 구간 처리처럼 정하지 않은 동작은 그 앱들의 방식을 확인해서 맞춘다.

기능 구현과 실제 운동 검증을 구분한다. 자동 검사와 책상에서의 실행만으로 GPS 정확도나 운동 중 배터리 사용을 통과 처리하지 않는다.

| 질문 | 확인 방법 |
|---|---|
| 워치 사용 시 Runary만으로 심박을 볼 수 있나 | 기존 워치 운동을 시작하지 않고 Runary 워치 연동을 사용해 심박 수집·양쪽 표시·보관을 확인 |
| 워치·심박 없이도 러닝할 수 있나 | 워치 미착용·연동 미사용·심박 미수신에서 아이폰 측정 시작·종료·저장이 가능하고 심박은 미측정인지 확인 |
| 잠금·다른 앱 사용 중에도 위치가 들어오나 | 전면·다른 앱·화면 잠금의 야외 실측에서 좌표 시각과 공백을 비교 |
| 거리가 적절한가 | 평소 운동 앱과의 거리·경로 차이를 먼저 확인하고, 차이가 큰 경우 기준 코스를 별도 확인 |
| 배터리가 적절한가 | 평소 운동의 잔량 변화를 자동 기록하되, 동시 실행 앱의 영향을 분리한 비교를 나중에 수행 |
| 종료 뒤 데이터가 남나 | 강제 종료와 재실행에서 마지막 저장 경로·거리·시간·중단 표시를 확인 |
| 없어진 구간을 잘못 그리지 않나 | 일시정지·GPS 공백·중단 뒤 재개에서 구간 사이 연결과 거리 증가를 확인 |

[내부 검증 계획](../../ops/internal-run-tracking-qa.md)에 수행 조건·제안 기준과 결과를 모은다. 바쁜 팀원이 평소 러닝에서 Runary를 시작하고 종료하는 것으로 관찰 자료를 모은다. 원하면 다른 아이폰 앱과 비교하되 Runary 워치 운동과 다른 워치 운동을 중복 시작하지 않는다. 진단은 자동 기록하고 사람이 적는 항목을 줄인다. 통제되지 않은 병행 사용만으로 GPS 정확도·배터리 소모를 합격 처리하지 않는다. 복구 같은 위험 항목은 개발 담당자가 별도 검증한다.

## 5. 중단과 복구의 의미

화면 잠금·다른 앱으로 전환은 계속 측정하는 상황이다. 강제 종료·크래시·OS 종료 후에는 저장된 기록을 복구하는 상황이다. 둘을 같은 기능으로 안내하지 않는다.

아이폰 단독 측정의 첫 구현은 앱 종료 중 GPS 수집이나 자동 재실행을 보장하지 않는다. 재실행하면 저장된 시점까지 복구해 중단 상태로 보여준다. 사용자가 재개하면 새 구간으로 측정한다. 종료 중 잃은 좌표나 시간을 만들어 넣지 않는다. 아이폰 앱 종료 후에도 살아 있는 워치 세션과 재연결하는 정책은 별도로 정하고 검증한다. 아이폰 앱 종료를 워치 세션 종료로 단정하지 않는다.

## 6. 보관과 삭제

좌표·시각·정확도·걸음 수·케이던스와 검증용 상태·배터리 정보를 기기에 보관한다. 병행 심박 읽기에서는 받은 심박·출처·측정 시각·수신 지연을, 직접 워치 연동에서는 연결 상태도 보관한다. Runary 서버로 보내지 않는다. 지도 배경 표시는 Apple 지도 서비스의 네트워크 요청을 사용하며, 기기 내 기록 보관과 지도 제공자의 요청을 구분해 안내한다. 사용자가 채택한 `진단 요약 복사`는 빌드·기기·거리·시간·GPS 공백·센서 지연·오류·배터리 같은 집계만 복사한다. 좌표·장소·개별 심박 원본과 식별 가능한 기기 ID는 포함하지 않는다. 사용자가 복사한 내용을 팀에 전달하며 자동 전송은 없다. 사용자가 측정 기록을 삭제하면 해당 원본과 진단 정보도 삭제한다. 앱 삭제 시 사라지며 이번 버전은 백업·동기화를 제공하지 않는다. 내부 기록 폴더는 시스템 클라우드 백업에서 제외한다.

## 7. 다음 결정

첫 버전 범위·주요 정보의 동일한 중요도·진단 요약 복사·내부 TestFlight 사용 방향은 2026-10-05 사용자 답변을 반영했다. [FRD](../frd/internal-run-tracking.md) §9 사용자 선택과 확정한 기준에 지표 계산·GPS 준비와 시작 시각·센서 기준·실패 복구·권한 화면의 상세 추천안을 분리해 기록한다. 상세 추천안과 전체 FRD의 착수 확인을 완료했다. 기술값의 초기 설정과 실제 제품 범위 결정을 구분한다.

실제 운동 검증이 끝나면 자체 측정을 공개할지, 어느 진단을 제품에서 제거할지, 측정 기록을 기존 만들기 흐름에 연결할지 정한다. 검증이 부족하면 공개 진입점을 추가하지 않고 내부 단계에서 개선한다.

2026-10-06 회의에서 11/3 ~ 11/10 정식 등재 재제출에 측정 기능을 넣기로 했다([결정](../../decisions/2026-10-06-second-sprint-app-store.md)). 그 전에 안정성을 먼저 잡는다. 공개 범위와 §3에 적은 공개 전 개정(MVP PRD, 결정문, 기록 선택 FRD, 개인정보 처리방침, 스토어 권한 안내)은 아직 하지 않았다.

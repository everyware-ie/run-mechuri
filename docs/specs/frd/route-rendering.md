# 경로 렌더링 FRD

> **status: `draft`.** approved가 아니면 구현 근거가 아니다.
> 근거: [PRD](../prd/running-drawing-mvp.md) · [2026-08-18 결정](../../decisions/2026-08-18-native-ios-and-mvp-scope.md)

## 0. 범위

트랙 하나가 들어와 9:16 클립 하나가 나오기까지를 정한다. 투영, 전처리, 애니메이션, 프리셋 정의, 각인, 배경 합성, 출력 규격이 여기 있다.

**이 문서는 렌더러가 무엇을 할 수 있는지를 정한다.** 사용자가 그중 무엇을 고를 수 있는지는 [결과물 편집](result-editing.md)이 정한다.

| 담지 않는 것 | 어디에 |
|---|---|
| 프리셋 선택, 크기·위치·회전, 다듬기 세기, 각인 모드 | [결과물 편집](result-editing.md) |
| 배경을 어떻게 확보하나 | [배경 선택](background-selection.md) |
| 트랙을 어디서 가져오나 | [러닝 기록 선택](run-record-selection.md) |
| 색상값, 타이포, 간격 | 디자인 시스템 |

## 1. 원칙

| # | 원칙 | 출처 |
|---|---|---|
| R1 | 기본값만으로 완성된 결과물이 나온다. 편집은 그 위에서 바꾸는 것이지 편집해야 완성되는 것이 아니다 | 2026-08-19 |
| R2 | 실제로 지나가지 않은 길이 보이면 안 된다. 왜곡의 상한은 "이 그림을 보고 같은 길을 다시 뛸 수 있는가"다 | PRD §8 |
| R3 | 표현 요소는 전부 러닝 데이터에서 나온다. 예외는 배경 하나뿐이다 | PRD P1 |

## 2. 입력

> 렌더러가 무엇을 받는지 확인할 때 본다.

데이터 출처와 무관하게 아래 형태로 정규화된 뒤에야 렌더러를 만난다. HealthKit에서 왔든 나중에 GPX에서 왔든 렌더러는 구분하지 않는다.

| 필드 | 필수 | 비고 |
|---|---|---|
| 좌표열 (시각, 위도, 경도) | 필수 | 시간순 |
| 총 거리 | 필수 | 각인에는 선 길이가 아니라 이 값을 쓴다 |
| 총 시간 | 필수 | |
| 평균 페이스 | 필수 | |
| 심박 | 선택 | 아래 참고 |
| 고도 | 선택 | MVP 프리셋 셋은 쓰지 않는다 |

### 2-1. 심박은 있을 수도 없을 수도 있다

HealthKit이 심박을 주면 함께 읽어 트랙에 담는다. 시계나 밴드를 찼다면 대체로 있고, 나중에 GPX로 가져온 기록에는 없는 경우가 많다.

**심박에 의존하는 표현은 "있을 때만" 동작해야 한다.** 심박이 없다고 렌더링이 실패하거나 화면에 빈 자리가 남으면 안 된다.

MVP 프리셋 셋은 심박을 쓰지 않으므로 없어도 결과물이 온전하다. 각인에서는 심박이 있을 때만 항목이 나타난다(§7-1). 로드맵의 심박 맥동 프리셋은 이 데이터 위에 바로 얹힌다.

### 2-2. 그릴 수 없는 트랙은 여기까지 오지 않는다

좌표 수가 지나치게 적거나 거리가 너무 짧으면 그림이 되지 않는다. 그런 기록은 목록에서 고르는 시점에 걸러낸다([러닝 기록 선택](run-record-selection.md) §5). **렌더러는 그릴 수 있는 트랙만 받는다.**

### 2-3. 실제 트랙이 어떻게 생겼나

phs00의 실외 러닝 기록 두 건을 뜯어봤다. 2026-06-11(4.44km)과 2026-06-17(2.73km)이고, HealthKit에서 GPX로 내보낸 것이다. (2026-08-25)

| 항목 | 값 |
|---|---|
| 샘플 간격 | 1초. 두 파일 모두 99% 이상 |
| 점 간 거리 | 중앙값 약 2m |
| 트랙 포인트 | 4.44km에 2,082개 |
| 고도 | 있다 |
| **심박** | **없다** |

**점이 매우 촘촘하다.** 2m 간격이면 GPS 노이즈가 그대로 들어 있다는 뜻이라 다듬기(§3-2)가 실제로 필요하다. 12초 클립으로 치면 프레임당 5~6점을 소화해야 한다.

**심박이 없는 것은 GPX 경로의 한계일 수 있다.** 심박은 워크아웃과 별도로 저장되므로 내보내기 앱이 안 담았을 가능성이 있다. HealthKit을 직접 읽으면 다를 수 있어서 아직 단정하지 않는다. 다만 §7-1의 "심박은 있을 때만" 규칙이 실제로 자주 발동한다는 것은 확인됐다.

## 3. 전처리

> 좌표를 손보는 단계다. 그리기 전에 무엇이 일어나는지 정한다.

### 3-1. 이상점 제거

명백히 잘못 찍힌 좌표는 항상 제거한다. **다듬기 세기를 0으로 둬도 적용된다.** 스타일이 아니라 오류 처리이기 때문이다.

### 3-2. 다듬기

GPS 노이즈로 지글거리는 선을 정리한다. 축은 둘이다. **직선**은 곧게 뻗어야 할 구간의 흔들림을 펴고, **코너**는 길모퉁이의 각을 다듬는다.

직선은 시원하게, 코너는 실제 길모퉁이만큼 다듬는다. 직선을 펴려고 코너를 뭉개지 않는다(PRD §8).

**슬라이더 범위 자체를 안전 구간으로 잡는다.** 사용자가 최대치까지 올려도 R2를 깨지 않아야 한다. 그래서 경고나 차단 UI를 두지 않는다. 사용자에게 어떻게 노출할지는 [결과물 편집](result-editing.md) §5가 정한다.

`[확인 필요]` 안전 구간의 상한. [경로 보정 수준 비교 화면](../../ideation/phs00/2026-08-17-route-stylization-levels.html)에서 원본 대비 평균 이탈(m)을 보며 정한다. 잠정 기준은 B~C 수준이다(패널 순서: A 원본 / B 가벼운 정리 / C 양식화). 이 값은 출발점이지 통과 기준이 아니다. 드로잉 담당이 시도하면서 바뀔 수 있다.

### 3-3. 같은 구간을 여러 번 지날 때

애니메이션은 기록된 순서를 그대로 따라간다. 같은 길을 두 번 지났으면 그 구간 위를 두 번 지나간다. 왕복이든 같은 블록을 여러 바퀴 돈 것이든 마찬가지다.

경로는 시간순 좌표열이고 드로잉은 그 위를 따라가는 애니메이션이다. **특별한 처리가 아니라 자연스러운 결과이므로 옵션으로 두지 않는다.**

다만 완성된 정지 화면에서는 겹친 선이 한 줄로 보인다. 지나간 횟수는 그리는 동안에만 보이고 최종 그림에는 남지 않는다.

#### 왕복 분리는 MVP에서 뺀다

겹친 구간을 두 줄로 벌려 나란히 보여주는 처리를 말한다. 정지 화면에서도 왕복이 읽히게 하는 방법이지만 넣지 않는다.

실제로 두 줄로 뛴 적이 없으므로 **없는 선을 만들어내는 조작이고, R2에 걸린다.** 켤 때 사용자가 알 수 있게 하려면 안내 UI까지 필요해서 일정 대비 값어치도 약하다.

`[확인 필요]` 겹쳐 지나간 구간을 더 밝게 또는 굵게 표시하는 안. 선의 위치를 옮기지 않으므로 R2에 걸리지 않으면서, 정지 화면에도 "여기를 여러 번 지났다"가 남는다. 3주차에 실제 왕복 코스로 보고 판단한다.

### 3-4. 신호가 끊긴 구간

**좌표가 아예 없는 구간이 생긴다.** 터널이나 건물 사이에서 GPS가 잡히지 않는 경우다. 잘못 찍힌 점을 빼는 §3-1과는 다른 문제다. 그쪽은 있는 점이 틀린 것이고 이쪽은 점이 없는 것이다.

실제 샘플에서 나왔다. 2026-06-17 기록에 **82초짜리 공백**이 있고, 그 앞뒤 두 점 사이가 **26m** 떨어져 있다(§2-3). 나머지 구간이 점 간 2m인 것을 생각하면 열 배 이상이다.

두 점을 그냥 이으면 **실제로 지나가지 않은 직선이 그려진다.** R2에 걸린다.

`[확인 필요]` 공백을 어떻게 그릴지. 후보는 셋이다.

| 안 | |
|---|---|
| 그냥 잇는다 | 가장 단순하지만 R2를 어길 수 있다 |
| 점선이나 흐린 선으로 잇는다 | 확실하지 않다는 것을 보여준다 |
| 끊어서 그린다 | 정직하지만 그림이 두 동강 난다 |

**얼마나 흔한지부터 봐야 한다.** 팀이 GPX를 모으면 공백이 몇 번, 몇 미터씩 나오는지 함께 센다.

## 4. 프레이밍

> 경로를 화면 어디에 얼마만 하게 앉힐지 정한다.

값은 셋이다. 회전, 크기, 위치.

**렌더러는 이 셋의 초기값을 정하고, 편집은 같은 셋을 사용자가 바꾼다.** 서로 다른 기능이 아니라 같은 값을 누가 정하느냐의 차이다.

| 값 | 렌더러의 초기값 |
|---|---|
| 회전 | 0도. 돌리지 않는다 |
| 크기 | 경로 전체가 여백 안에 들어오는 최대 크기 |
| 위치 | 화면 가운데 |

기본값 기준 여백은 화면 짧은 축의 8%다.

### 4-1. 회전 0도가 무슨 뜻인가

**경로를 세로 화면에 잘 들어맞게 하려고 돌리는 일을 하지 않는다는 뜻이다.**

좌표를 그대로 투영하므로 **지도와 마찬가지로 북쪽이 화면 위가 된다.** 내가 뛴 길과 그림의 방향이 일치하고, 이것이 R2("이 그림을 보고 같은 길을 다시 뛸 수 있는가")에 유리하다.

**대신 가로로 긴 경로가 문제가 된다.** 실제 러닝 코스는 좌우로 뻗은 경우가 많다. 그런 경로를 9:16 세로 화면에 넣으면 좌우로는 꽉 차는데 위아래로는 납작해진다. 이때 경로를 90도 눕히면 화면을 훨씬 크게 쓸 수 있지만, 그 자동 보정을 하지 않는다.

가로로 긴 경로는 세로 화면 가운데에 띠처럼 작게 남는다. 위아래 여백은 배경 사진이 채우고 각인이 놓이므로 화면이 비지는 않는다.

다만 경로를 크게 보고 싶은 사용자를 위해 **회전 편집이 실질적으로 필요한 옵션이 된다.** 자동으로 안 돌리는 대신 사용자가 직접 돌린다.

### 4-2. 크기와 축척은 같은 말이다

경로를 몇 배로 확대해 그리느냐다. 렌더러는 경로 전체가 여백 안에 들어오는 최대 크기로 시작하고, 사용자는 편집에서 키우거나 줄인다. 키워서 경로 일부가 화면 밖으로 나가는 것도 허용한다.

## 5. 애니메이션

> 클립이 어떻게 시작해서 어떻게 끝나는지 정한다.

### 5-1. 클립 길이는 거리와 무관하게 고정이다

5km든 20km든 같은 길이의 클립이 나온다. 긴 거리는 그만큼 빨리 그려진다.

| 구간 | 기본값 |
|---|---|
| 그리기 | 9초 |
| 완성 후 정지 | 3초 |
| 합계 | **12초** |

**15초를 넘기지 않는 것이 조건이다.** 인스타 스토리가 15초 단위로 잘리기 때문이다. 정지 구간은 보는 사람이 모양을 알아볼 시간이자 캡처가 일어나는 자리다.

사용자가 편집에서 속도를 바꾸면 클립 길이가 달라진다([결과물 편집](result-editing.md) §6-1). 배경 영상 처리가 이 길이를 기준으로 돌아간다([배경 선택](background-selection.md) §5-1).

### 5-2. 시작 상태는 프리셋마다 다르다

경로 전체가 희미하게 미리 깔리는지, 빈 화면에서 시작하는지는 프리셋 정의(§6)에 각각 적는다.

### 5-3. 끝나면 정지한다

그리기가 끝나면 완성된 경로가 화면에 남은 채로 정지 구간이 이어진다. 반복 재생하지 않는다.

### 5-4. `[확인 필요]` 진행 속도의 기준: 점 인덱스가 아니라 거리

**진행률(§6이 말하는 "경로 위 진행률")을 좌표 배열의 몇 번째 점이냐로 계산하면 안 된다.** 다듬기(§3)를 거친 트랙은 점 밀도가 구간마다 크게 다르다 — 직선은 점이 거의 사라지고, 코너는 라운딩 때문에 점이 오히려 늘어난다. 점 인덱스 기준으로 진행하면 직선에서는 순간이동하듯 끊기고 코너에서는 부자연스럽게 느려진다. **거리(호 길이) 기준으로 진행해야 다듬기 강도와 무관하게 일정한 속도로 보인다.** (JiEung2 2026-08-23, [실제 GPX 테스트 도구](../../ideation/JiEung2/2026-08-23-real-gpx-stylization-test.html)에서 발견)

**추가로 열린 질문**: 지금까지는 "실제로 뛴 페이스와 무관하게 일정 속도로만 그린다"는 전제였는데, **실제 기록된 시간 간격을 그대로 살려서(신호 대기에서 빛도 잠깐 멈칫하는 식) 보여주는 옵션을 사용자가 고를 수 있게 하면 어떤가**라는 아이디어가 나왔다. 프리셋과는 다른 축이라 프리셋 개수를 늘리지 않고 편집 옵션 하나로 얹을 수 있어 보인다. (2026-08-23, JiEung2)

| 안 | 무엇 |
|---|---|
| **일정 속도** (지금까지의 기본 전제) | 다듬기 강도와 무관하게, 경로 전체 길이를 9초에 고르게 나눠 진행 |
| **실제 템포** (새 아이디어) | 기록된 시각 간격을 그대로 반영. 페이스가 빨랐던 구간은 빛도 빠르고, 신호 대기 등으로 멈췄던 구간은 빛도 멈칫한다 |

시각 데이터는 실제 샘플에 들어 있었다. 1초 간격으로 빠짐없이 있다(§2-3). "실제 템포"는 데이터상 가능하다.

#### 두 기준이 정면으로 갈리는 자리가 있다

**신호가 끊긴 구간이다**(§3-4). 실제 샘플에 82초 공백이 있었고 그 사이 두 점이 26m 떨어져 있었다.

| 기준 | 그 구간에서 |
|---|---|
| 거리 | 26m를 순식간에 지나간다. **82초 동안 멈춰 있었다는 사실이 사라진다** |
| 실제 템포 | 빛이 82초만큼 멈칫한다. 12초 클립에서 약 0.5초 |

**거리 기준이 다듬기 문제를 푸는 것은 맞지만, 공백 구간에서는 오히려 있었던 일을 지운다.** 둘 중 하나를 고르는 문제가 아닐 수 있다. 기본은 거리로 두되 공백만 시간을 반영하는 절충도 가능하다.

§3-4와 함께 판단한다.

## 6. 프리셋

> 프리셋 하나를 구현할 때 본다.

**프리셋은 전부 하나의 렌더러다.** 차이는 경로 위 진행률을 어떻게 칠하느냐뿐이다(PRD §7). 따라서 프리셋마다 다른 것은 넷뿐이다.

| 항목 | 무엇 |
|---|---|
| 시작 상태 | 그리기 전 화면 |
| 진행 표현 | 진행률에 따라 무엇이 어떻게 변하나 |
| 마무리 | 그리기가 끝나는 순간의 연출 |
| 기본 색 | 프리셋의 정체성 색 |

MVP 기본은 셋이다. 그 위의 연출 아이디어(폭죽, 줌 추적 등)는 PRD §7의 아이디어 풀에 있으며 이 문서 범위 밖이다.

### 6-1. 기본 드로잉

앱을 처음 열었을 때의 기본값이다. 가장 단순하고 어떤 코스에서도 성립한다.

| 항목 | |
|---|---|
| 시작 상태 | 빈 화면. 배경만 있다 |
| 진행 표현 | 경로가 처음부터 선으로 그려져 나간다. 그려진 부분은 남는다 |
| 마무리 | 별도 연출 없이 완성된 선이 남는다 |
| 기본 색 | `[확인 필요]` 디자인 시스템 |

### 6-2. 불빛 러너

| 항목 | |
|---|---|
| 시작 상태 | 빈 화면 |
| 진행 표현 | 빛이 경로를 달리고, 지나온 길에 잔광이 남는다 |
| 마무리 | 끝점에 닿는 순간 경로 전체가 밝아진다 |
| 기본 색 | `[확인 필요]` 디자인 시스템 |

원안은 마무리가 "출발점에 닿는 순간"이었는데 **끝점으로 일반화했다.** 돌아오는 코스에서는 끝점이 곧 출발점이라 원래 의도가 그대로 살고, 편도 코스에서도 마무리 연출이 생긴다.

### 6-3. 구간 점등

| 항목 | |
|---|---|
| 시작 상태 | 경로 전체가 희미하게 깔린 채로 시작 |
| 진행 표현 | 구간이 하나씩 켜진다. 켜진 구간은 남는다 |
| 마무리 | 마지막 구간이 켜지면 전체가 켜진 상태 |
| 기본 색 | `[확인 필요]` 디자인 시스템 |

**구간 수는 거리에 따라 자동으로 조절한다.** km 고정이면 20km에서 20번이 되어 깜빡임처럼 보인다. 클립 길이가 고정이므로 점등 횟수가 일정해야 리듬이 산다.

점등 횟수 5~8회를 목표로 구간 단위를 자동 선택한다.

| 총 거리 | 구간 단위 | 횟수 |
|---|---|---|
| ~3km | 0.5km | 최대 6 |
| 3~8km | 1km | 3~8 |
| 8~16km | 2km | 4~8 |
| 16km~ | 5km | 4~ |

## 7. 각인

> 결과물에 새기는 기록 숫자를 다룬다.

### 7-1. 넷을 다 새긴다

| 항목 | 진행에 따른 값 | 비고 |
|---|---|---|
| 거리 | 그려진 만큼 차오른다 | 선 길이가 아니라 기록된 거리를 쓴다 |
| 시간 | 흐른다 | |
| 페이스 | 그 구간 값 | |
| 심박 | 그 시점 bpm | 데이터가 있을 때만 |

**심박이 없으면 항목 자체가 빠지고 나머지 셋이 그 자리를 채운다.** 빈 자리를 남기지 않는다. 나중에 GPX로 가져온 기록에는 심박이 없는 경우가 많으므로 예외가 아니라 흔한 경우다(§2-1).

넷 다 시간축을 가지므로 §7-3의 카운트업이 일관되게 적용된다. 표기 형식은 [공통 규칙](common-rules.md) §7을 따른다.

### 7-2. 언제 보이나

| 모드 | 동작 |
|---|---|
| **항상** (기본값) | 그리는 동안에도 계속 보인다 |
| 완성 후만 | 그릴 때는 없고 정지 구간에 올라온다 |
| 숨김 | 전혀 나오지 않는다 |

기본값을 "항상"으로 둔 것은 **러너가 공유할 때 기록을 웬만하면 함께 올리기 때문**이다. 숫자가 없으면 러닝이라는 맥락이 안 읽힐 수 있다.

> **3주차 반응 테스트에서 확인한다.** 그림만 보이는 구간이 없는 데다 항목이 넷이라 "숫자가 많아 정신없다"는 반응이 나올 수 있다. 그러면 기본값을 뒤집는다. 모드를 "완성 후만"으로 바꾸거나 항목을 줄인다.

### 7-3. 값의 움직임

"항상" 모드에서는 진행에 따라 숫자가 올라간다. 프리셋들이 이미 진행률을 따라가고 있으므로 같은 값을 숫자에 물리면 된다.

"완성 후만" 모드에서는 최종값만 나온다. 페이스와 심박은 평균값을 쓴다.

거리는 선 길이가 아니라 기록된 총 거리를 쓴다(§2). 다듬기 세기를 바꿔도 표시 거리가 흔들리면 안 되기 때문이다.

표현 방식을 사용자가 고르는 것은 로드맵이다. MVP에서는 위 동작으로 고정한다.

### 7-4. 항목별 끄기

넷 다 켜진 상태가 기본이고 사용자가 필요 없는 것을 끈다. 어떤 항목을 끌지는 편집에서 고른다([결과물 편집](result-editing.md) §7).

### 7-5. 배치

두 영역을 피한다. **인스타 스토리 UI에 가리는 상하단**과 **경로가 지나가는 영역**이다. "항상" 모드에서는 각인이 그리는 내내 화면에 떠 있으므로 경로와 겹치면 계속 거슬린다.

`[확인 필요]` 안전 영역 수치. 상단 14%, 하단 20%를 제안값으로 두고 실기기에서 인스타를 띄워 확인한다.

`[확인 필요]` 넷을 어떻게 늘어놓을지. 한 줄인지 두 줄로 묶는지, 심박이 빠졌을 때 어떻게 재배치하는지. 하단 안전 영역 위에 묶어 두는 것을 제안하고, 구체 레이아웃은 디자인 시스템에서 정한다.

## 8. 배경 합성

> 배경과 경로와 각인을 겹칠 때 본다.

아래에서 위로 쌓는다.

```
배경 (사진 또는 영상)
  ↓
경로 (프리셋 스타일)
  ↓
각인
```

배경이 영상일 때는 클립 길이(§5-1)에 맞춘다. 배경 영상이 더 짧거나 길 때의 처리는 [배경 선택](background-selection.md) §5-1이 정한다.

**배경에서 선 색을 자동 추출하지 않는다**(PRD §5 제외). 대비는 선 굵기와 외곽선·그림자로 보완한다.

`[확인 필요]` 선 굵기와 대비의 하한. 인스타에 올리면 재압축되면서 얇은 선이 뭉개질 수 있다. 3주차에 실제로 올렸다 내려받아 실측한다(PRD §12).

## 9. 출력 규격

| 항목 | 값 |
|---|---|
| 비율 | 9:16 |
| 해상도 | 1080 × 1920 |
| 프레임레이트 | 30fps |
| 포맷 | mp4 (H.264) |
| 길이 | 12초 (§5-1) |

`[확인 필요]` 용량 상한. 인스타 공유 API와 기기 저장 양쪽의 제약을 확인해야 한다.

정지 이미지 폴백은 이 문서에서 정하지 않는다. 클립 생성 경로가 검증되는 시점에 개발 담당이 판단한다(2026-08-18 결정).

## 10. 품질 판정

PRD §8을 따른다. 팀 3명 육안 합의와 외부인 반응 테스트로 판정하고, 3주차(8/26~9/1) 퀄리티 주간의 통과 조건으로 쓴다.

**기본 프리셋 셋이 먼저 이 기준을 넘어야 한다.** 연출 아이디어 시도는 그 뒤의 여유분이다.

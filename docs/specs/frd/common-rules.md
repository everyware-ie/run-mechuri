# 공통 규칙 FRD

> **status: `draft`.** 팀 확인 후 `approved`로 올린다. **approved가 아니면 구현 근거가 아니다.**
> 근거: [PRD](../prd/running-drawing-mvp.md)

## 0. 범위

**여러 화면이 함께 지키는 규칙만 담는다.** 화면 하나에만 해당하는 것은 그 화면의 FRD에 있다.

여기 있는 것을 다른 FRD가 참조한다. 같은 규칙을 여러 곳에 적으면 곧 서로 달라진다.

| 담는 것 | |
|---|---|
| 권한 | 무엇을 언제 묻고, 거부하면 어떻게 되나 |
| 빈 상태 | 보여줄 것이 없을 때 |
| 실패 | 어디서 실패하든 지키는 원칙 |
| 중단과 복귀 | 앱을 나갔다 돌아왔을 때 |
| 화면 이동 | 앞뒤로 오갈 때 무엇이 남나 |
| 대기 표시 | 오래 걸리는 일을 어떻게 보여주나 |
| 언어와 단위 | |
| 오프라인 | 네트워크 없이 어디까지 되나 |

## 1. 권한

### 1-1. 무엇이 필요한가

| 권한 | 언제 | 없으면 |
|---|---|---|
| **건강 데이터 읽기** (HealthKit) | 러닝 기록을 불러올 때 | **제품이 성립하지 않는다** |
| 카메라 | 그 자리에서 배경을 찍을 때 | 기본 이미지와 갤러리로 계속할 수 있다 |
| 사진 갤러리 읽기 | **필요 없다** | `PHPickerViewController`를 쓰는 경우([배경 선택](background-selection.md) §3-3) |

### 1-2. 필요한 순간에 묻는다

**앱을 열자마자 권한을 묻지 않는다.** 그 기능을 쓰려는 순간에 묻는다.

- 건강 데이터는 **기록을 불러오려 할 때**
- 카메라는 **찍기를 고를 때**

무엇에 쓰는지 모르는 채로 묻는 것과, 하려는 일이 눈앞에 있을 때 묻는 것은 승낙률이 다르다. PRD §6이 "무엇을 만들어주는지 먼저 보여준다"를 세운 것과 같은 이유다.

### 1-3. 건강 데이터 거부는 알 수 없다

**애플이 앱에게 알려주지 않는다.** 거부 여부를 알려주면 그 자체로 건강 정보가 새기 때문이다. 앱이 보는 것은 **"기록이 안 온다"** 뿐이고, 거부한 것인지 진짜로 기록이 없는 것인지 구분할 수 없다.

> **그래서 "권한을 거부했을 때의 화면"을 따로 설계할 수 없다.** 빈 상태 하나가 두 경우를 다 감당해야 한다(§2).

### 1-4. 권한 거부가 막다른 길이 되지 않는다

- **배경 권한**을 거부해도 기본 이미지로 결과물이 나온다
- **건강 데이터**는 대체 경로가 데이터 확보 방식에 걸린다. GPX 임포트가 들어가면 그쪽으로 갈 수 있다

`[확인 필요]` GPX 임포트를 MVP에 넣는지가 아직 안 닫혔다(PRD §11). 넣지 않으면 건강 데이터 거부는 곧 막다른 길이 되고, **그 경우 §2의 빈 상태가 유일한 대응**이 된다.

## 2. 빈 상태

### 2-1. 기록이 하나도 없을 때

**두 경우를 함께 안내하고 길을 준다.** (2026-08-23)

담을 것은 셋이다.

1. **무엇이 없는지** - 불러올 러닝 기록이 없다
2. **왜일 수 있는지** - 기록이 아직 없거나, 건강 데이터 접근이 허용되지 않았을 수 있다. **둘 다 적는다**
3. **다음에 할 수 있는 것** - 설정에서 권한을 확인하는 길과, 기록이 정말 없는 사람을 위한 길

한쪽만 앞세우지 않는 이유는 §1-3 때문이다. **권한 안내만 크게 띄우면 진짜로 기록이 없는 사람에게는 엉뚱한 말**이 되고, "기록이 없습니다"만 띄우면 거부한 사람은 왜 안 되는지 모른 채 나간다.

`[확인 필요]` "기록이 정말 없는 사람을 위한 길"이 무엇인지는 데이터 확보 방식이 닫혀야 정해진다. GPX 임포트가 있으면 그쪽이고, 없으면 "한 번 뛰고 오세요"에 가깝다.

### 2-2. 보관함이 비어 있을 때

첫 실행에는 만든 것이 없다. 이 자리는 **PRD §6의 쇼케이스**가 채운다. 홈과 보관함 FRD에서 정한다.

## 3. 실패

### 3-1. 원칙 셋

| # | 원칙 |
|---|---|
| F1 | **처음부터 다시 시키지 않는다.** 실패한 그 단계만 다시 하면 된다 |
| F2 | **사용자가 한 선택은 남는다.** 고른 기록·배경·편집값이 실패 때문에 날아가지 않는다 |
| F3 | **무엇이 안 됐는지와 다음에 할 수 있는 것을 같이 준다.** 원인만 알리고 끝내지 않는다 |

F1과 F2가 이 문서에서 가장 자주 참조될 규칙이다. 코어 루프가 네 단계인데 어느 한 곳에서 실패해 처음으로 돌아가면, 러닝 직후에 손이 덜 가는 제품이라는 성질이 무너진다.

### 3-2. 미리 걸러낼 수 있으면 미리 걸러낸다

고른 뒤에 실패를 알리지 말고, **고르는 시점에 안 되는 것은 보이지 않게 한다.** 지원하지 않는 형식을 목록에서 빼는 것이 예다([배경 선택](background-selection.md) §7).

## 4. 중단과 복귀

**하던 작업을 그대로 복구한다.** (2026-08-23)

인스타를 확인하거나 전화를 받는 일은 흔하다. 매번 처음부터면 편집을 많이 한 사람일수록 손해가 크다.

| 항목 | |
|---|---|
| 복구하는 것 | 고른 기록, 고른 배경, 편집값 전부, 보고 있던 화면 |
| 버리는 때 | **사용자가 명시적으로 그만둘 때만.** 앱이 임의로 버리지 않는다 |
| 기한 | **두지 않는다.** 오래 지났다고 버리지 않는다 |

기한을 두지 않는 이유는, 며칠 뒤에 돌아왔을 때 하던 것이 사라져 있으면 그 자체가 손해이기 때문이다. 남겨두는 비용은 값 몇 개를 기기에 두는 것뿐이다.

`[확인 필요]` 만들다 만 것을 보관함에 보이게 할지. 홈과 보관함 FRD에서 정한다. 보이게 하면 이어서 만들기가 쉬워지고, 안 보이게 하면 목록이 깔끔하다.

## 5. 화면 이동

### 5-1. 뒤로 가도 선택은 남는다

코어 루프는 네 단계다(PRD §6).

```
[러닝 기록 선택] → [배경 선택] → [편집] → [공유]
```

- **뒤로 가면 앞 단계에서 고른 것이 그대로 있다.** 배경을 바꾸려고 뒤로 갔다가 다시 와도 편집값이 살아 있다
- **배경은 편집 화면에서 바로 다시 열 수 있다**([결과물 편집](result-editing.md) §1). 뒤로 갈 필요가 없다

### 5-2. 그만두기는 물어본다

편집값이 있는 상태에서 흐름을 벗어나면 **한 번 확인한다.** 실수로 날리는 것을 막는다.

## 6. 대기 표시

**오래 걸리는 일을 보여주는 규칙은 어디서나 같다.** (2026-08-23)

| 항목 | 값 |
|---|---|
| 대기 표시를 띄우는 임계값 | **0.3초** |
| 띄웠을 때 최소 유지 시간 | **0.5초** |
| 2초를 넘기면 | **진행률과 취소로 바뀐다** (추가가 아니라 교체) |

| 실제 소요 | 보이는 것 |
|---|---|
| 0.2초 | **아무것도 안 보인다** |
| 0.4초 | 0.3초에 표시 → **0.8초까지 유지** |
| 3초 | 0.3초에 표시 → 2초에 진행률·취소로 바뀜 → 끝나면 사라진다 |

**바로 띄우지 않는 이유**는 빨리 끝나는 경우에 표시가 번쩍하고 사라지기 때문이다. 그게 아무것도 안 보여주는 것보다 나쁘다. 최소 유지 시간도 같은 이유다.

**취소를 주는 이유**는 얼마나 걸릴지 모르는 일이 있기 때문이다. 취소하면 **그 일을 시작하기 직전 상태로 돌아오고 앞선 선택은 유지된다**(F2).

이 규칙이 적용되는 곳은 배경 소재 불러오기, 결과물 만들기 같은 것들이다. 각 FRD는 이 규칙을 참조하고 다시 적지 않는다.

`[확인 필요]` 세 수치는 실제 기기에서 조정한다. 특히 2초가 적절한지는 실측이 필요하다.

## 7. 언어와 단위

**한국어와 km로 고정한다.** 기기 설정을 따르지 않는다. (2026-08-23)

타겟이 팀 3명과 그 주변인이므로(PRD §3) 지금 다국어를 할 이유가 없다. 번역 문구 관리가 빠지고 스토어 등록도 한국어만 준비하면 된다.

| 항목 | 표기 |
|---|---|
| 거리 | km. **제안** 소수 둘째 자리 (5.23km) |
| 페이스 | 분'초"/km (**제안** 5'42"/km) |
| 시간 | **제안** 1시간 미만은 mm:ss, 넘으면 h:mm:ss |
| 심박 | bpm |

**결과물에 새기는 각인도 같은 표기를 쓴다**([경로 렌더링](route-rendering.md) §7).

`[확인 필요]` 위 표기 형식. 러닝 앱들의 관례를 보고 정한다.

## 8. 오프라인

**MVP에 서버가 없다.** 기록을 읽고, 그리고, 내보내는 일이 전부 기기 안에서 끝난다.

| 네트워크가 필요한 곳 | |
|---|---|
| iCloud에만 있는 배경 소재 내려받기 | [배경 선택](background-selection.md) §6 |
| 인스타그램으로 공유 | 인스타 앱이 처리한다 |

그 외에는 **비행기 모드에서도 결과물을 만들 수 있어야 한다.** 러닝 직후에 신호가 약한 곳에 있을 수 있다.

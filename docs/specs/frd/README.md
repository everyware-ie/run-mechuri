# FRD 목록과 작성 순서

기능정의서(FRD)는 **구현의 유일한 근거**다. `status`가 `approved`가 아니면 착수하지 않는다. 훅이 PR 시점에 막는다.

> **일곱 문서 전부 `approved`다.** 2026-08-25 회의에서 확정됐다([결정](../../decisions/2026-08-25-react-native-expo-stack.md)). 구현 근거로 쓸 수 있다.

이 문서는 어떤 FRD가 있고 무엇을 담는지 안내한다. 각자 AI를 쓰며 작업할 때 "이 규칙은 어느 문서에 있나"를 먼저 확인하면 중복 작업과 어긋남을 줄일 수 있다.

상위 근거는 [PRD](../prd/running-drawing-mvp.md)와 [2026-08-18 결정](../../decisions/2026-08-18-native-ios-and-mvp-scope.md)이고, 작성 담당은 phs00이다.

## 어떻게 나눴나

**화면 단위가 아니라 관심사 단위로 나눴다.** 화면으로 자르면 세 군데서 같은 규칙을 다르게 말하게 된다.

가장 중요한 경계는 이것이다.

| | 어디에 |
|---|---|
| 렌더러가 무엇을 **할 수 있나** (프리셋이 무엇을 어떻게 그리는지) | 경로 렌더링 |
| 사용자가 무엇을 **고를 수 있나** (프리셋 선택, 크기·위치·회전, 다듬기 세기) | 결과물 편집 |

프리셋의 정의는 렌더러 쪽, 프리셋을 고르는 것은 편집 쪽이다. PRD §7의 "프리셋은 전부 하나의 렌더러이고 차이는 칠하는 방식뿐"이라는 구조를 그대로 옮긴 것이다.

## 어떤 순서로 썼나

개발이 막히지 않는 순서로 잡았다.

| 순서 | FRD | 왜 이 순서인가 |
|---|---|---|
| 1 | 경로 렌더링 | 제품의 메인이고 렌더링·내보내기 트랙에 바로 필요 |
| 2 | 배경 선택 | 화면 골격 작업에 바로 필요 |
| 3 | 공통 규칙 | 나머지가 참조한다 |
| 4 | 결과물 편집 | W4 작업 |
| 5 | 홈과 보관함 | 두 번째 실행부터 필요 |
| 6 | 내보내기·공유·저장 | W4 작업 |
| 7 | 러닝 기록 선택 | 데이터 확보 방식이 미결이라 마지막에 뒀다 |

**러닝 기록 선택을 마지막에 둔 것은 순위가 낮아서가 아니다.** 데이터 확보 방식이 안 정해져 진입 화면을 그릴 수 없었기 때문인데, HealthKit 하나로 좁혀지면서 그 막힘이 풀렸다. **GPX 임포트는 2026-08-25에 제외 확정됐다**(PRD §6).

**팀 3명 기기에 경로가 저장돼 있다는 것도 확인됐다.** 여섯 건 전부 좌표가 1초 간격으로 들어 있었다([경로 렌더링](route-rendering.md) §2-3). 남은 것은 HealthKit API로 그것이 읽히느냐이고, 앱 착수 직후에 닫힌다.

## 근거 지도

**어느 FRD가 PRD의 어느 부분을 근거로 하는지.** PRD를 고칠 때 어떤 FRD를 함께 봐야 하는지 여기서 찾는다. 각 FRD의 frontmatter `derives_from`과 `prd_sections`에도 같은 내용이 들어간다.

| FRD | 근거가 되는 PRD 부분 |
|---|---|
| 홈과 보관함 | §5 재방문 검증, §6 무엇을 만들어주는지 먼저 보여준다, §6 내보낸 다음 |
| 러닝 기록 선택 | §5 포함 1번, §6 첫 진입, §6 데이터 진입 |
| 배경 선택 | §1 한 줄 정의(배경 표), §6 배경 선택 |
| 경로 렌더링 | P1, P3, §7 결과물의 형태, §8 렌더링 품질 기준 |
| 결과물 편집 | P3, §6 코어 루프, §7 사용자가 편집할 수 있는 것 |
| 내보내기·공유·저장 | §5 포함 4번, §6 내보낸 다음, §12 인코딩 대기 |
| 공통 규칙 | §6 사용자 플로우, §9 기록 열람 정책, §12 리스크와 폴백 |

**절 번호로 참조할 때는 제목도 함께 적는다.** "§7"만 적으면 절이 하나 끼어들 때 조용히 어긋난다. "§7 결과물의 형태"라고 적으면 번호가 밀려도 찾을 수 있다.

## 무엇을 어디에 쓰나

| 내용 | 위치 |
|---|---|
| 왜 이 제품인가, 무엇을 만드는가, 범위와 우선순위 | PRD |
| 화면과 기능의 규칙, 수치, 동작 | FRD |
| 색상값, 타이포, 간격, 컴포넌트 생김새 | 디자인 시스템 |
| 코드 구조와 기술 선택 | `docs/product/features/` 구현 노트 |

**FRD는 색을 정하지 않는다.** 예를 들어 경로 렌더링 FRD는 "프리셋마다 고정 색을 갖는다"는 규칙만 정하고 실제 색값은 디자인 시스템으로 넘긴다. 반대로 디자인 시스템은 "각인이 언제 나타나는가" 같은 동작을 정하지 않는다.

## 규칙

1. **`approved`만 구현 근거다.** `draft`나 `review`는 아니다
2. FRD와 구현이 어긋나면 **FRD가 상류**다. 같은 PR에서 함께 고치는 것을 기본으로 한다
3. FRD가 PRD와 어긋나면 PRD를 고친다. 스펙이 조용히 제품 정의를 바꾸게 두지 않는다
4. 수치 중 "출발점이지 통과 기준이 아닌 것"은 그렇게 명시한다. 다듬기 세기가 대표적이다

## 누가 `approved`로 올리나

둘 중 하나다.

| 방법 | 언제 |
|---|---|
| 개발 담당자가 착수 전에 읽고 확정한다 | 그 FRD로 구현을 시작할 때 |
| 통합 회의에서 공유하고 확정한다 | 회의가 먼저 오는 경우 |

**phs00이 단독으로 올리지 않는다.** FRD는 구현의 근거이므로 구현할 사람이 읽고 동의한 상태여야 의미가 있다. 쓴 사람이 혼자 승인하면 그 절차가 형식이 된다.

**2026-08-25 회의에서 일곱 개가 한꺼번에 확정됐다.** 아래 두 번째 경로다.

**한꺼번에 올려야 하는 것은 아니다.** FRD마다 따로 `approved`가 되므로, 앞으로 새 FRD가 생기면 먼저 착수하는 것부터 확정하면 된다.

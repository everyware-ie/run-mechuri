# FRD 목록과 작성 순서

기능정의서(FRD)는 **구현의 유일한 근거**다. `status`가 `approved`가 아니면 착수하지 않는다(훅이 PR 시점에 막는다).

이 문서는 **어떤 FRD가 나올 예정이고 어떤 순서로 나오는지**를 미리 알리기 위한 것이다. 각자 AI를 쓰며 작업할 때 "이 규칙은 어느 문서에 있을 예정인가"를 먼저 확인하면 중복 작업과 어긋남을 줄일 수 있다.

- 상위 근거: [PRD](../prd/running-drawing-mvp.md) · [2026-08-18 결정](../../decisions/2026-08-18-native-ios-and-mvp-scope.md)
- 작성 담당: phs00

## 어떻게 나눴나

**화면 단위가 아니라 관심사 단위로 나눴다.** 화면으로 자르면 세 군데서 같은 규칙을 다르게 말하게 된다.

가장 중요한 경계는 이것이다.

| | 어디에 |
|---|---|
| **렌더러가 무엇을 할 수 있나** (프리셋이 무엇을 어떻게 그리는지) | 경로 렌더링 |
| **사용자가 무엇을 고를 수 있나** (프리셋 선택, 크기·위치·회전, 다듬기 세기) | 결과물 편집 |

프리셋의 **정의**는 렌더러 쪽, 프리셋을 **고르는 것**은 편집 쪽이다. PRD §7의 "프리셋은 전부 하나의 렌더러이고 차이는 칠하는 방식뿐"이라는 구조를 그대로 옮긴 것이다.

## 작성 순서

개발이 막히지 않는 순서로 잡았다.

| 순서 | FRD | 왜 이 순서인가 | 상태 |
|---|---|---|---|
| 1 | 4. 경로 렌더링 | 제품의 메인이고 렌더링·내보내기 트랙에 바로 필요 | **작성됨** |
| 2 | 3. 배경 선택 | 화면 골격 작업에 바로 필요 | **작성됨** |
| 3 | 공통 규칙 | 나머지가 참조한다 | **작성됨** |
| 4 | 5. 결과물 편집 | W4 작업 | **작성됨** |
| 5 | 1. 홈과 보관함 | 두 번째 실행부터 필요 | **작성됨** |
| 6 | 6. 내보내기·공유·저장 | W4 작업 | **작성됨** |
| 7 | **2. 러닝 기록 선택** | 데이터 진입. 마지막에 두는 이유는 아래 | 다음 |

**러닝 기록 선택을 마지막에 두는 이유**는 순위가 낮아서가 아니다. 데이터 확보 방식이 미결이었기 때문인데, **2026-08-23에 HealthKit 하나로 정해지면서 그 막힘은 풀렸다**(PRD §6). 다만 **팀 3명 기기에서 HealthKit에 경로가 실제로 저장되는지** 확인이 남아 있고, 거기서 문제가 나오면 GPX가 필수가 되어 진입 화면이 달라진다.

**모든 FRD가 `draft`다. `approved`로 올리는 주체가 아직 정해지지 않았다.** approved가 아니면 구현 PR이 훅에 막힌다.

2번이 마지막인 것은 순위가 낮아서가 아니라 **선행 미결 때문**이다. 진입 화면 설계가 HealthKit 읽기냐 GPX 임포트냐에 따라 갈린다([PRD §11](../prd/running-drawing-mvp.md)).

## 근거 지도

**어느 FRD가 PRD의 어느 부분을 근거로 하는지.** PRD를 고칠 때 어떤 FRD를 함께 봐야 하는지 여기서 찾는다. 각 FRD의 frontmatter `derives_from`·`prd_sections`에도 같은 내용이 들어간다.

| FRD | 근거가 되는 PRD 부분 |
|---|---|
| 홈과 보관함 | §5 재방문 검증, §6 무엇을 만들어주는지 먼저 보여준다, §6 내보낸 다음 |
| 러닝 기록 선택 | §6 첫 진입, §11-2 데이터 확보 |
| **배경 선택** | §1 한 줄 정의(배경 표), §6 배경 선택 |
| **경로 렌더링** | P1, P3, §7 결과물의 형태, §8 렌더링 품질 기준 |
| **결과물 편집** | P3, §6 코어 루프, §7 사용자가 편집할 수 있는 것 |
| **내보내기·공유·저장** | §5 포함 4번, §6 내보낸 다음, §12 인코딩 대기 |
| **공통 규칙** | §6 사용자 플로우, §9 기록 열람 정책, §12 리스크와 폴백 |

**절 번호로 참조할 때는 제목도 함께 적는다.** "§7"만 적으면 절이 하나 끼어들 때 조용히 어긋난다. "§7 결과물의 형태"라고 적으면 번호가 밀려도 찾을 수 있다.

## 무엇을 어디에 쓰나

| 내용 | 위치 |
|---|---|
| 왜 이 제품인가, 무엇을 만드는가, 범위와 우선순위 | PRD |
| 화면과 기능의 규칙, 수치, 동작 | **FRD** |
| 색상값, 타이포, 간격, 컴포넌트 생김새 | 디자인 시스템 |
| 코드 구조와 기술 선택 | `docs/product/features/` 구현 노트 |

**FRD는 색을 정하지 않는다.** 예를 들어 경로 렌더링 FRD는 "프리셋마다 고정 색을 갖는다"는 규칙만 정하고, 실제 색값은 디자인 시스템으로 넘긴다. 반대로 디자인 시스템은 "각인이 언제 나타나는가" 같은 동작을 정하지 않는다.

## 규칙

1. **`approved`만 구현 근거.** `draft`나 `review`는 아니다
2. FRD와 구현이 어긋나면 **FRD가 상류**다. 같은 PR에서 함께 고치는 것을 기본으로 한다
3. FRD가 PRD와 어긋나면 PRD를 고친다. 스펙이 조용히 제품 정의를 바꾸게 두지 않는다
4. 수치 중 **"출발점이지 통과 기준이 아닌 것"** 은 그렇게 명시한다. 다듬기 세기가 대표적이다

`[확인 필요]` **`approved`로 올리는 주체가 정해져 있지 않다.** phs00 단독인지 팀 3명 확인인지 정해야 한다. 8/21 전에 필요하다.

# 프레임 병렬 생성 실험

2026-09-28 · 전경 비교 완료, 후보 유지·제품 기본 적용 보류

근거: [내보내기·공유 FRD](../../specs/frd/export-and-share.md) §2-5 앱 전환·화면 잠금 중 인코딩, [경로 렌더링 FRD](../../specs/frd/route-rendering.md) §9 출력 규격. 사용자 요청은 품질을 유지하면서 효과가 클 후보부터 순서대로 적용·검증하고 성과가 작으면 중단하는 것이다.

## 선정 이유

[앞선 실측](export-preparation.md)에서 네이티브 생성 44.5~48.9초 중 프레임 그리기·복사·축소가 약 97~98%였다. 편집 중 재료 준비는 최대 약 0.2초여서 중단했다.

현재 한 장씩 수행하는 프레임 작업을 최대 두 장씩 동시에 수행하는 후보를 실험한다. 그림 계산과 내부 배율, 글꼴·색상·그림자·인코딩 설정은 그대로 두고 CPU의 동시 작업만 늘린다. 반복 계산을 없애는 방식과 달리 총 계산량은 줄지 않으므로 메모리·발열·백그라운드 경쟁이 채택 여부를 좌우한다. 속도가 두 배가 된다고 가정하지 않는다.

먼저 배경·경로·러닝 데이터별 세부 시간을 기록하는 임시 빌드를 설치했지만, 아이폰 잠금으로 실행하지 못했다. 이 세부 측정 결과는 아직 없다. 독립적으로 진행 가능한 두 프레임 비교 실험 코드와 Release 빌드까지 준비했다.

## 실험 구조

[소스 생성 스크립트](../../../frontend/scripts/export-frame-parallel-experiment.py)는 깨끗한 `RouteRendererModule.swift`를 읽어 별도 경로에 임시 모듈 소스를 만든다. 원본 경로를 출력으로 쓰거나 기존 실험 코드가 포함된 입력은 거부한다. 제품 소스에는 병렬 코드나 진입점이 남지 않는다.

- 각 작업에 독립된 renderer와 결과 슬롯을 준다. 한 renderer를 동시에 사용하지 않는다.
- 최대 두 프레임의 결과만 대기시키고, 두 작업이 끝난 뒤 원래 프레임 순서대로 writer에 넣는다.
- 완료 후 3초의 정지 프레임 재사용은 유지한다.
- 각 작업 전후 취소 여부를 확인하고, 작업들이 합류한 뒤 오류를 전달한다. writer는 기존 단일 큐에서만 다룬다.
- 성능 로그의 raster/copy는 두 작업의 누적 시간이다. 병렬 실행 시 실제 대기는 `nativeTotal`로 판단한다.
- `resident_size_peak`와 종료 시 `phys_footprint`를 기록한다. 전자는 프로세스 최대 resident 값이며 실제 최대 물리 메모리 footprint와 동일한 지표로 취급하지 않는다.

[Apple UIGraphicsRenderer 문서](https://developer.apple.com/documentation/uikit/uigraphicsrenderer)는 renderer 재사용 시 내부 컨텍스트를 재사용한다고 설명한다. 이 실험에서는 작업별로 renderer를 분리하고 작업 내부에서 재사용한다. 실제 스레드 안전성과 메모리 적합성은 실기기 비교가 필요하다.

## 재현과 채택 조건

1. 스크립트에 `--source`로 제품 모듈, `--output`으로 별도 임시 경로를 준다. 제품 모듈과 생성된 AppDelegate를 백업한다.
2. [기존 측정 진입 절차](export-preparation.md)의 방식으로 임시 소스를 넣고 `EXPORT_PREPARATION_BENCHMARK` Release 빌드를 만든 뒤 소스를 복원한다. 매크로와 임시 진입점은 배포하지 않는다.
3. 동일한 빌드에서 `--export-preparation-benchmark`만 주면 기존 직렬 방식, `--parallel-frames`를 추가하면 두 장씩 생성한다. 각 실행은 같은 합성 입력 1회를 만든다. 실행마다 결과 파일을 회수해 다음 실행에 덮어쓰이지 않게 한다.
4. 직렬·병렬을 번갈아 반복하고 전경 시간과 메모리를 비교한다. 효과가 분명하면 다른 프리셋·사진·복잡한 경로로 넓힌다.
5. 두 출력의 360프레임을 디코딩해 규격·프레임 시각·픽셀을 비교한다. 불일치는 자동 통과시키지 않는다.
6. 효과가 작거나 메모리·발열이 나빠지면 중단한다. 제품 반영 전에는 취소·연속 요청·앱 전환·잠금도 검증한다.

## 실기기 비교 결과

iPhone 11 Pro / iOS 26.6.2, 같은 Release 바이너리, 앞선 측정과 같은 1,000점 합성 경로·고해상도 합성 배경·불빛 러너·글래스·동적 숫자·한글 문구다. 미러링을 종료하고 전경에서 실행했다. 순서 영향을 줄이려고 직렬 → 병렬 → 병렬 → 직렬 순서로 각각 프로세스를 다시 실행했다. 모든 실행 전후 thermalState는 0(nominal), 저전력 모드는 꺼져 있었다.

| 실행 순서 | 방식 | 네이티브 전체 | 최대 resident | 종료 시 footprint |
|---|---|---:|---:|---:|
| 1 | 기존 직렬 | 43.2182초 | 335.5MiB | 136.6MiB |
| 2 | 두 프레임 병렬 | 29.5983초 | 492.5MiB | 144.2MiB |
| 3 | 두 프레임 병렬 | 30.6698초 | 496.0MiB | 151.0MiB |
| 4 | 기존 직렬 | 43.1496초 | 363.9MiB | 135.0MiB |

두 실행 평균 기준 직렬 43.18초 → 병렬 30.13초로 약 **30.2% 단축**했다. 각 비교 쌍의 단축률은 31.5%, 28.9%다. 기존 방식의 처음과 마지막이 비슷해 이번 비교에서 순서만으로 생긴 개선으로 보이지 않는다. 반복 2회·입력 1종의 탐색 결과이므로 전체 사용 환경으로 일반화하지 않는다.

최대 resident 평균은 349.7MiB → 494.3MiB로 약 **144.6MiB(41.4%) 증가**했다. 병렬 렌더러 두 개와 동시에 존재하는 프레임이 원인 후보이며, 실제 앱의 JS·미리보기 자원이 함께 있을 때의 여유 메모리는 아직 측정하지 않았다. 종료 시 footprint가 낮다고 순간 메모리 증가를 무시하지 않는다.

두 비교 쌍 모두 각 360프레임의 시각과 디코딩 RGB 픽셀이 완전히 동일했다(차이 프레임 0, 최대 채널 차이 0). 출력은 모두 1080×1920·30fps·12초, 내부 렌더 배율 3이다. UIKit이 만든 첫 프레임의 실제 형식은 8bit/component·32bit/pixel·sRGB였다. 고비트 형식 제거를 새 개선안으로 가정하지 않는다.

원본 로그·영상은 측정 Mac의 `/private/tmp/runary-parallel-control*`, `/private/tmp/runary-parallel-trial*`, `/private/tmp/runary-parallel-pixels*`에 있다. 임시 파일이므로 위 조건·수치와 재현 절차를 함께 남긴다.

## 판단과 다음 검증

사전 준비와 달리 속도 효과가 재현됐으므로 후보를 유지한다. 다만 메모리 사용 증가가 확인되어 일반 앱의 기본 렌더러에는 아직 적용하지 않는다. 실험용 실행 인자가 없는 일반 앱은 기존 직렬 방식이다.

다음은 실제 앱의 미리보기·JS가 함께 있는 상태에서 최대 메모리, 취소·작업 교체와 화면 잠금 동작을 검증하고, 필요하면 메모리·발열 상황에서 직렬 처리로 돌아가는 방식을 설계한다. 다른 경로 프리셋·사진·긴 경로의 품질 비교도 필요하다. 10초 목표를 달성한 단계는 아니며 더 큰 폭의 단축에는 반복 작업 감소나 GPU 합성의 별도 검토가 남는다.

## 현재 검증

- 임시 병렬 코드의 iOS Release 빌드 성공.
- 빌드 후 제품 모듈과 AppDelegate를 복원했다.
- 실기기에서 직렬 2회·병렬 2회의 전경 시간·메모리 측정을 완료했다. 두 비교 쌍 모두 각 360프레임의 픽셀 일치 검증을 통과했다.
- 앱 전환·잠금·취소·메모리 경고·다른 입력은 아직 검증하지 않았다. 측정 후 일반 앱 화면으로 다시 열었다.
- 이 합성 입력의 전경 속도 개선과 픽셀 일치가 확인된 실험이다. 제품 전체의 품질·안정성이 검증된 기능으로 취급하지 않는다. FRD·PRD의 제품 동작은 변경하지 않는다.

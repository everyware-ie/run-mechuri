# 편집 중 재료 준비와 성능 측정

근거: [내보내기·공유 FRD](../../specs/frd/export-and-share.md) §2 인코딩, [경로 렌더링 FRD](../../specs/frd/route-rendering.md) §9 출력 규격.

## 착수 확인 (2026-09-28)

사용자가 [1차 계획](../../topics/2026-09-28-export-preparation-plan.md)의 FRD 근거·범위를 확인하고 구현 착수를 승인했다. 성과가 낮으면 중단하고 다른 방안을 검토하도록 요청했다.

## 진행 원칙

배경·경로 재료 준비 시간을 먼저 전체 생성 시간과 분리해 측정한다. 첫 단계부터 앱에 캐시·수명 관리 복잡도를 추가하지 않는다. 준비 비용이 전체의 5% 미만이고 1초 미만이면 작은 대표 실험에서 중단하는 판단 기준으로 삼는다. 이 수치는 제품 성능 보장값이 아니라 이번 실험의 중단 기준이다. 조건이 다르면 일반화하지 않는다.

최종 영상 규격·렌더 배율·폰트·그림자는 유지한다. 실험 결과가 유효하면 편집 중 준비와 최신 값 확인·메모리 제한·실패 시 기존 경로를 구현하고 FRD·PRD에 함께 반영한다.

## 어긋남 기록

FRD의 실측 없음 문구와 9/13 측정 기록이 어긋나므로 이 작업에서 정리한다. 사전 준비는 측정 결과로 채택하기 전까지 활성화된 제품 기능으로 기록하지 않는다.

## 1차 반영 (2026-09-28)

`RouteRendererModule.swift`에 이미지 로드, 경로 계산, 배경 준비 시간을 분리하는 로그를 추가했다. 기존 프레임 생성·복사·writer 대기 시간과 함께 원인을 나눠 볼 수 있다. `load + route + background`를 `nativeTotal`과 비교한다. `background`는 기존 `total`에 이미 포함되므로 총 시간에 다시 더하지 않는다. 로그의 `nativeTotal`에는 JS 요청 전달과 보관함 저장은 포함되지 않는다.

실기기 측정 결과 사전 준비 비용이 중단 기준보다 작았다. 사전 준비 캐시 구현은 중단한다. 측정 로그만 유지하고 반복 프레임 작업을 다음 검토 대상으로 삼는다. 출력 해상도·프레임 수·폰트·렌더 배율과 인코딩 설정은 바꾸지 않았다.

## 재현용 실험

[측정 진입 코드](../../../frontend/scripts/export-preparation-benchmark.swift)는 제품 모듈에 등록하지 않는 로컬 실험이다. 실제 사용자 기록 대신 1,000개 합성 경로 좌표, 4032×3024 합성 JPEG 배경, 불빛 러너·글래스·동적 페이스·한글 문구로 3회 생성한다. 필수 폰트를 읽지 못하면 실험을 실패 처리한다.

로컬 재현 절차:

1. `RouteRendererModule.swift`와 생성된 `ios/app/AppDelegate.swift`를 별도 백업한다. 모듈 끝에 측정 진입 코드를 임시로 붙인다.
2. AppDelegate에 `#if EXPORT_PREPARATION_BENCHMARK`로 감싼 `internal import RouteRenderer`를 추가한다. `didFinishLaunchingWithOptions`에서 React 초기화 전에 같은 조건으로 `--export-preparation-benchmark` 실행 인자를 검사하고, 검은 UIWindow·UIViewController를 만든 뒤 `RouteRendererModule.runPreparationBenchmark()`를 호출하고 `true`를 반환한다.
3. Xcode Release 구성에 `OTHER_SWIFT_FLAGS='$(inherited) -D EXPORT_PREPARATION_BENCHMARK'`를 추가해 빌드한다. 빌드가 끝나거나 실패하면 두 소스를 즉시 복원한다. 이 매크로는 배포 빌드에 설정하지 않는다.
4. 실기기에 앱을 설치하고 위 실행 인자로 시작한다. 앱을 전경에 두고 콘솔의 `[preparation-benchmark] COMPLETE`를 기다린다. `FAILED` 또는 완료 로그 누락은 성공 측정으로 취급하지 않는다.
5. 앱 Documents의 `export-preparation-benchmark/baseline-0.mp4`부터 3개 결과물을 회수해 규격을 확인한다. 로그의 기기·OS·저전력 모드·발열 상태와 각 실행 시간을 함께 남긴다.

이 실험은 네이티브 전경 렌더링의 비용 분해용이다. UI가 실행 중인 사용 환경, 보관함 저장, 앱 전환·화면 잠금 성능을 대신하지 않는다. 채택 시에는 별도 실사용 검증이 필요하다.

## 실기기 결과와 중단 판단

2026-09-28 iPhone 11 Pro / iOS 26.6.2, Release, 전경 네이티브 단독 실행. 저전력 모드는 꺼져 있었고 세 실행 전후 thermalState는 모두 0(nominal)이었다. 각 영상은 271프레임을 그리고 360프레임을 인코딩했으며 내부 배율은 기존과 같은 3이었다. 세 번 연속 실행했고 중간 냉각 시간은 두지 않았다.

준비 비용을 전부 미리 처리하더라도 이 입력에서 줄일 수 있는 네이티브 대기는 약 0.12~0.20초다. 세 실행 모두 1초 미만·5% 미만이므로 **편집 중 배경·경로 사전 준비 캐시의 구현을 중단한다.** 이는 모든 사진·경로의 상한을 측정한 결과는 아니지만, 40초를 10초 이내로 줄이려는 현재 목적에는 이 접근의 효과가 작다. 아직 속도 개선을 달성한 결과가 아니다.

다음 후보는 매 프레임 반복되는 경로·문자 계산과 정적 레이어 그리기를 줄이는 것이다. 프레임 그리기와 복사·축소가 약 97~98%를 차지하므로 그 구간을 대상으로 한 번에 하나씩 바꾸고 동일 입력·동일 출력으로 비교한다. 개선이 작으면 GPU 합성 실험을 검토하되, 기존 화면 잠금 지원과 품질 유지 조건을 함께 다룬다. 이번 측정만으로 10초 이내를 약속하지 않는다.

원본 로그는 측정한 Mac의 `/private/tmp/runary-preparation-device.log`, 합성 영상은 `/private/tmp/runary-preparation-results/`에 있다. 임시 경로이므로 영구 증거는 위 표와 재현 절차를 사용한다. 사용자 기록·사진은 사용하지 않았다.

## 검증

- 타입 검사 통과, Jest 5개 스위트·56개 테스트 통과.
- 린트 오류 0개, 기존 경고 16개.
- 측정용 iOS Release 빌드 성공. 임시 측정 진입 코드는 제품 소스에서 제거했다.
- 문서 검사 및 diff 공백 검사 통과.
- 잠금 해제 후 실기기 설치·실행과 3회 측정을 완료했다. 측정 후 일반 실행 인자로 앱을 다시 열었다.
- 합성 결과물 3개 모두 1080×1920·30fps·12초·360프레임으로 디코딩 완료.
- 캐시를 채택하지 않아 변경 전후 화질 비교는 수행하지 않았다. 이번 네이티브 단독 측정에는 JS·보관함 저장이 포함되지 않으며 앱 전환·화면 잠금도 검증하지 않았다.

## 2차 탐색 착수 (2026-09-28)

사용자가 다음으로 효과가 클 후보부터 진행하도록 요청했다. 같은 approved FRD의 출력 규격과 품질 유지 조건 아래에서 프레임 반복 작업의 비용을 추가로 분해하고 한 후보씩 비교한다. `CLAUDE.md`의 탐색 절차로 임시 진단 코드를 사용하며, 제품 기본 경로에 채택하기 전 속도와 결과물 차이를 확인한다. 효과가 작거나 품질 조건을 만족하지 못하면 실험 변경을 제거한다.

후속: [프레임 병렬 생성 실험](export-frame-parallel.md)에서 같은 입력의 전경 시간이 평균 약 30% 줄었고 최대 메모리는 증가했다. 일반 앱 기본 적용 전 추가 검증이 남아 있다.

# 측정 화면 시안 반영

## 착수 근거

2026-11-02 사용자가 PR 128·130 머지와 지민의 화면 시안에 따른 측정 UI·UX 구현 및 미러링 확인을 요청했다. [측정 FRD](../../specs/frd/internal-run-tracking.md), [워치 FRD](../../specs/frd/watch-workout-integration.md), [측정 PRD](../../specs/prd/internal-run-tracking.md)를 근거로 한다. 시안은 [PR 130의 원본](../../ideation/jminkkk/2026-11-02-running-measurement-supplement.html)을 사용한다.

## 적용 범위

아이폰 준비 화면의 GPS·워치·건강 저장 상태를 세 행으로 정리하고 기존 연동 설정을 시트로 옮긴다. 측정 중과 상세에서는 거리를 크게, 시간·평균 페이스·심박을 왼쪽 정렬해 표시한다. 종료와 일시정지·재개는 아이콘으로 제공하고 종료 확인에 실제 요약을 표시한다. 완료한 기록은 기존 편집 흐름으로 연결한다.

워치에서는 거리와 핵심 지표·버튼을 첫 페이지에 모으고 케이던스와 상세 연결 안내는 다음 페이지에 둔다. 실제 상태·권한·신선도·저장 결과만 표시한다. 다른 운동 시작 여부를 단정하지 않으며 가상 지표와 저장 성공 체크를 만들지 않는다. 기존 수집·동기화·저장 정책은 유지한다.

## 검증

구현 후 타입·린트·관련 회귀 검사·문서 검사와 아이폰·워치 빌드를 수행한다. 실기기 확인은 기존 기록을 보존하고 별도 QA 러닝으로 시작·일시정지·재개·종료·상세·연결 시트를 확인한다. TestFlight 배포와 새 작업의 main 머지는 이번 요청 범위에 없다.


## 구현과 확인

공통 `RunDistanceSummary`와 `RunSheet`로 준비·측정·상세의 표시를 맞췄다. 기존 설정 토글을 시트로 옮기고 하단 제어는 종료·일시정지/재개 순서로 배치했다. 실제 저장된 심박을 최대 40개 시간 구간으로 집계해 상세에 표시하며 수신이 없는 구간을 채우지 않는다. 경로 검증과 화면 이탈 검사를 통과한 기록만 기존 영상 제작 흐름으로 넘긴다.

워치는 첫 페이지의 상태·거리·세 지표·제어를 고정하고 두 번째 페이지에 케이던스와 상세 연결 안내를 둔다. 권한·중단 동작은 첫 페이지에서도 접근할 수 있다. 기존 워치 세션과 전송 로직은 유지했다.

PR 128과 130은 각각 `8176280`, `ace7f0c`로 main에 머지됐다. 기존 측정 기록을 `/private/tmp/runary-ui-before-20261102`에 보존했고, 아이폰에 개발 앱을 업데이트했다. 처음 빌드와 깊은 서명 검증은 통과했다. Mac 잠금으로 미러링 확인이 막혔으며 새 앱 실행도 아이폰 잠금 상태 때문에 거절됐다. 워치 직접 설치는 기기 연결 해제로 확인하지 못했다. 최신 최종 검증과 화면 확인은 아래에 이어 기록한다.


### 최종 자동 검증과 설치

- Jest 전체 51개 묶음 379개 통과. 종료 확인 취소·중복 저장 방지, 이전 기록의 늦은 제작 요청 차단 포함.
- Swift 측정·저장소 142개, 잠금화면 36개 통과. 심박 집계의 빈 구간·잘못된 시각·최대 40구간 검증 포함.
- 건강 기록 캐시 검사, TypeScript 검사, 문서·공백 검사 통과. 린트 오류 0개와 기존 경고 30개.
- 아이폰·워치 전체 iphoneos Debug 빌드와 깊은 서명 검증 통과. 최종 앱을 아이폰에 업데이트 설치했다. PR 128·130 머지 후 main CI도 각각 통과했다.

### 아이폰 실기기 확인

사용자가 Mac 잠금을 해제한 뒤 iPhone 11 Pro 미러링에서 준비 화면과 연결 시트를 확인했다. 워치 운동 연동을 켜면 준비 화면에 ‘시작하면 심박 측정’이 표시됐고, 확인 후 원래의 꺼짐으로 복원했다. 건강 앱 자동 저장은 꺼진 상태를 유지했다.

실내 QA 러닝을 시작해 11초에서 일시정지했다. 시간이 멈춘 상태와 재개 버튼의 주황색 강조를 확인했다. 종료 시트의 실제 요약을 확인하고 돌아가기를 누르면 같은 러닝의 일시정지가 유지됐으며, 재개 시 시간이 즉시 다시 흘렀다. 이후 39초·0km로 종료·저장했다. 경로가 없는 기록은 영상 만들기가 비활성화되고 이유가 표시됐다.

기존 5.41km 기록에서 거리, 시간 38:11, 평균 심박 165bpm과 실제 심박 그래프·시간축을 확인했다. 영상 만들기를 누르면 같은 기록의 경로가 배경 선택 화면에 표시됐다. 편집 화면으로 넘어가지 않고 돌아와 저장된 편집 초안은 변경하지 않았다.

최종 기록은 44건이며 모두 완료 상태다. 설치 전 보존한 43건의 모든 파일을 최종 기기 사본과 바이트 단위로 대조해 변경이 없음을 확인했다. 새 QA 기록 한 건은 보존했다. React 검토 스킬의 비동기 응답·중복 실행·훅 정리·접근성 항목도 점검했다.

워치 직접 설치와 실물 화면 확인은 기기 연결 복구 후 진행한다. 이번 확인은 아이폰 측정 UI와 기존 기록 제작 연결에 한정하며, 야외 거리·장시간 심박·워치 자동 화면 복귀를 새로 검증한 결과는 아니다.

### 워치 개발 연결 재확인

사용자가 워치 연결 후 Runary 실행과 Mac과 같은 Wi-Fi 사용을 확인했다. CoreDevice는 워치를 `available (paired)`로 나열했지만 실제 설치·앱 조회·실행은 모두 연결 시간 초과로 실패했다. 기기 상세에는 개발자 모드 `enabled`, 개발 터널 `disconnected`가 표시됐다. Xcode의 직접 Connect와 하드웨어 ID로 재시도한 설치도 같은 결과였다.

현재 사용자 소유의 CoreDeviceService를 다시 시작했으나 워치 설치는 여전히 CoreDevice 4000·POSIX 60 오류로 끝났다. 아이폰 개발 연결과 Metro는 정상이다. 페어링 해제, 기록 삭제, 새 인증서·프로파일 생성은 하지 않았다. 워치 재시동 후 재확인을 요청했으며, 최신 워치 UI 설치와 실물 검증은 완료 처리하지 않는다.

### 워치 업데이트와 실기기 검증 완료

워치 재시동 후에도 직접 개발 연결은 실패했다. 기존 페어링 재확인도 통과했지만 터널은 연결되지 않았다. 기능 코드는 유지하고 아이폰·워치·잠금화면 타깃의 로컬 Debug 빌드 번호만 45로 맞춰 재빌드했다. 전체 빌드와 깊은 서명 검증 후 아이폰에 업데이트 설치했다. 생성 프로젝트의 버전 표기는 빌드 뒤 원래 값으로 복원했으며 새 TestFlight 제출은 하지 않았다.

처음 23초 QA 러닝에서는 워치가 아직 빌드 1로 응답했다. 이후 사용자가 워치 앱을 다시 열어 큰 원형 재생 버튼과 ‘러닝 시작’ 문구를 확인했고, 다음 러닝에서 실제 `build:45,sync:4` 응답이 기록됐다. 아이폰 동봉 앱 업데이트로 최신 워치 실행을 확인했다. Mac의 직접 개발 연결이 복구된 결과로 해석하지 않는다.

사용자는 첫 측정 화면의 거리·시간·평균 페이스·심박과 하단 네모·일시정지 아이콘이 잘리지 않고 함께 보이며 심박 숫자도 나온다고 확인했다. 아이폰에도 워치 측정 중 상태와 실제 심박 79bpm이 표시됐다. 사용자가 워치 일시정지를 누르자 아이폰의 같은 러닝이 1:47에서 멈추고 워치도 일시정지 상태로 표시됐다. 아이폰에서 재개한 뒤 워치 측정 중 상태와 심박 76bpm의 수신을 확인했다.

종료·저장된 기록은 3:01이며 실제 심박 35건, 평균 약 80bpm이 보존됐다. 실내 GPS로 기록된 52m는 거리 정확도 검증 근거로 쓰지 않는다. 이번 두 QA 기록을 더해 총 46건이 모두 완료 상태이며, 이전 44건의 모든 파일은 최종 사본과 바이트 단위로 일치했다. 테스트 후 워치 운동 연동은 원래의 꺼짐으로 복원했고 건강 자동 저장도 꺼짐을 유지했다.

워치 첫 페이지의 실물 배치와 기본 연동 동작은 확인했다. 앱 목록에 다녀온 뒤 손목을 들어 측정 화면으로 자동 복귀하는 동작, 두 번째 페이지와 워치 종료 시트의 직접 조작, 장시간 측정은 이번 검증에 포함하지 않는다. 사용자 화면 확인과 아이폰 수신 로그를 근거로 하며 Mac에서 워치 화면을 직접 캡처하지는 못했다.

### 코드 리뷰와 수정

사용자의 전체 코드 리뷰 요청에 따라 `ace7f0c` 이후 측정 UI 변경을 승인된 기능정의서와 대조했다. React 검토 스킬의 비동기 응답, 중복 실행, 훅 정리와 접근성 항목도 적용했다. 다음 세 문제를 수정했다.

- 워치 운동 권한을 확인해야 하거나 세션이 중단되면 종료·일시정지까지 사라졌다. 권한 확인·재시도는 상단 44pt 버튼으로 옮기고 하단 제어를 유지했다. 보조 버튼이 있을 때는 거리 글자 크기를 줄인다.
- 종료 확인 중 다른 러닝으로 바뀌면 이전 확인창이 새 기록에 적용될 수 있었다. 아이폰과 워치의 확인 상태를 처음 연 기록 ID에 묶었다. 아이폰은 최신 상태를 다시 읽으며, 새 네이티브 `finishRun(id)`도 메인 큐에서 ID를 확인한 뒤 종료한다. 워치는 다른 ID나 이미 완료된 상태의 확인 요청을 거절한다. 이전 개발 클라이언트는 상태 재확인 후 기존 API를 사용하는 호환 경로를 유지한다.
- 오래된 미완료 기록이나 긴 일시정지는 심박 집계 시각과 상세 시간축이 달라졌다. 집계 종료 시각을 같은 요약의 시작 시각과 경과 시간으로 계산해, 일시정지 뒤 오래 기다려도 심박 구간이 한 칸으로 뭉치지 않게 했다.

이전 확인창의 늦은 요청, 폴링 전 기록 교체, 중복 종료와 ID가 묶인 API 호출을 회귀 검사에 추가했다. Swift에서는 같은 기록의 오프라인 종료, ID 교체·완료 후 제어 차단과 오래된 일시정지 기록의 심박 구간을 확인했다. Jest 전체 381개, Swift 측정·저장소 148개와 잠금화면 36개가 통과했다. 타입 검사도 통과했고 린트는 오류 0개와 기존 경고 30개다.

아이폰·워치·잠금화면 전체 Debug 빌드와 깊은 서명 검증 후 로컬 개발 앱 `1.0.0(46)`을 아이폰에 업데이트했다. 기존 46건의 기록 파일은 설치 전후로 일치했다. 실기기에서 0:07로 표시된 QA 러닝(실제 약 7.7초)의 일시정지·종료 취소·재확인 후 저장을 확인했다. 최종 47건은 모두 완료 상태이며, 이전 46건의 모든 파일은 변경되지 않았다. 워치 권한 오류 상태의 새 상단 버튼 배치는 실기기로 확인하지 않았다. 새 TestFlight 제출이나 main 머지는 수행하지 않았다.

### 자동 복귀와 재시작 실기기 확인

사용자는 별도 QA 러닝 중 손목을 내렸다 든 경우와 앱 목록으로 나갔다가 손목을 내렸다 든 경우 모두 측정 화면으로 자동 복귀한다고 확인했다. 당시 아이폰은 46번, 실제 응답한 워치는 45번이었다. 이 결과를 워치 46번의 검증으로 합치지 않는다.

워치 앱을 완전히 종료하고 다시 연 뒤 새 러닝에서는 심박과 운동 세션이 시작되지 않았다. 전체 로그를 대조하니 워치 45번 응답과 앱 실행 요청의 성공 응답이 남아 있었다. 초기 조사에서 요청 누락으로 단정했던 설명을 정정한다. 워치 운동 생성 조건이 전면 상태만 허용해, HealthKit이 백그라운드로 깨운 경우 세션을 시작하지 못하는 경로를 확인했다. [Apple의 운동 시작 콜백 설명](https://developer.apple.com/documentation/watchkit/wkapplicationdelegate/handle%28_%3A%29-1pfoc)은 이 콜백에서 운동 세션을 구성하도록 안내한다.

HealthKit 콜백 뒤 새로 요청한 실시간 아이폰 응답에만 일회성 허가를 붙였다. 10초 안의 실행 중 기록과 워치 연동 켜짐을 확인한 경우 해당 ID의 세션을 백그라운드에서 시작할 수 있다. 캐시, 지연·이전 응답, 다른 상태와 꺼진 설정은 허가하지 않는다. 동시에 아이폰의 `isReachable`만으로 실행 요청을 생략하는 조건도 제거했다. 이는 메시지 통신 가능 여부이며 전면 표시나 운동 실행을 보장하지 않는다. [Apple의 reachable 설명](https://developer.apple.com/documentation/watchconnectivity/wcsession/isreachable), [워치 운동 앱 실행 API](https://developer.apple.com/documentation/healthkit/hkhealthstore/startwatchapp%28with%3Acompletion%3A%29)를 근거로 한다.

실행 요청은 기존처럼 사용자가 명시적으로 시작·재개한 경우에만 보낸다. 주기적인 동기화에서 반복 실행하지 않고, 요청 성공을 운동 세션 실행 성공으로 표시하지도 않는다. 실제 세션 응답과 심박 수신으로 재검증한다.

### 로컬 47번의 시작과 자동 복귀 재검증

새 허가의 재사용·이전 요청·만료·오래된 상태·연동 꺼짐·완료 상태를 회귀 검사에 추가했다. Swift 측정·저장소 156개와 잠금화면 36개, 타입 검사와 문서 검사를 통과했다. 린트는 오류 0개와 기존 경고 30개다. 전체 Debug 빌드와 깊은 서명 검증 후 아이폰에 47번을 업데이트했다. 생성 프로젝트의 버전은 빌드 후 복원했고 EAS의 제출 번호는 변경하지 않았다.

아이폰 Watch 앱에서 Runary의 설치 상태를 확인한 뒤 별도 QA 러닝을 시작했다. 실제 워치가 `build:47,sync:4,launchHandled:true`로 응답했고 약 9초 시점의 기록에 심박 수신이 남았다. 아이폰 화면에서도 심박 갱신을 확인했다. 사용자는 최신 워치에서도 앱 목록으로 나갔다가 손목을 내리고 들면 Runary를 누르지 않아도 측정 화면으로 자동 복귀한다고 확인했다.

Mac의 워치 직접 개발 연결을 복구한 것은 아니다. 아이폰의 동봉 앱 업데이트와 실제 응답 버전으로 확인했다. 권한 거부·다른 운동 충돌 상태의 상단 버튼 배치는 이번 정상 세션 결과로 대신하지 않는다.

같은 QA 러닝에서 아이폰 앱 프로세스만 40초간 중단했다가 자동으로 복구했다. 복구 후 같은 기록 ID의 새 심박 14건이 수신됐고 사용자는 정상 측정 화면이라고 확인했다. Bluetooth나 Wi-Fi를 실제로 끊은 검사는 아니다. 지연 중의 안내와 하단 제어 배치는 확인 시점을 맞추지 못해 실물 검증 완료로 처리하지 않는다. 이 기록은 3:37, 심박 42건으로 종료·저장했다.

종료 후 새 러닝에서는 `requested:reachable`과 성공 응답을 확인했고 실제 새 심박 8건을 받아 48초 기록으로 저장했다. 처음 시작과 이미 통신 가능한 워치에 대한 재시작을 모두 확인했다. 최종 51건은 모두 완료 상태이며 시작 전 47건의 모든 파일을 최종 기기 사본과 바이트 단위로 대조해 변경이 없음을 확인했다. QA 사본은 `/private/tmp/runary-watch47-final-20261102`에 보존했다.

워치 운동 연동은 테스트 전의 꺼짐으로 복원했고 건강 자동 저장도 꺼짐을 유지했다. 권한 거부·다른 운동 충돌 화면과 지연 중의 버튼 배치, 실제 무선 단절은 남은 확인이다. TestFlight 제출과 main 머지는 하지 않았다.

### 예외 상황 QA와 종료 요청 보존

사용자가 남은 예외 상황 QA를 승인했다. 워치 FRD의 연결 끊김과 충돌, 같은 러닝의 종료 요청 재전송을 기준으로 실제 `WatchRun`과 `WatchWorkoutSession` 제어 코드를 헤드리스 검사에 넣었다. 검사 도구는 SwiftUI 앱 진입부와 뷰를 제외하고 원본 제어 코드 본문을 그대로 컴파일한다. Apple API·시계·기기 저장소만 테스트 대역으로 교체하며 사용자 권한과 센서에는 접근하지 않는다. 이 결과를 실제 HealthKit 동작이나 실물 화면 검증으로 대신하지 않는다.

최초 24개 검사 중 4개가 실패했다. 연결이 끊긴 상태에서 종료를 반복하면 요청 시각이 바뀌었고, 아이폰 상태를 받으면 ‘종료 요청 전달 중’ 설명이 지워졌다. 다른 러닝이 도착한 뒤 종료하면 보관한 요청의 ID도 덮어쓸 수 있었다. 마지막 실패는 이 덮어쓰기로 인해 다른 ID의 확인 응답이 현재 요청을 해제한 결과였다.

최초 종료 요청을 해당 ID의 확인 응답이 올 때까지 유지하도록 수정했다. 중복 입력은 같은 요청을 재전송하며 새 시각이나 ID를 넣지 않는다. 종료 대기를 관찰 가능한 상태로 노출해 측정 화면과 첫 화면에 안내를 유지하고, 재개·새 시작과 워치 운동 재시작은 대기 중에 제공하지 않는다. 통신 가능 상태로 바뀌면 보관한 종료 요청도 다시 전달한다.

확장한 33개 검사가 통과했다. 운동 권한 거부 후 자동 권한 요청 없음, 31초 지연 후 일시정지, 재연결 후 같은 세션 재개, 2분 이후 종료, 캐시의 백그라운드 재생성 차단, 명시적 실행 요청 후 복원, 외부 세션 종료·생성 오류 후 자동 재시작 방지와 늦은 콜백 차단을 포함한다. 종료 요청은 재실행 후에도 원래 ID·시각을 유지하며 해당 요청의 응답으로만 해제되는지 확인했다. 권한 거부와 세션 중단 상태에서도 같은 아이폰 러닝을 제어·종료할 수 있는지 확인했다.

명령은 `sh scripts/check-watch-exceptions.sh`다. Swift 측정·저장소와 잠금화면 192개, 관련 Jest 17개, 타입 검사도 통과했다. 린트 오류는 없고 기존 경고는 30개다. 전체 Debug 빌드와 세 타깃 48번 확인 및 깊은 서명 검증을 완료했다. 실기기 결과는 아래에 별도로 기록한다.

첫 실기기 QA에서 실제 워치 48번과 새 심박을 확인한 뒤 아이폰 앱 응답을 최대 90초 멈췄다. 사용자는 연결 안내·종료 버튼과 ‘종료 요청 전달 중’을 확인했고, 복구 뒤 워치는 러닝 시작 화면으로 돌아왔다. 기록은 2:41, 심박 32건으로 한 건만 저장됐다. 다만 종료 요청 시각이 응답 복구 직후라서 완전한 오프라인 종료 전달의 통과 근거로 쓰지 않는다. 입력과 복구의 순서를 확실히 나누어 재검증한다.

두 번째 QA는 사용자가 종료 대기를 확인한 뒤에만 아이폰을 복구했다. 실제 앱 응답 중단은 39.36초였고 종료 입력 시각은 복구 9.07초 전이었다. 아이폰에는 같은 러닝이 1:17, 심박 15건으로 저장됐다. `watchStop`은 한 건이며 기록 시간은 시작부터 최초 종료 요청까지의 시간과 일치했다. 종료 이후 시각의 심박과 중복 심박 식별자는 없었다. 실제 무선 연결 해제 대신 아이폰 앱 응답 중단을 사용한 결과다.

최종 사본은 `/private/tmp/runary-watch48-exceptions-final`에 보존했다. 53건이 모두 완료 상태이고 이번 QA 전 51건의 모든 기록 파일은 변경되지 않았다. 워치 운동 연동은 기존 꺼짐으로 복원했으며 건강 자동 저장도 꺼짐을 유지했다. 권한 거부·다른 운동 중단은 제어 코드 검사 통과이며, 실제 OS 권한 철회나 다른 운동 앱과의 충돌 및 해당 화면 배치는 실물 검증으로 처리하지 않는다. TestFlight 제출과 main 머지는 하지 않았다.

# 두 프레임 병렬 생성의 제품 적용

- 근거: [9/29 결정](../../decisions/2026-09-29-export-parallel-rendering.md), [내보내기·공유 FRD](../../specs/frd/export-and-share.md) §2 인코딩·§2-5 앱 전환·화면 잠금 중 인코딩, [경로 렌더링 FRD](../../specs/frd/route-rendering.md) §9 출력 규격.
- 착수: 2026-10-03. 사용자가 최근 회의 결과에 맞춰 성능 개선부터 진행하도록 요청했다. 앞서 확인받은 출력 규격·품질 유지 정책과 9/29 채택 결정을 적용한다.
- 상태: PR #75에서 사진 병렬 적용을 main에 반영했다. 이후 사용자가 측정된 영상 압축 픽셀 차이를 기록하고 적용하도록 요청해 영상 배경에도 병렬 생성을 확장한다. 차이·검증 한계는 아래에 보존한다. 2026-10-04 사용자의 후속 배포 요청에 따라 [빌드 27](../../ops/build-and-dev-commands.md#2026-10-04-스토리형-편집-1단계-배포-10027)에 함께 포함한다.
- 반영 범위: 2026-10-03 사용자의 후속 요청에 따라 PR #75를 main에 머지했고, 영상 병렬 확장은 별도 PR로 반영한다. TestFlight 배포는 다른 변경과 모아 다음에 진행하며 이번 작업에서는 TestFlight용 빌드·제출하지 않는다. 9/29 회의의 기술 채택 결정은 유지한다.

## 구현 범위

사진·기본 이미지·영상 배경은 두 프레임을 묶어 그린 뒤 순서대로 writer에 넣는다. 동시에 진행하는 프레임은 최대 둘이며 작업별 renderer를 분리한다. 배율·폰트·색·경로 계산·인코더 설정은 바꾸지 않는다. 정지 배경의 마지막 3초 완성 프레임 재사용을 유지한다.

영상 배경은 reader가 기존 렌더 큐에서 시간순으로 최대 두 장면을 읽고, 그리기만 작업별 renderer로 병렬 처리한다. writer 입력도 같은 큐에서 시간순으로 유지한다. 마지막 3초에도 움직이므로 완성 프레임을 재사용하지 않는다. 빠른 병렬 입력의 압축 픽셀 차이는 사용자 요청에 따라 기록하고 적용한다.

메모리 압박 알림, 심각한 발열, 현재 프로세스 메모리 여유가 256MiB 미만인 경우 남은 프레임은 하나씩 만든다. 둘째 renderer를 해제하며 같은 작업에서 다시 병렬로 올라가지 않는다. 256MiB는 실험의 추가 resident 약 145MiB보다 여유를 둔 초기 방어 기준이며 종료 방지 보장값이 아니다. 취소는 각 작업 전후와 writer 대기·append 직전에 확인한다. 작업 합류 후 오류를 전달하고 미완성 파일을 정리한다.

참고: [Apple 메모리 압박 알림](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure). `os_proc_available_memory()`의 SDK 원문(`os/proc.h`)은 현재 앱의 메모리 한도까지 남은 순간값이며 기기 총 여유 메모리가 아니라고 설명한다. 다른 작업으로 즉시 바뀔 수 있으므로 배치마다 다시 확인한다.

## 검증과 남은 항목

아래 표는 최신 코드의 실기기 비교다. 검증이 진행되는 항목은 결과가 나온 뒤 추가한다. 9/28의 약 30% 단축은 구버전 합성 입력 실험이며 최신 영상 배경 포함 앱의 성능 보장값으로 쓰지 않는다. 전경·앱 전환·잠금·취소·메모리·서로 다른 입력을 확인하고 조건과 미확인 항목을 기록한다.

## 정합성

회의 결정의 두 프레임 병렬 생성을 적용하며 FRD의 출력·백그라운드·완성 등록 기준을 바꾸지 않는다. 품질을 낮추거나 GPU 변환·정적 캐시를 결합하지 않는다.

## 검증 재현

[제품 비교 소스 생성기](../../../frontend/scripts/export-parallel-product-benchmark.py)는 현재 모듈을 읽어 별도 임시 소스와 측정 진입점을 만든다. `--export-preparation-benchmark`로 병렬, `--serial-frames`를 더하면 같은 출력 알고리즘의 직렬 비교다. `--fallback-test`는 네 번 병렬 배치 후 직렬 전환을 강제하며 `--cancel-test`는 2초 후 취소와 임시 파일 삭제를 검사한다. 이 테스트 인자는 제품 소스에 넣지 않는다.

`--preset=<프리셋>`·`--layout=<러닝 데이터 프리셋>`으로 입력을 바꾸고 `--video-test`는 Documents/export-preparation-benchmark/synthetic-video.mp4를 읽는다. `--with-lease`는 기존 시스템 백그라운드 실행 권한을 사용하고 영상 회수용 파일 복사 후 완료 ACK를 보낸다. 실제 JS 보관함 저장 검증과 구분한다. `--with-ui`를 AppDelegate에서 처리하면 React 시작 화면과 함께 12초 후 같은 네이티브 비교를 시작한다. 이는 UI/JS 공존 메모리 확인이며 공유 버튼부터 보관함 등록까지의 전체 검증은 아니다.

배포에 포함하지 않는 AppDelegate 진입·매크로는 [기존 측정 절차](export-preparation.md)에 따라 임시로 추가하고 빌드 후 복원한다. 결과는 같은 폴더의 baseline-0.mp4와 콘솔 로그이며, 다음 실행 전에 반드시 복사해 보존한다.

## 2026-10-03 실기기 결과

iPhone 11 Pro / iOS 26.6.2, 동일 Release 비교 빌드. 전경 네이티브 단독으로 기존 합성 입력을 사용했다. 내부 배율 3·1080×1920·30fps·12초·360프레임을 유지했다. 아래는 각 1회 비교이며 전체 기기의 성능 보장값은 아니다.

| 입력·처리 | nativeTotal | 최대 resident | 종료 footprint | 출력 |
|---|---:|---:|---:|---|
| 불빛 러너·글래스 직렬 | 44.9283초 | 362.8MiB | 145.0MiB | 기준선 |
| 같은 입력 병렬 | 29.7666초 | 535.3MiB | 151.7MiB | 360프레임 시각·픽셀 동일 |
| 4배치 후 직렬 전환 강제 | 43.0088초 | 496.1MiB | 144.8MiB | 360프레임 시각·픽셀 동일 |

첫 비교는 약 33.7% 단축, 최대 resident 약 172.5MiB 증가다. resident 최대와 실제 최대 물리 footprint를 같은 지표로 취급하지 않는다. raster/copy 로그는 worker별 시간 합계이므로 병렬 실행에서는 nativeTotal보다 클 수 있다. 실제 대기 단축은 nativeTotal로 판단한다.

직렬 전환은 메모리를 강제로 소비하지 않고 같은 전환 함수를 테스트 인자로 호출했다. 병렬 4배치·직렬 263배치로 끝났고 271프레임 생성·360프레임 인코딩을 유지했다. 실제 압박 알림 발생이나 모든 메모리 부족 상황의 복구까지 검증했다는 뜻은 아니다.

2초 후 취소 테스트는 약 2.15초 시점에 취소가 전달되어 미완성 파일 삭제 확인을 통과했다. 그 뒤 다른 생성 요청도 정상 완료했다. 테스트는 작업의 취소 경로이며 사용자가 취소 버튼을 누르는 UI 자체를 새로 검증한 것은 아니다.

같은 기기의 전경 측정이다. 아래 실행은 모두 thermalState 0 → 0, 저전력 모드 꺼짐이다. UI 공존은 React 시작 화면과 JS가 살아 있는 상태이며 실제 편집 화면의 전체 생성·보관함 저장 검증은 아니다.

UI 직렬과 병렬 메모리 수치는 각각 열 누적·냉각 상태에서 나온 별도 실행이다. resident는 해당 프로세스의 최대값이며 편집 UI의 최대 메모리나 기기 전체 한도를 뜻하지 않는다. UI 병렬 종료 footprint는 573.3MiB였다. 메모리 부족 자동 직렬 전환은 실제 모든 종료 상황을 막는 보장이 아니다.

### PR #75에서 영상 병렬을 제외했던 이유

빠른 병렬 영상의 규격·프레임 시각은 같았으나 디코딩 RGB는 355프레임에서 차이가 났다. 채널 최대 차이 87/255, 평균 절대 차이 0.0579657/255였다. 최신 소스로 재빌드하고 진단 옵션을 끈 정상 속도에서 다시 실행해도 같은 차이가 났다(nativeTotal 54.1950초). 속도 성과만으로 품질 일치 판정을 통과시키지 않았다.

인코딩 전 RGB를 SHA-256으로 비교한 진단 실행에서는 직렬 2회와 병렬 1회의 360프레임이 모두 같았다. 그 진단 실행의 최종 mp4 픽셀도 모두 같았다. 다만 해시 계산이 입력 간격을 바꾸므로 이를 빠른 정상 경로의 최종 픽셀 일치로 대신하지 않는다. 두 프레임 연속 writer 입력과 압축 결과의 관계는 추가 분석 대상이며, 원인을 확정했다고 기록하지 않는다.

PR #75에서는 영상 배경이면 한 프레임씩 처리했다. 사진·기본 이미지의 병렬 성과를 먼저 반영했으며, 이후 사용자의 후속 요청으로 영상 직렬 제한을 해제한다. 출력·백그라운드 정책과 인코더 설정은 유지한다.

재현 도구의 `--raw-frame-hashes`는 인코딩 전 RGB만 비교하고 미사용 alpha·행 padding을 제외한다. `--keep-awake`는 측정 사이 자동 잠금을 막는 임시 측정 옵션이다. 둘 다 생성된 임시 소스에만 있으며 제품 앱에는 들어가지 않는다. 해시 계산 시간을 포함한 실행은 속도 비교에서 제외한다.

추가 증거: `/private/tmp/runary-product-{control-line,trial-line,ui-glass-cool,hash-video-control,hash-video-repeat,hash-video-parallel,video-final-fast}*`, `/private/tmp/runary-product-hash-check.log`. 영상 직렬 제한 후 최종 검증 결과는 아래에 기록한다. 일반 앱 소스로 다시 iOS Release 빌드 성공했고 타입 검사·린트도 재확인했다(오류 0개·기존 경고 21개).


### PR #75의 영상 직렬 제한 코드 검증

영상 직렬 제한을 포함한 같은 소스의 Release 비교 빌드에서 사진·영상 모두 생성 완료와 기준선 대비 360프레임 시각·픽셀 일치를 확인했다.

| 입력 | nativeTotal | 병렬·직렬 배치 | 최대 resident | 종료 footprint | 출력 |
|---|---:|---|---:|---:|---|
| 불빛 러너·글래스 사진 | 33.3941초 | 135·1 | 486.8MiB | 143.1MiB | 직렬 사진 기준선과 동일 |

진단 코드가 없는 최종 일반 Release 빌드도 성공했다. 2026-10-03 아이폰에 일반 앱을 재설치하고 실행했다. 측정용 AppDelegate 진입점·CLI 제어·프레임 해시가 제품 소스에 남지 않은 것을 확인했다. TestFlight용 빌드·제출은 하지 않았다.


## 2026-10-03 후속 요청: 압축 픽셀 차이를 기록하고 영상 병렬 적용

사용자는 PR #75 머지 후 “작은 압축 픽셀 작은 차이라면 일단 적용하고 그 사실을 남기는 걸로 할게요”라고 요청했다. [9/29 결정의 후속 보완](../../decisions/2026-09-29-export-parallel-rendering.md), PRD와 FRD에 이 범위를 반영하고 영상 배경의 직렬 전용 조건을 해제한다.

수용한 것은 이번 합성 영상 비교에서 확인한 압축 픽셀 차이다. 출력은 1080×1920·30fps·12초·360프레임을 유지하고, 프레임 시각과 인코더 설정도 유지한다. 저해상도 전환이나 품질 설정 하향은 하지 않는다. 이후 다른 입력에서 생기는 큰 손상까지 자동으로 허용한다는 뜻은 아니다.

- 기존 정상 속도 비교: 직렬 87.4570초 → 병렬 55.3308초(약 36.7% 단축), 병렬 재실행 54.1950초.
- 차이: 디코딩 RGB 355/360프레임에서 차이, 전체 RGB 채널 평균 절대 차이 0.0579657/255, 국소 최대 차이 87/255. 평균이 작더라도 일부 픽셀의 차이가 같은 수준이라는 뜻은 아니다.
- 해시 진단: 직렬 2회와 병렬 1회의 인코딩 전 RGB는 360프레임 전체가 같았다. 해시 계산으로 입력 간격이 달라지는 조건이므로 정상 속도 출력의 픽셀 일치를 보장하지 않는다.
- 원인과 육안 영향: 두 프레임 연속 입력과 압축 결과의 관계는 추가 분석 대상이다. 육안으로 항상 구별되지 않거나 품질이 항상 같다고 확정하지 않는다. 실제 입력·기기·편집·잠금 상태 QA와 함께 다음 배포 전에 확인한다.

메모리 압박·메모리 여유 256MiB 미만·심각한 발열에서 남은 작업을 직렬로 전환하는 기존 방어는 영상에도 적용한다. 이번 정상 경로는 앞서 여러 번 측정한 병렬 경로와 같으므로 기존 시간·픽셀·해시·취소·전환 증거를 재사용하고 불필요하게 같은 측정을 반복하지 않는다. 최신 일반 Release 빌드와 저장소 검사를 수행하고 별도 PR로 머지한다. TestFlight 배포는 계속 보류한다.

최신 일반 iOS Release 빌드, 타입 검사, 린트(오류 0개·기존 경고 21개), 문서 정합성 검사를 통과했다. 별도 실기기 재측정 없이 앞서 확인한 정상 속도 영상 병렬 결과와 해시 진단을 근거로 사용한다.

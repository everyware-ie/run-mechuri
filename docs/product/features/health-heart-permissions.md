# 건강 앱 심박 불러오기와 권한 반복 요청 수정

## 근거와 착수 확인

- [내부 측정 FRD](../../specs/frd/internal-run-tracking.md) §2 권한과 시작, §3-1 지표 계산 추천안, §8-1 건강 앱 심박 불러오기
- [공통 규칙 FRD](../../specs/frd/common-rules.md) §1 권한, §2-1 기록이 하나도 없을 때
- [기록 선택 FRD](../../specs/frd/run-record-selection.md) §3 권한
- [결정](../../decisions/2026-10-06-second-sprint-app-store.md) §5 측정 기능의 기준과 2026-10-07 구현 범위 보완

2026-10-07 사용자가 위 근거와 수정 범위를 확인하고 문서 정리부터 구현까지 진행하도록 승인했다. 건강 앱 불러오기를 기본으로 제공하고 워치 직접 측정은 별도 선택으로 유지한다. 권한 요청 필요 여부 확인·설정 복귀 재조회, 측정 중 수신·종료 후 지연 심박 병합을 함께 구현한다.

## 구현 방향

아이폰 GPS 수집과 심박 읽기를 분리한다. 심박 샘플의 측정·수신 시각과 출처를 보관하고 기존 유효 구간·중복·신선도 계산을 사용한다. 상세 재조회는 과거 통계만 갱신하고 종료 시각·경로를 바꾸지 않는다. 삭제된 기록과 이전 쿼리의 늦은 응답은 무시한다. 이미 응답한 권한을 허용으로 단정하거나 빈 결과를 권한 거부로 표시하지 않는다.

## 어긋남 기록

선택 실험으로 남아 있던 FRD와 PRD를 10/7 결정·사용자 승인에 맞췄다. 직접 측정은 유지하며 건강 앱 읽기와 동시에 합산하지 않는다.

## 검증

구현 후 자동 검사 결과와 실기기에서 확인할 권한 창·워치 동기화·잠금 수신을 구분해 기록한다.

## 구현 경로와 확인한 동작

- `TrackingManager.swift`: 건강 앱 심박의 네이티브 관찰, 전면 복귀 재조회, 기록별 재조회 요청 합치기, 늦은 응답의 저장 시점 재확인. 심박 요청과 GPS를 분리하고 첫 건강·동작 권한 창의 경쟁을 줄이도록 순서를 나눴다.
- `TrackingEngine.swift`: 심박 방식과 출처를 로그에 보관한다. 기존 기록의 방식은 워치 사용 값으로 복원한다. 유효 측정 구간과 UUID 중복 제거를 사용하며 명시적인 건강 데이터 삭제 통지를 처리한다. 빈 조회 결과로 기존 데이터를 삭제하지 않는다.
- `HealthKitBridgeModule.swift`, `RunaryWatchApp.swift`: OS의 권한 요청 필요 여부를 확인한다. 아이폰의 동시 기록 권한 요청은 같은 작업을 기다린다. 읽기 허용 상태로 해석하지 않는다.
- `record-selection.tsx`: 설정 복귀는 데이터만 재조회한다. 권한 시트에 따른 앱 상태 변경도 중복 요청 없이 처리하며 늦은 조회를 화면에 반영하지 않는다.
- `internal-run.tsx`, `internal-run/[id].tsx`: 심박 방식 선택, 대기·지연·확인 실패, 종료 후 다시 불러오기를 제공한다. 조회 실패에도 GPS 기록을 표시하며 건강 데이터 재조회는 작성 중 메모를 덮지 않는다. 이전 개발 앱에는 새 빌드 필요 안내를 표시한다.

## 검증 결과

2026-10-07 자동 검사에서 Jest 40개 묶음·306개, Swift 합성 계산·저장 검사 51개, TypeScript, 공개/내부 빌드 설정, 문서 검사와 diff 공백 검사를 통과했다. ESLint는 오류 0개·기존 경고 30개다. 아이폰·워치 동봉 무서명 Debug 빌드도 통과했다.

심박의 늦은 수신·중복·일시정지/종료 밖/미래 시각 제외, 삭제 통지 후 평균·최대값 재계산, 로그 재실행에서의 출처·종료 시각 보존을 합성 자료로 검증했다. 화면 검사는 설정 복귀·권한 시트 생명주기의 요청 반복 방지, 심박 실패 후 기존 기록 보존·재시도, 이전 기록의 늦은 응답 차단, 건강 앱 기본 선택과 심박 사용 안 함을 확인했다.

실제 권한 창이 반복되는 원인은 코드 호출만으로 확정하지 않았다. 기존 코드가 매번 권한 요청을 호출한 것을 확인했고 요청 필요 여부 확인과 동시 요청 제어를 보완했다. 실제 iOS 권한 창 횟수, 최초 건강·동작 권한 흐름, 권한 철회·설정 복귀, 다른 운동 앱과 병행한 심박의 측정/수신 시각·잠금 중 수신·종료 후 동기화, 워치 직접 측정 재확인은 [내부 QA](../../ops/internal-run-tracking-qa.md)에서 이어간다. 최초 구현 검증에서는 실기기 설치·TestFlight 제출을 수행하지 않았다. 이후 개발 설치 결과는 아래에 구분한다.

## 기술 근거

- [Apple 권한 요청 상태](https://developer.apple.com/documentation/healthkit/hkauthorizationrequeststatus): `unnecessary`는 요청에 응답했다는 의미이며 읽기 허용 여부가 아니다.
- [Apple 권한 요청](https://developer.apple.com/documentation/healthkit/hkhealthstore/requestauthorization(toshare:read:)): 이미 응답한 같은 항목은 권한 창 없이 돌아온다. 워치의 권한 창은 워치에서 제공한다.
- [Apple anchored query](https://developer.apple.com/documentation/healthkit/hkanchoredobjectquery): 건강 데이터 저장소의 추가·삭제와 업데이트를 관찰한다. 워치의 심박 동기화 주기는 앱이 보장하지 않는다.

## 개발 서버·미러링과 코드 리뷰 (2026-10-07)

사용자가 개발 서버 실행·미러링 확인 준비와 코드 리뷰를 요청했다. 내부 측정 플래그를 켜고 Expo 개발 서버를 LAN 8081에서 실행했다. 서버의 `packager-status:running` 응답과 iOS 번들 완료를 확인했다.

아이폰에 설치돼 있던 TestFlight 34를 기존 개발 프로파일로 서명한 개발 앱 1.0.0(1)로 업데이트 설치했다. 앱 삭제는 하지 않았다. 워치 개발용 프로파일이 없어 동봉 개발 빌드 서명은 실패했다. 워치 동봉 무서명 빌드를 임시 복사하고 그 사본의 워치만 제외해 아이폰 확인용으로 서명했다. 원본 빌드와 저장소의 워치 타깃은 보존했다. 이 사본은 배포물이 아니며 워치 동봉 설치 검증의 근거로 사용하지 않는다.

미러링에서 개발 서버 연결·홈 표시, 러닝 준비 화면의 GPS 준비 완료와 심박 방식 세 가지, 건강 앱 방식의 기본 선택, 러닝 시작 버튼을 확인했다. 사용자가 직접 러닝을 시작할 수 있게 준비 화면을 열어 두었다. 실제 러닝 시작·심박 수신·권한 창의 반복 여부는 이번 화면 확인에서 검사하지 않았다. Metro에는 기존 Skia Path API 사용 경고가 있으며 연결·번들은 완료됐다.

리뷰는 권한 요청 상태, 네이티브·화면 사이의 호출, 심박 수신·중복·지연·삭제, 저장 후 재조회와 기존 기록 호환을 중심으로 진행했다. 다음 P2 항목을 발견했고, 사용자의 후속 수정 요청에 따라 아래와 같이 해결했다.

### P2: 묶음 심박을 한 측정값으로 처리한다

`TrackingManager.mergeHealthHeart`는 `HKQuantitySample` 하나를 해당 UUID와 시작 시각의 심박 값 하나로 넣는다. 하지만 `count > 1`인 자료는 여러 심박을 담은 시리즈다. 이 경우 각각의 값과 시각이 빠져 최대 심박·평균과 최신값 판단이 잘못될 수 있다. 현재 합성 검사는 개별 심박 이벤트를 사용하므로 이 입력 형태를 검증하지 않는다.

샘플 개수가 1이면 개별 값으로, 1보다 크면 `HKQuantitySeriesSampleQuery`로 각 값·측정 시각을 읽는다. 원본 UUID와 시리즈 내부 순번으로 항목을 식별하고 원본 UUID도 별도 보관한다. 조회는 러닝 구간과 겹치는 원본을 포함하며 실제 유효 구간 판정은 개별 측정 시각에 적용한다. 모든 항목을 읽지 못하면 기존 값은 유지하고 재조회 실패를 알린다.

이전 개발 앱이 같은 UUID의 대표값 하나를 저장한 경우, 시리즈 조회 완료 후 대표값만 제거하고 개별 값을 넣는다. 반복 조회는 기존 항목을 중복으로 넣지 않는다. 원본 삭제 통지는 시리즈 조회 전에 반영한다. 이후 시리즈 조회가 실패해도 이미 받은 삭제 통지는 유지한다. 삭제 통지는 그 UUID에 속한 모든 값을 제거하며 삭제 표식을 로그에 남겨 더 늦게 끝난 조회와 앱 재실행에서도 복원되지 않게 한다. 워치 직접 측정의 기존 값은 이 삭제로 제거하지 않는다.

Swift 합성 계산·저장 검사는 51개에서 63개로 늘었다. 시리즈가 시작·종료 경계를 걸치는 경우, 일시정지 제외, 개별 최대값·평균·최신값, 같은 시각의 별도 측정, 반복 조회, 대표값 교체, 원본 단위 삭제, 삭제보다 늦은 조회, 로그 재실행을 확인했다. 실제 HealthKit 묶음 자료의 조회는 실기기 QA에서 별도 확인해야 한다.

근거: [Apple 묶음 운동 샘플 안내](https://developer.apple.com/documentation/healthkit/accessing-condensed-workout-samples), [샘플의 count](https://developer.apple.com/documentation/healthkit/hkquantitysample/count). Apple은 심박을 포함한 운동 자료를 묶을 수 있으며 `count > 1`인 샘플은 시리즈 쿼리로 상세 값을 읽도록 안내한다.

### 후속 수정 검증 (2026-10-07)

최종 코드에서 Swift 합성 검사 63개와 심박·권한 관련 화면 회귀 검사 3개 묶음·12개가 통과했다. TypeScript, 내부/공개 빌드 설정, 문서·diff 검사도 통과했고 ESLint는 오류 0개·기존 경고 30개다. 아이폰·워치 동봉 무서명 Debug 빌드가 완료됐다. 기존과 같은 아이폰 확인용 서명 사본으로 업데이트 설치했으며 앱 삭제는 하지 않았다. 개발 서버는 8081에서 계속 실행 중이다. 설치 후 아이폰 사용 중 상태로 미러링이 끊겼다가 다시 연결됐다. 첫 실행에서 개발 서버 연결 오류가 표시됐지만 JS 재로드 후 러닝 준비 화면이 정상 표시됐다. 건강 앱 기본 선택과 세 가지 심박 방식, GPS 준비 버튼을 확인하고 화면을 열어 두었다. 실제 러닝은 시작하지 않았다. 실제 묶음 건강 데이터와 권한 창 반복 여부는 합성 검사로 확인한 범위에 포함하지 않는다.

## 건강 앱 고정과 워치 표시 정정 (2026-10-07)

사용자가 심박 선택 옵션 제거와 아이폰 시작 후 워치 미표시 수정을 직접 요청했다. 앞서 승인한 내부 측정 작업의 정정으로 [FRD](../../specs/frd/internal-run-tracking.md) §8-1 건강 앱 심박 불러오기·§8-2 워치는 아이폰 지표를 표시하고 제어한다·§8-3 워치가 열리지 않거나 연결이 끊어질 때를 갱신했다. 새 러닝은 건강 앱 읽기로 고정하며, 워치는 별도 운동 세션을 만들지 않는 지표 표시·제어 앱으로 수정한다. 기존 직접 측정 기록은 보존한다.

기존 구현은 건강 앱 방식에서 `watchEnabled`가 꺼져 워치 상태 전송이 막혔다. 설치한 QA 사본도 워치를 제외했으므로 최신 워치 코드가 설치됐다는 근거가 없었다. 전송 조건과 워치 수신·표시를 함께 수정하고 서명·설치 결과는 별도로 기록한다.

이 정정에서 Swift 합성 검사 74개·Jest 40개 묶음 307개가 통과했고, 타입·린트·공개/내부 설정·문서 검사를 완료했다. 린트는 오류 0개·기존 경고 30개다. 아이폰·워치 무서명 Debug 빌드를 통과했다. 워치에는 HealthKit entitlement와 운동 백그라운드 모드를 생성하지 않으며 EAS 워치 자격 증명 선언도 같은 기준으로 맞췄다. Xcode 자동 서명은 해당 팀 계정을 찾지 못하고 워치 개발 프로파일도 없어 실패했다. 기존 EAS·Apple 인증으로 등록 정보와 설치된 개발 인증서를 확인했다. 사용자가 개발팀 BT2KSYYPDF의 Apple Watch SE 등록·개발 프로파일 생성을 별도로 승인했다. 워치를 등록하고 기존 인증서를 사용하는 워치 개발 프로파일을 생성했다. 새 인증서 생성·기존 인증서 폐기는 하지 않았다. 해당 프로파일과 기존 아이폰 프로파일로 아이폰·워치 동봉 사본의 서명을 완료했고 깊은 서명 검증을 통과했다. 설치·실기기 결과는 아래에 이어 기록한다.

아이폰·워치 동봉 개발 사본 1.0.0(1)을 아이폰에 업데이트 설치했다. 아이폰 Watch 앱의 사용 가능한 앱에서 Runary 설치를 요청했고, 설치된 앱 목록에 Runary가 표시되는 것을 확인했다. Mac에서 워치에 직접 연결하는 개발 채널은 준비 단계에서 시간 초과했다. 워치의 직접 화면·실행과 실제 연결 응답은 사용자 확인을 기다리고 있으며, 아이폰의 설치 목록만으로 워치 지표 표시를 통과 처리하지 않는다.

워치 실행 확인과 짧은 연결 검사를 진행하는 동안 아이폰 GPS 준비에서 위치 권한 창이 나타났다. 위치 접근은 사용자 응답을 기다리며 러닝을 시작하지 않았다. 워치 설치 완료와 실제 지표 표시·제어의 통과를 구분한다.

## 자동 연결·워치 시작과 빈 값 표기 보완 (2026-10-07)

사용자가 개발 앱에서 워치 연동이 일부 동작하지만 현재 러닝 누락, 종료·새 시작 반영 지연, 정상 대기 화면의 다시 연결 버튼을 제보하고 자동 동기화·워치 시작·하이픈 표기를 요청했다. 앞선 승인 작업의 보완으로 [FRD](../../specs/frd/internal-run-tracking.md) §8-4 자동 상태 갱신과 워치에서 시작과 PRD를 함께 개정했다. 이 사용자 제보는 실제 실행의 근거지만 안정적인 지표·제어 통과의 근거는 아니다.

아이폰의 종료 이후 상태 전송 누락과 워치의 주기적 재조회 부재를 수정한다. 워치에서 아이폰 GPS 시작·재개를 요청하고, 전면·GPS·권한 조건을 만족하면 같은 식별자로 반영한다. 건강 앱 읽기는 유지한다. 사용자는 30초 테스트에서 Runary만 실행했다고 확인했으며, 센서의 연속 측정을 시작하던 이전 워치 운동 방식과 현재 읽기 방식의 차이를 안내했다. 20~30초 심박 수신을 보장하지 않는다. 앱의 자동 전면 실행과 상태 자동 동기화를 구분한다. 구현·검증 결과는 작업 후 아래에 남긴다.


### 자동 동기화 구현과 검증

`TrackingManager`가 엔진 없는 대기·종료 상태도 전달하도록 바꾸고, 연결 복귀와 워치의 상태 요청에 현재 스냅샷으로 답한다. 워치는 활성 화면에서 3초 간격으로 다시 조회하며 마지막 상태와 최신 응답을 구분한다. 요청 식별자·10초 명령 신선도·2분 대기 만료를 공통 Swift 타입으로 처리하고 시작 요청·처리 이력을 저장한다. GPS·전면 실행 조건이 준비된 뒤 같은 요청 식별자로 한 번만 시작한다. 정상 상태의 수동 연결 버튼을 제거하고 빈 지표를 ASCII `-`로 맞췄다.

Swift 계산·저장·상태 검사 90개, 전체 Jest 40개 묶음 308개가 통과했다. 최신 화면 보완 후 해당 화면 검사 5개도 통과했다. 타입·내부/공개 설정·문서·diff 검사를 완료했고 린트는 오류 0개·기존 경고 30개다. 새 공통 Swift 파일이 기존 Pods 프로젝트의 컴파일 목록에서 빠진 빌드 실패를 확인해 기존 의존성으로 `pod install --no-repo-update`를 실행한 뒤 아이폰·워치 Debug 빌드를 통과했다.

### 건강 앱 읽기를 유지한 워치 실행 탐색

사용자가 건강 앱 방식으로도 워치 앱을 열 수 있는지 다시 물었다. Apple SDK와 문서에서 `startWatchApp` 호출과 워치의 운동 세션 생성이 별개임을 확인했다. 다만 워치 델리게이트 문서는 이 요청을 백그라운드 실행으로 설명한다. [FRD](../../specs/frd/internal-run-tracking.md) §8-5 건강 앱 방식을 유지하는 워치 실행 검증·PRD·결정문을 같은 변경에 맞췄다. Nike의 내부 API는 확인하지 못했다.

내부 빌드의 명시적인 시작·재개에서만 실행을 요청하고 워치 델리게이트는 상태 갱신만 한다. HealthKit 운동 세션·워치 센서·워치 건강 권한·운동 쓰기 권한은 추가하지 않았다. 실행 완료 콜백은 연결 성공 판정으로 사용하지 않는다. 워치의 실제 응답에 앱 빌드·동기화 버전·델리게이트 수신 여부를 넣어 설치 버전과 전달 여부를 확인할 수 있게 했다. 성공 진단을 오류로 분류하던 탐색 코드는 즉시 고쳐 별도 이벤트로 보관하고, 대기 상태에서는 기록용 이벤트를 쌓지 않는다.

기존 승인 프로파일로 서명·검증한 아이폰·워치 동봉 개발 사본 `1.0.0(2)`를 업데이트 설치했다. 미러링에서 GPS 준비·건강 앱 고정·짧은 러닝 시작·`-` 표기·종료 저장을 확인했다. 이번 실내 정지 QA 기록은 4분 58초·0.02km이며 실제 운동 정확도의 근거가 아니다. 실행 요청은 `watchLaunchSucceeded`로 응답했지만 사용자는 워치가 자동으로 열리지 않았다고 확인했다. 자동 전면 표시는 미통과다. 이 기록에는 심박 이벤트가 없고 건강 조회 오류도 없었다. 빈 조회는 권한 허용·거부를 구분하지 못하므로 심박 생성·동기화 완료나 권한 허용을 판정하지 않는다.

직접 워치 개발 채널에서 설치 빌드 조회는 20초 제한의 연결 시간 초과로 실패했다. 아이폰 설치 완료만으로 최신 워치 바이너리의 반영과 양방향 시작·종료를 통과 처리하지 않는다. 최종 설치와 남은 실기기 확인은 아래에 이어 기록한다.


### 최종 개발 설치 확인

마지막 소스 수정 이후 `TrackingManager` 객체 파일의 생성 시각과 소스 시각을 비교하고 아이폰·워치 최종 Debug 컴파일 성공을 확인했다. 개발 사본 `1.0.0(3)`에서 두 앱의 빌드 번호 일치와 깊은 서명 검증을 확인한 뒤 업데이트 설치했다. CoreDevice의 실제 아이폰 앱 조회에서도 `1.0.0(3)`을 확인했다. 미러링에서 기존 보관함 21개 유지, 개발 서버 연결과 GPS 준비 완료·심박 옵션 없는 러닝 준비 화면을 확인했다. QA 기록은 종료·저장됐으며 최종 설치 때 진행 중인 러닝은 없다.

사용자에게 최신 워치 앱의 시작 버튼과 아이폰 측정 반영을 확인하도록 요청했다. 이 사용자 확인 전까지 최신 워치 설치 버전·양방향 시작은 미검증이다. 최종 타입·린트·Swift 90개·문서·diff 검사도 다시 통과했으며 린트 경고 30개는 기존 항목이다. 자동 전면 표시와 건강 앱 읽기만으로 연속 심박을 얻는 조건은 해결 완료로 보고하지 않는다.


## 실제 읽기 설정·지연 심박 확인과 워치 직접 설치 (2026-10-07 후속)

사용자가 Runary만 실행한 테스트에서 1분 이상 심박과 워치 화면이 나타나지 않는다고 다시 제보했다. 현재 러닝을 종료하거나 아이폰 앱을 재시작하지 않고 기기 내 로그와 건강 앱 설정을 확인했다. `heartSource=health`와 건강 조회의 삭제 통지 수신을 확인했고, 건강 앱 → 앱 → Runary의 심박수·운동·운동 경로 읽기 토글이 켜져 있음을 미러링으로 확인했다. 권한을 변경하지 않았다.

건강 앱에 이번 러닝 시작 뒤 측정된 심박이 있었으며 Runary 전면 복귀 후 같은 기록에 실제 심박이 병합됐다. 수신 당시 측정 시각은 약 12분 전이었다. 이후 최신 건강 심박도 수신됐다. 조회·병합은 실제로 동작하지만 15초보다 오래된 값을 현재 심박으로 숨기는 화면 때문에 수신 성공이 드러나지 않았다. 평균 심박과 마지막 측정 시각을 별도 안내하고 최신값 대기를 구분하도록 화면을 수정했다. 현재 심박·통계·GPS·시간 계산은 바꾸지 않았다. 같은 진행 기록에서 미러링 안내 반영을 확인했다. 측정 앱 없이 연속 심박이 생성되는 것과 저장된 심박 읽기 성공을 구분한다.

`heartImportNotice`와 화면 회귀 검사 2개 묶음 10개, 타입·린트·diff 검사가 통과했다. 린트는 오류 0개·기존 경고 30개다. 이번 표시 변경은 JS만 수정해 진행 중인 러닝을 유지한 채 개발 서버에서 반영했다.

사용자가 Apple Watch SE의 직접 미러링을 물어 Apple 공식 지원 문서에서 SE 미지원임을 확인했다. [Apple Watch 미러링](https://support.apple.com/guide/watch/apple-watch-mirroring-apd890848603/watchos). Mac의 오래된 개발자 모드 기록은 현재 상태의 근거로 사용하지 않는다. 사용자가 실제 워치 개발자 모드가 켜져 있다고 확인했다. 첫 직접 설치는 개발 서비스 준비 중 30초 제한으로 종료됐지만 이어진 기기 정보 조회는 성공했다. 준비된 채널에서 최신 워치 직접 설치를 이어 확인한다. 설치 결과는 아래에 기록한다.


### 실제 워치 설치·응답 확인

CoreDevice의 새 기기 정보 조회에서 현재 Apple Watch SE / watchOS 10.6.2의 개발자 모드 `enabled`와 개발 서비스 사용 가능을 확인했다. 오래된 `disabled` 캐시와 구분한다. 준비된 채널로 최신 서명 워치 개발 앱을 직접 업데이트 설치했고 워치의 앱 조회에서 실제 `1.0.0(3)`을 확인했다. 워치 앱을 직접 실행한 뒤 현재 아이폰 러닝의 로그에 `build:3,sync:2,launchHandled:false` 응답이 들어왔다. 이 러닝의 심박은 2건이며 오류는 없다. 앞선 아이폰 설치 완료와 이번 실제 워치 설치·응답 확인을 구분한다.

아이폰 미러링에서는 평균 심박·마지막 측정 시각 안내가 표시되는 것을 확인했다. 현재 심박의 15초 기준은 유지해 오래된 값을 현재값으로 바꾸지 않는다. 아이폰 러닝을 종료·재설치하지 않았다. 워치 실제 화면 캡처를 위해 Xcode 기기 창도 확인했지만 별도 연결이 시간 초과했고 캡처 버튼은 비활성 상태다. CLI의 설치·앱 조회·실행·워치 응답 성공을 화면 캡처 성공으로 기록하지 않는다. 사용자에게 실제 워치의 시간·거리 표시 확인을 요청했다.

이번 확인은 저장된 건강 심박 읽기와 최신 워치 연결의 실제 동작 근거다. Runary만 켠 상태의 연속 심박 생성·1분 이내 최신값, 아이폰 새 시작 때 워치 자동 전면 표시, 최신 워치에서 시작·종료·재시작의 전체 물리 QA는 여전히 미검증이다.


사용자는 최신 설치 이후 워치에 러닝 화면이 보였지만 이후 다시 안 보인다고 제보했다. 지속 표시를 통과 처리하지 않는다. 시계 화면으로 복귀한 경우와 Runary 안에서 데이터가 사라진 경우, 값만 멈춘 경우를 구분하도록 확인을 요청했다. [Apple의 시계 복귀 설정](https://support.apple.com/en-ie/guide/watch/apd127ec93ac/watchos)과 [워치 전면 상태](https://developer.apple.com/documentation/watchkit/taking-advantage-of-frontmost-app-state)를 확인했으나 현재 제보를 OS 시계 복귀로 단정하거나 설정을 변경하지 않았다.


사용자가 미표시 상태를 기본 시계 배경 화면이라고 확인했다. Runary 내부에서 데이터가 지워진 제보와 구분한다. 워치의 앱별 시계 복귀 시간은 OS 설정이며 일반 앱의 전면 유지 시간과 관련된다. 다른 운동 앱에 영향을 주지 않는 현재 정책을 유지하면서 Runary만 1시간 후 복귀로 설정할 수 있는 경로를 사용자에게 안내하고 적용 여부를 요청했다. 설정을 임의로 변경하지 않았다. 한 번 열린 앱의 유지 시간과 최초 자동 전면 실행·연속 심박 생성은 서로 다른 조건이다.


## 추가 요구: 측정 중 깨울 때 항상 측정 화면으로 복귀

사용자가 요구를 구체화했다. Runary에서 측정 중에는 워치 화면이 꺼졌다가 깨어날 때 측정 화면이 우선 표시돼야 한다. 앱 목록으로 이동한 뒤 화면을 끄고 다시 깨워도 측정 화면으로 돌아와야 한다. 일반 앱의 전면 시간을 1시간으로 바꾸는 제안은 이 요구를 충족하지 못하므로 철회한다. 사용자 OS 설정은 변경하지 않았다.

현재 일반 표시 앱과 상태 동기화만으로 이 동작을 완료 처리하지 않는다. Apple 문서는 앱을 명시적으로 나가면 일반 앱의 전면 상태를 잃는다고 설명한다. 운동 세션은 표준 러닝 경로지만 워치에서 세션 하나만 실행하므로 기존 다른 운동 앱 병행 정책과 충돌한다. iPhone의 세션을 워치로 역방향 미러링하는 방안도 현재 SDK에서는 지원되지 않는다(`startMirroringToCompanionDevice`는 iOS에서 unavailable).

대안으로 공개 `CLBackgroundActivitySession`과 실제 워치 위치 수신의 세션을 내부 실험으로 검토한다. watchOS 10.0에서 사용 가능하지만 원한 앱 복귀 동작이 제공되는지는 실기기로 검증해야 한다. 임시 생성 iOS 파일과 `/private/tmp`에만 실험 코드를 준비했으며 제품 워치 원본은 바꾸지 않았다. 실험은 위치 수신 건수·권한 상태·앱 단계만 로컬에 기록하고 좌표는 저장·전송하지 않는다. 사용자가 직접 시작하기 전에는 GPS를 켜지 않으며 3분 후 종료한다. 워치에 새로운 GPS 수집이 생기므로 실험 시작 전에 사용자 확인을 받는다. 건강 앱 심박 읽기와 다른 운동 앱 세션은 유지한다.

근거: [Apple 워치 전면 상태](https://developer.apple.com/documentation/watchkit/taking-advantage-of-frontmost-app-state), [Apple 운동 세션 제한](https://developer.apple.com/documentation/healthkit/hkworkoutsession), [Apple의 진행 중 세션 설명](https://developer.apple.com/forums/thread/756400), [Core Location 배경 활동 세션](https://developer.apple.com/documentation/corelocation/clbackgroundactivitysession). 위치 권한을 화면 유지 우회만을 위해 제품에 추가하지 않으며 실제 수집의 효용과 배포 적합성은 별도로 판단한다.


위치 세션 실험의 워치 타깃 컴파일과 기존 개발 자격의 서명·깊은 검증이 통과했다. 검토용 Swift 소스와 앱을 `/private/tmp`에 보관하고, 로컬 생성 iOS 소스·Info.plist는 제품 버전으로 복원했다. 실험 앱은 아직 설치하지 않았으며 실제 GPS 수집도 시작하지 않았다. 원한 복귀 동작의 성공은 아직 확인되지 않았다. 사용자에게 3분 워치 GPS 사용의 명시적 확인을 요청했다.


## 2026-10-08 재개와 위치 세션 실험 준비

사용자가 중단한 작업을 이어 진행하도록 요청했다. 규약·FRD·임시 실험 소스와 앱을 다시 확인했다. 실험 종료는 타이머뿐 아니라 위치 수신과 앱 재활성화에서도 3분 만료를 확인하도록 보완했고 오류 코드 표시의 이스케이프도 바로잡았다. 워치 타깃 재컴파일·기존 개발 자격의 서명·깊은 검증을 통과했다. 로컬 생성 소스와 Info.plist는 제품 버전으로 복원했다.

개발 서버가 중단돼 있어 내부 플래그·LAN 8081로 재개하고 서버 응답·iOS 번들을 확인했다. 실제 워치 기기 정보에서 개발자 모드와 개발 서비스 준비를 확인한 뒤 실험 앱을 직접 업데이트 설치·실행했다. 시작 버튼을 사용자가 누르기 전에는 위치를 요청하거나 수집하지 않는다.

초기 진단 파일 조회는 제어 채널 준비 단계의 시간 초과로 실패했다. 위치 수신 성공을 판정하지 않는다. 사용자에게 실험 시작과 앱 목록 이동·손목 내림·깨움 이후 자동 복귀를 확인하도록 요청했다. 아이폰은 진행 기록 없이 준비 화면이었지만 GPS 준비가 만료돼 실제 QA 러닝을 시작하지 못했다. 준비 조건을 우회하지 않고 위치 세션의 OS 복귀 실험을 독립적으로 먼저 확인한다.


재개 화면에서 GPS 준비가 만료된 것을 확인하고 코드 리뷰에서 시간 초과 기준 오류를 발견했다. 준비 완료 뒤에도 준비 버튼을 누른 시각만 기준으로 30초 후 취소되고 있었다. 마지막으로 유효한 위치를 수신한 시각을 기준으로 바꿔, 좋은 위치가 계속 들어오면 준비 완료를 유지하고 실제 수신 공백만 시간 초과로 처리한다. 시작 시 위치 신선도·정확도 검사는 유지한다. 해당 회귀 검사는 초기 대기·30초 경계·준비 화면에서 1분 이상 대기·연속 수신·수신 중단을 확인한다.


### 위치 세션 결과와 운동 세션 검증 선택

사용자는 워치 위치 실험을 시작했지만 손목을 내렸다 깨워도 시계·목록 화면이 나온다고 확인했다. 이 실험은 자동 복귀 미통과이며 제품에 넣지 않는다. 워치 직접 진단 파일 조회는 제어 채널 시간 초과로 실패해 실제 위치 수신 건수는 검증하지 못했다. 기존 앱 복원 요청도 같은 연결 오류로 완료되지 않았다. 3분 종료 처리 외 추가 GPS 시작은 요청하지 않는다. 복원 완료는 설치 결과로 따로 확인한다.

사용자는 다음 단계에서 `측정 화면 복귀 우선: Runary 운동 세션 검증`을 직접 선택했다. 기존 다른 워치 운동 앱 병행 정책과 충돌할 수 있다는 설명을 확인한 뒤의 실험 선택이다. 따라서 운동 세션의 진행 중 화면 복귀를 3분 실험으로 확인하되, 다른 워치 운동을 모두 마친 상태에서 시작하도록 실험 UI에서도 확인한다. 사용자가 시작하기 전 운동 권한을 요청하거나 세션을 만들지 않는다. 건강 앱에 운동 기록을 저장하는 builder·save는 사용하지 않고 좌표·개별 심박 원본을 전송하지 않는다. 아이폰의 심박 출처는 건강 앱 읽기로 유지한다.

워치 파일 조회 대신 기존 WatchConnectivity로 실험 식별자·시간·앱 단계·운동 세션 상태·권한 상태·이벤트 종류만 아이폰에 전달하는 경로를 추가했다. 아이폰은 내부 빌드에서만 허용하고 필드를 검증·정규화해 60건까지 별도 로컬 진단 파일로 보관한다. 중복 전달은 제거하고 좌표·심박 같은 추가 필드는 저장하지 않으며 러닝 제어·원본 기록을 변경하지 않는다. 순수 Swift 검사 99개에서 메타데이터 허용·원본 센서 제외·만료·잘못된 상태를 확인했다. 타입·린트·문서·diff와 네이티브 빌드 검사도 완료한다.


운동 실험과 진단 수신의 아이폰·워치 컴파일, Swift 검사 99개, 타입·린트·문서·diff를 통과했다. 권한 화면 종료 뒤 활성화 대기와 이전 세션의 늦은 콜백도 실험 소스에서 막았다. 기존 프로파일이 HealthKit을 허용함을 확인하고 새 자격 생성 없이 운동 실험 워치를 포함한 아이폰·워치 개발 사본 `1.0.0(4)`의 서명·깊은 검증을 완료했다. 생성 소스·Info.plist는 제품 기준으로 복원했다.

아이폰 4번 개발 앱의 업데이트 설치·개발 서버 연결과 보관함 21개 유지를 확인했다. 워치 직접 설치는 제어 채널 준비 단계의 시간 초과로 실패했다. 따라서 워치 설치 완료나 운동 실험 성공을 기록하지 않는다. 아이폰에 동봉한 워치가 페어링 설치 경로로 갱신됐는지 사용자에게 `운동 실험 시작` 버튼 유무와 실제 자동 복귀를 확인하도록 요청했다. 다른 워치 운동을 끝낸 상태에서만 시작하도록 안내했다. 워치 위치 실험은 더 시작하지 않는다.

### 이전 실험 앱 잔류와 버튼 혼동 확인

사용자는 워치에 `GPS 실험 시작`과 일반 `러닝 시작`이 함께 보이며 `운동 실험 시작`은 없다고 확인했다. 따라서 아이폰에 4번을 설치한 것만으로 워치가 갱신됐다고 판단하지 않는다. 일반 `러닝 시작`을 실수로 눌렀을 때 아이폰 측정이 시작됐다는 사용자 확인은 워치에서 아이폰으로 시작 요청이 전달된 근거다. 이후 아이폰 미러링에서 진행 중인 기록 없이 준비 화면으로 돌아온 상태를 확인했다. 에이전트가 측정을 일시정지하거나 종료한 것으로 기록하지 않는다.

새 임시 운동 실험 화면에서는 일반 러닝 제어를 제거하고 운동 실험 시작·종료 버튼 하나만 표시한다. 운동 세션의 실행 콜백이 온 뒤에만 `검증 중`을 표시한다. 아이폰 기록은 새로 시작하지 않으며 기존 최대 3분 종료·다른 운동 종료 확인·권한 확인을 유지한다. 수정한 워치의 컴파일과 아이폰·워치 개발 사본 `1.0.0(5)`의 깊은 서명 검증을 통과했다. 5번은 아직 기기에 설치하지 않았다. 생성 소스·Info.plist는 제품 기준으로 복원했다.

새 기기 조회에서도 워치 개발자 모드는 켜져 있지만 개발 서비스는 사용 불가이며 네트워크 터널이 끊겨 있었다. 기존 페어링 재연결 요청은 페어링 상태만 확인했고 개발 연결은 복구하지 못했다. Xcode도 연결 준비 중이며 공유 캐시 복사 오류를 표시한다. Mac Wi-Fi에는 현재 로컬 주소가 있고 아이폰 개발 연결은 유지된다. 워치의 Wi-Fi 연결·잠금 해제 상태 확인을 요청했으며, 같은 설치 명령을 반복하지 않고 이 확인 뒤 이어간다. 앱 삭제·기기 초기화·개발자 모드 변경은 하지 않았다.

### 운동 세션 실행 확인과 심박 미수신 원인 분리

후속 사용자 테스트에서 양방향 러닝 연동이 확인됐다. 사용자는 앱 목록을 나갔다가 깨우면 시계 화면이 보이고, 상단 Runary 아이콘을 누르면 측정 화면이 열린다고 확인했다. 요청한 자동 복귀는 여전히 미통과다. Runary의 시계 복귀 설정에는 `기본 설정`과 `사용자화`가 있다고 답했으며 별도 `세션 중/앱으로 돌아가기` 항목은 확인되지 않았다. 설정을 변경하도록 다시 요청하지 않았다. [Apple 전면 상태 설명](https://developer.apple.com/documentation/watchkit/taking-advantage-of-frontmost-app-state)의 명시적 앱 이탈과 시계의 진행 중 세션 아이콘 경로를 실제 자동 복귀 성공과 구분한다.

새 아이폰 로그에서 워치 `build:4,sync:2,launchHandled:false` 응답을 확인했다. 따라서 앞서 남아 있던 GPS 실험 앱은 이후 운동 실험 4번으로 갱신됐다. 직접 설치 실패의 이전 기록을 실제 현재 설치 상태로 사용하지 않는다. 별도 진단에는 2026-10-08 21:23:30 KST 운동 세션 실행과 21:26:29 종료가 남았고, 중간 백그라운드·활성 전환도 수신됐다. 아이콘 표시와 세션 실행은 확인됐지만 앱 목록 이후 자동 화면 복귀는 확인되지 않았다.

같은 시간대의 아이폰 러닝 세 개는 심박 출처가 모두 `health`이고 심박 이벤트는 각각 0건이다. 건강 조회 오류는 없고 삭제 통지를 수신했다. 이 근거로 읽기 허용이나 새 샘플 생성·동기화 완료를 단정하지 않는다. 실험 4번의 권한 요청은 운동 쓰기만 포함했고 워치 심박 조회·전달 코드는 없었다. 사용자가 승인한 운동 권한을 심박 읽기 승인이나 아이폰의 실시간 건강 동기화로 해석하지 않는다.

### 워치 건강 저장소 읽기 진단 6번

심박이 워치 건강 저장소에도 없는지, 아이폰으로의 건강 동기화가 늦는지 분리하기 위해 임시 진단을 추가했다. 사용자가 선호한 일반 `러닝 시작`·일시정지·재개·종료와 아이폰 연동을 유지한다. 단일 버튼 실험 5번은 설치하지 않고 건너뛴다. 임시 Swift 소스와 개발 사본은 `/private/tmp`에만 두며 제품 워치 원본·FRD의 심박 전달 정책은 바꾸지 않는다.

사용자가 다른 워치 운동을 마친 뒤 직접 시작하면 최대 3분 운동 세션과 함께 심박수 읽기 권한을 요청한다. 워치의 HealthKit 저장소를 anchored query로 관찰하고 묶음 샘플도 펼쳐 `워치 건강 심박`과 수신 건수를 표시한다. 읽기 권한 허용·거부를 API로 단정하지 않으며 빈 조회·조회 실패를 구분한다. 15초보다 오래된 값은 현재 심박으로 표시하지 않는다. 종료 후 조회를 멈추고 이전 실험의 늦은 콜백과 삭제된 샘플의 재반영을 막는다. 코드 리뷰에서 권한 요청 실패 뒤 실험 시작과 시리즈 완료·오류 뒤 중복 콜백 처리도 차단했다.

이 진단은 `HKLiveWorkoutBuilder`를 사용하지 않고 운동 기록을 저장하지 않는다. 개별 심박·좌표를 파일이나 아이폰에 보내지 않는다. 아이폰 심박 수신 문제의 구현 완료가 아니라 첫 미수신 지점을 확인하는 실험이다. 워치 저장소에서 심박이 확인되면 아이폰 전달 방식을 별도로 검증하고 제품 기준을 함께 개정한다.

워치 타깃 컴파일과 기존 인증서·프로파일을 재사용한 개발 사본 `1.0.0(6)`의 깊은 서명 검증을 통과했다. 생성 iOS 워치 소스·Info.plist는 제품 기준으로 복원했다. 미러링에서 진행 기록 없이 최근 러닝 25개가 있는 준비 화면을 확인한 뒤 아이폰을 업데이트했고 실제 앱 조회에서 빌드 `6`을 확인했다. 워치 직접 설치는 제어 채널 준비 시간 초과로 실패했다. 동봉 앱의 페어링 설치 완료는 아직 확인되지 않아 사용자에게 새 `워치 건강 심박` 항목과 실제 조회 결과를 확인하도록 요청했다. 심박 표시·자동 복귀는 완료 처리하지 않는다.

사용자는 처음 새 항목이 없다고 답했지만, 워치 Runary를 종료하고 다시 연 뒤 `워치 건강 심박: - bpm`이 보인다고 확인했다. 새 진단 화면의 실제 반영 근거다. 이어 운동 실험과 심박수 읽기를 확인한 뒤 숫자와 수신 건수가 나온다고 답했다. 워치 건강 저장소 읽기는 실기기 확인을 완료했다. 개별 심박을 아이폰으로 전송하는 기능은 진단에 없으므로 아이폰 기록 반영의 통과로 확대하지 않는다.

아이폰 Watch 앱에서는 Runary 설치됨·앱 보기 켜짐을 확인했지만 버전은 표시되지 않았다. 업데이트 완료는 이 화면만으로 판정하지 않는다. 아이폰 6번 개발 앱은 LAN 서버에서 번들을 받아 실행됐고 기존 보관함 21개를 확인했다. `새로 만들기`에서 운동·운동 경로 읽기 권한 화면이 나타났다. 심박수 요청은 화면에 없었다. 이 두 항목의 이전 응답 여부가 확인되지 않아 반복 요청 오류로 단정하거나 허용·거부를 대신 선택하지 않았다.

다음 수정안을 [FRD §8-7](../../specs/frd/internal-run-tracking.md#8-7-워치-건강-저장소의-심박-직접-전달-2026-10-08-사용자-승인)에 정리했다. 건강 앱 방식과 다른 운동 비제어를 유지하면서 워치 건강 저장소의 샘플을 페어링된 아이폰 기록에 직접 전달하는 안이다. 현재 표시·제어 전용 기준을 넓히므로 사용자 확인 후 제품 구현에 들어간다. 자체 운동 세션의 자동 결합은 이 안에 포함하지 않는다. 워치 진단 컴파일·서명·문서·diff 검사는 통과했다.


## 2026-10-08 직접 전달 구현 승인

사용자가 FRD §8-7 워치 건강 저장소의 심박 직접 전달 수정안을 확인하고 구현 진행을 승인했다. 아이폰 건강 읽기와 같은 샘플 식별자를 재사용하고 늦은 전달·중복·삭제·종료 뒤 다른 기록 섞임을 검증한다. 워치 심박수 읽기의 최초 명시적 요청을 추가하지만 자체 운동 세션의 자동 시작은 넣지 않는다. 구현·검증 결과는 아래에 이어 기록한다.

### 구현 경로와 자동 검증

`WatchHealthReader`가 워치 건강 저장소의 단일·묶음 심박을 읽는다. 최초 명시적인 러닝 시작·재개·건강 심박 연결에서만 요청하며, 앱 활성화·워치 실행 요청은 요청 필요 여부 확인과 읽기 재사용만 한다. 조회 완료와 읽기 허용을 구분한다. 중단된 묶음 조회는 완료 처리하지 않고 다음 활성화에 다시 읽는다. 같은 콜백의 단일 샘플과 여러 묶음을 일괄 처리해 개별 값마다 파일을 쓰거나 쿼리를 만들지 않는다.

공통 `TrackingWatchHealth` 타입이 기록·샘플 UUID, 묶음 순번, 시각, 유효 수치, 출처와 삭제 통지를 검증한다. 워치는 보호된 대기 파일에 저장한 뒤 WatchConnectivity로 보내며 아이폰의 실제 저장 응답까지 보관한다. 100항목·256배치·24시간 한도, 백업 제외, 삭제 시 대기·전송 정리를 적용했다. 현재 러닝의 새 심박을 먼저 보내고 과거 자료는 배경 경로로 보완한다. 아이폰·워치의 현재 심박 신선도는 15초로 유지한다.

아이폰은 기존 건강 병합 경로를 재사용한다. 건강 UUID·묶음 순번으로 두 전달 경로와 뒤늦은 아이폰 건강 동기화의 중복을 제거한다. 삭제·알 수 없는 기록을 만들지 않으며 다른 기록의 값은 현재 기록에 넣지 않는다. 완료된 같은 기록의 유효 과거 구간은 보완할 수 있지만 시간·경로·종료 시각은 바꾸지 않는다. 실제 워치 심박 수신 뒤 아이폰의 과거 조회 실패 상태가 계속 표시되는 문제도 리뷰에서 수정했다. 비정상적으로 큰 심박 수치가 워치 정수 표시·통계 합산을 망가뜨리지 않도록 공통 유효성 검사에 1,000 이하의 넉넉한 기술 상한을 뒀다. 의학적 정상 범위 판정은 아니다.

Swift 순수 계산·전송·저장 검사 123개, 전체 Jest 40개 묶음 310개, 타입·내부/공개 설정 검사를 통과했다. 린트는 오류 0개·기존 경고 30개다. 새 공통 파일을 기존 Pods 목록에 반영하고 아이폰·워치 전체 Debug 컴파일을 통과했다. 제품 워치는 HealthKit 읽기 capability와 심박 설명만 포함하며 운동 쓰기 설명·workout-processing 모드는 없다. 기존 인증서·프로파일로 제품 개발 사본 7번의 깊은 서명 검증을 통과했다.

실기기 QA 사본에는 승인된 기존 최대 3분 운동 실험만 임시로 결합한다. 직접 전달은 실제 제품 코드로 확인하며 일반 제품 원본에 운동 세션·실험 UI를 넣지 않는다. 설치 버전·워치 실제 응답·아이폰 심박 이벤트와 미러링 표시를 확인한 뒤 아래에 결과를 기록한다.

### 실제 설치와 첫 QA의 버전 분리

최종 제품 사본 7번과 임시 운동 실험을 포함한 QA 사본 8번의 서명·깊은 검증을 완료했다. 사용자가 러닝 종료·아이폰 잠금을 확인한 뒤 미러링에서도 준비 상태를 확인하고 아이폰 8번을 업데이트했다. 실제 버전 조회와 개발 서버 연결·보관함 21개 유지를 확인했다.

첫 QA 러닝은 워치 시작 요청으로 생성됐으며 5분 59초·0km·건강 심박 19건으로 종료·저장됐다. 상세 평균 심박 표시도 확인했다. 그러나 로그에는 워치 빌드 6번·동기화 버전 2가 있었고 `healthWatch` 직접 전달 이벤트가 없었다. 사용자가 실제 워치 문구도 6번이라고 확인했다. 이 수신은 기존 아이폰 건강 동기화 경로의 결과이며 새로운 직접 전달 성공으로 처리하지 않는다.

워치 직접 조회는 처음 시간 초과였지만, 첫 QA를 종료한 뒤 직접 업데이트 설치가 성공했다. 23:04 KST 설치 완료 후 실제 앱 조회에서 `1.0.0(8)`을 확인하고 새 앱을 실행했다. 설치 전에 요청했던 앱 전환기 동작은 이후 필요 없어졌음을 사용자에게 알렸다. 최신 워치로 러닝 시작·3분 운동 실험을 다시 요청했고 실제 전달 이벤트·샘플과 두 화면을 이어 확인한다.

### 직접 전달 확인과 TestFlight 제출 결정

최신 워치의 두 번째 QA 기록 `8AC00955-8D7E-47D9-968C-E442A97D69F7`에서 `build:8,sync:3` 응답과 실제 `healthWatch` 전달을 확인했다. 진행 중 확인 때 심박 45건·고유 식별자 45개와 최근 약 1~5초 수신 지연이 있었고 아이폰 미러링에 현재 심박이 표시됐다. 최종 기록은 8분 1초·0km·심박 78건·직접 전달 이벤트 124건으로 종료·저장됐다. 심박 식별자와 측정 시각·값·출처 조합에 중복이 없었고 워치 전송 대기는 0배치였다. 센서 원본은 콘솔에 출력하지 않고 집계만 확인했다. 실내 정지 QA이며 운동 정확도·장시간 배터리 근거는 아니다.

사용자는 추가 개선에 시간이 오래 걸려 현재 구현을 TestFlight로 제출하고 미진한 부분은 다음에 이어가도록 지시했다. 현재 제품 원본의 건강 읽기·직접 전달·양방향 제어·권한 보완을 내부 측정 프로필로 배포한다. 임시 운동 실험 코드·UI와 개인 `.claude/launch.json`은 배포에 포함하지 않는다. 자동 화면 복귀, Runary 단독의 연속 심박 생성, 다른 운동과의 장시간 병행·잠금·야외 GPS·배터리는 후속 항목이다. 제출·Apple 처리 상태는 빌드·개발 명령어 문서에 기록한다.

### Apple 제출 검증의 필수 설명 보완 (2026-10-09)

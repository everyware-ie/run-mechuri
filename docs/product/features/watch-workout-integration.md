# 워치 운동 세션과 건강 저장

## 착수 근거

[FRD](../../specs/frd/watch-workout-integration.md), [PRD](../../specs/prd/watch-workout-integration.md)를 제시한 뒤 2026-10-26 사용자가 “2번까지 진행해 주세요”로 워치 세션과 건강 저장 구현을 승인했다. 워치 없이 아이폰만으로 측정한 완료 기록도 건강 저장 대상이다. 배포와 실기기 검증 완료를 뜻하지 않는다.

## 진행

아이폰 기록을 기준으로 워치 세션과 건강 내보내기를 별도로 연결했다. 워치 운동 연동과 건강 자동 저장은 처음에 사용자가 각각 켠다. 저장된 건강 심박 읽기는 운동 연동을 꺼도 유지한다.

- `WatchWorkoutSession`: 운동 권한, 같은 러닝의 세션 수명, 30초 연결 지연 시 일시정지, 2분 시 종료, 다른 운동 충돌 후 명시적 재시작, 복구 세션 확인.
- `RunaryWatchApp`: 거리 중심 지표와 아이콘 제어. 종료는 즉시 전송과 영속 전달을 함께 사용하고 아이폰 확인 전에는 전달 중으로 표시한다.
- `TrackingStore`: 늦은 워치 종료 시각을 원본 로그에 남긴다. 읽을 때 이후 좌표와 측정 시간을 제외하며 원본 로그를 훼손하지 않는다.
- `TrackingHealthExport`: 아이폰에서 완료 운동을 저장한다. 운동 객체를 먼저 보관해 재시도 때 UUID를 유지하고, 경로 구간별 저장 결과를 보관한다. 기존 심박 샘플을 연결하며 새로운 심박 사본을 생성하지 않는다.
- `HealthKitBridge`와 기록 목록: Runary 출처와 러닝 ID가 일치할 때만 중복을 숨긴다. 원본 삭제 후 건강 경로를 다시 읽을 때 여러 구간을 보존한다.

워치 시작은 GPS를 기다리지 않는다. 일시정지한 같은 러닝의 재개는 아이폰이 잠긴 상태에서도 네이티브 권한 조건을 확인한 뒤 처리한다. 중단 복구와 최초 시작은 아이폰 실행 조건을 유지한다.

## 검증

- JavaScript 51개 묶음, 376개 검사 통과. 내보낸 기록의 중복 제거와 원본이 없을 때 건강 기록 유지 포함.
- Swift 측정·저장소 137개, 잠금화면 36개 검사 통과. 늦은 워치 종료 요청 이후 좌표·시간 제외와 재실행 보존 포함.
- iPhone·Watch SDK 네이티브 타입 검사 통과. TypeScript 검사 통과, 린트 오류 0개와 기존 경고 30개.
- 내부/공개 설정 및 워치 확장 생성 검사 통과.
- 아이폰·워치 전체 Debug 시뮬레이터 빌드 통과. 이후 아이폰 실기기 설치와 건강 저장 확인은 아래에 기록했다. TestFlight 제출은 진행하지 않았다.

## 남은 실기기 확인

기본 운동 저장과 앱 재진입 후 한 건 유지까지 실기기에서 확인했다. 저장 도중 실패한 경우의 재시도와 실제 HealthKit 실패 복구, 기존 심박 연결의 권한 조건, 여러 경로 구간의 피트니스 표시는 확인해야 한다. 워치 화면 복귀와 단독 실행 심박 측정도 실기기 확인 전이며 자동 검사로 대체하지 않는다. 개인정보 공개 문서는 실제 배포 범위 확정 후 함께 개정한다.

## 2026-10-26 실기기 검증 진행

사용자가 개발 앱에서 실제 측정과 건강 운동 저장 검증을 요청했다. 기존 개발 인증서와 세 타깃 프로파일로 iphoneos Debug 빌드와 깊은 서명 검증을 통과했다. 아이폰의 TestFlight 43번 위에 개발 앱 1번을 업데이트했고, LAN 8081 서버에서 최신 화면이 열리는 것을 확인했다.

설치 전 진행 중인 러닝이 없었다. 설치 후 기존 보관함 27개와 측정 기록 37건을 확인했으며, 측정 기록의 QA 전 사본을 로컬에 보관했다. 사용자가 운동·운동 경로 쓰기를 승인한 뒤 건강 자동 저장을 켰다. 워치 운동 연동은 끈 채 QA 러닝을 시작하고 종료했다.


### 실기기 결과

2026-10-26 21:09 KST에 29.45초 QA 러닝을 완료했다. Runary 상세에 “건강 앱에 저장됨”이 표시됐고, 내보내기 상태도 `saved`, `workoutSaved=true`였다.Apple 건강의 원본 운동 상세에서 데이터 소스 `Runary`, 시작 21:09:13, 종료 21:09:43을 확인했다. 피트니스 요약에는 Runary 아이콘, 상세에는 운동 시간 `0:00:29`가 표시됐다.

앱 재진입 후에도 건강 운동 목록에는 오늘 QA 운동 한 건만 있었다. 측정 기록은 37건에서 38건으로 늘었으며 기존 37건의 요약 파일은 변경되지 않았다. QA 기록은 삭제하지 않고 남겼다.

제자리에서 진행한 짧은 검사라 거리 0, 심박 없음이었다. 경로와 심박 연결, 실패 후 재시도까지 통과한 결과는 아니다.워치를 착용한 뒤 기기는 검색됐지만 개발 서비스 준비와 직접 설치가 시간 초과됐다. 최신 워치 앱 설치와 운동 세션, 화면 복귀는 이번 검사에서 확인하지 못했다.


### 21:24 심박 실기기 추가 검증

워치에 남아 있던 42번 앱을 최신 개발 앱 1번으로 직접 업데이트하고 설치 버전과 실행 성공을 확인했다. 아이폰에서 워치 운동 연동을 켜고 21:24부터 약 72초 동안 제자리 측정을 했다. 사용자는 권한 요청 없이 워치 측정 화면이 바로 표시됐다고 확인했다.아이폰에서 워치 운동 상태 `측정 중`과 심박 78, 84, 90bpm 갱신을 관찰했다. 종료한 Runary 기록에는 평균 81bpm과 최대 90bpm이 저장됐다.

건강 운동 저장은 성공했지만 심박 연결은 실패했다. 최초 조회에서는 필요한 샘플을 모두 찾지 못했고, 같은 기록의 재시도에서는 `com.apple.healthkit` 오류 4가 반환됐다. Apple SDK의 `HKErrorAuthorizationDenied`에 해당한다.피트니스에는 운동 시간 `0:01:12`만 표시됐고 심박 항목은 없었다. 운동은 앞서 만든 29초 QA와 이번 72초 QA 각각 한 건으로 표시됐다. 이번 결과를 건강 심박 연결 완료로 판단하지 않는다.

후속 수정은 기존 심박 샘플 연결 요청의 권한 조건을 확인하는 것이다. 현재 요청하는 쓰기 권한은 운동과 운동 경로뿐이며, 추가 권한이 필요하다면 사용자에게 용도와 범위를 설명한 뒤 요청해야 한다. 타 출처 심박을 복제하는 방식으로 우회하지 않는다.워치 화면 자동 복귀와 경로 저장은 이번 제자리 검증 범위에 포함하지 않았다. QA 러닝은 종료했고 기록은 보존했다.


### 심박 연결 권한 수정

2026-10-26 사용자 수정 요청에 따라 건강 저장의 심박수 쓰기 권한을 추가한다. 기존 설치는 명시적 저장 재시도에서 아직 요청하지 않은 권한만 요청한다. 거부한 권한은 설정 안내로 처리하며 자동 저장은 권한 창을 열지 않는다. 기존 운동 UUID와 심박 샘플을 재사용하고 새 심박 사본을 만들지 않는다. 재시도 시작 시 이전 오류 코드를 지운다. 실기기 검증은 수정 빌드 설치 후 기록한다.

수정 빌드 재검증 중, 기존 피트니스 화면에 평균 84bpm과 심박 그래프가 뒤늦게 나타난 것을 확인했다. 앞선 즉시 조회에서 심박이 없었던 결과와 구분한다. Runary의 내보내기 상태는 여전히 권한 오류로 남아 있어 표시만으로 연결 성공을 판정하지 않는다. 추가 권한 필요 여부는 `getRequestStatusForAuthorization`으로 판단하도록 변경했다.


### 21:40 권한 허용 후 재검증 통과

사용자가 심박수 쓰기를 승인한 뒤 실제 권한을 적용했다. 권한 화면에서 기존 심박 읽기도 꺼진 채 반영돼 건강 설정에서 원래 허용한 읽기를 복원했다. 그 후 앱 재진입에서 기존 기록의 내보내기가 성공했다.

기존 운동 UUID `D6050DFA-94C0-4811-A904-E6398824241F`를 유지한 채 상태가 `saved`로 바뀌고 기존 심박 샘플 13개가 연결됐다. 이전 오류 코드는 제거됐다. Runary 화면에서도 “건강 앱에 저장됨”을 확인했다. 피트니스에는 앞선 29초 QA와 이번 72초 QA가 각각 한 건으로 유지됐다. 새 운동이나 심박 사본을 만들지 않았다.

Runary 평균은 81bpm, 피트니스의 표시 평균은 84bpm이었다. 표시 평균의 산식 일치는 이번 검증에서 확정하지 않았으며 같은 수치라고 보고하지 않는다. 심박 연결 및 기존 실패 기록 복구는 통과했다.

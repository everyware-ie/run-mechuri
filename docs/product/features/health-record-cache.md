# 건강 앱 기록 부가 정보 보관

- FRD: [Runary 기록으로 만들기](../../specs/frd/runary-record-editing.md) §목록(2026-10-28 개정, "건강 앱 기록의 부가 정보는 기기에 보관해 다시 조회하지 않는다")
- 근거 QA: [QA 기록](../../ops/qa-log.md) 2026-10-26 "새로 만들기에서 Runary 기록이 먼저 뜨고 건강 앱 기록이 뒤에 끼어들어 헷갈린다"(지응)
- 관련 규칙: [홈과 보관함 FRD](../../specs/frd/home-and-library.md) 건강 기록 정보는 기기 백업에서 제외, [Apple 심사 지침 5.1.3(ii)](https://developer.apple.com/app-store/review/guidelines/#health-and-health-research)
- 구현 상태: **FRD 개정안 확인 전.** 아직 코드를 고치지 않았다

## 왜 하나

기록 선택 화면은 Runary 기록(기기에 저장)과 건강 앱 기록(HealthKit) 두 출처를 합친다. 건강 앱 쪽이 한참 늦게 도착해서 Runary 기록이 먼저 몇 개 뜨고 나중에 사이사이에 끼어든다. 팀에서는 두 출처를 한꺼번에 보여주자는 의견, 느린 쪽을 기다리지 말자는 의견, 출처별 탭으로 나누자는 의견이 나왔다. 이 작업은 화면 구성과 상관없이 **건강 앱 쪽을 빠르게** 만든다. 탭이든 합친 목록이든 도움이 된다.

**느린 이유.** `HealthKitBridgeModule.swift`의 `getOutdoorRuns`가 모든 러닝 기록을 읽고(`HKObjectQueryNoLimit`), 기록마다 평균 심박과 경로 유무를 각각 조회한다. 기록 수 × 2번의 조회라서 기록이 쌓일수록 느려진다. 2026-09에 병렬로 바꿨지만 기록 수에 비례하는 구조는 그대로다.

## 정한 것 (사용자 확인 대기)

FRD의 새 규칙을 따른다.

| | |
|---|---|
| 목록 | 매번 건강 앱에서 새로 읽는다. 지운 기록은 바로 사라진다 |
| 보관하는 것 | 기록 ID별 평균 심박, 경로 유무. 좌표는 보관하지 않는다 |
| 24시간 이내에 끝난 기록 | 보관하지 않고 매번 조회한다(워치 동기화가 늦을 수 있다) |
| 백업 | 기기 백업에서 제외한다 |
| 실패 | 읽기·형식 오류면 버리고 예전처럼 조회한다 |
| 버전 | 계산 방식이 바뀌면 보관 정보를 버린다 |

## 구현 방향

- 위치: `frontend/modules/health-kit-bridge/ios/HealthKitBridgeModule.swift`. 부가 조회가 이 파일 안에 있어서 여기서 보관한다. JS 화면은 바꾸지 않는다
- 저장: Application Support 폴더의 파일 하나(JSON). 백업 제외 속성을 건다. 기록 수가 1,000건이어도 100KB 안팎일 것으로 추정한다(실측 아님)
- 흐름: 건강 앱 목록 조회 → 보관한 ID는 값을 그대로 쓰고 → 없는 ID와 24시간 이내 기록만 부가 조회 → 새로 조회한 값을 보관 → 목록에 없는 ID는 보관 정보에서 지운다
- 규칙(보관 여부 판단, 정리)은 따로 떼어 Swift 합성 검사로 테스트한다

## 확인할 것

1. 두 번째 진입부터 건강 앱 기록이 Runary 기록과 비슷하게 빨리 도착하는지(진입 시간 전후 비교)
2. 건강 앱에서 기록을 지우고 다시 들어갔을 때 사라지는지
3. 방금 끝낸 러닝(24시간 이내)이 심박·경로와 함께 정확히 나오는지
4. 처음 설치 직후(보관 정보 없음)에도 정상으로 나오는지
5. 보관 정보 파일을 지우거나 망가뜨려도 목록이 나오는지
6. 보관 정보가 기기 백업에서 제외되는지
7. 개인정보 처리방침의 건강 데이터 보관 설명과 어긋나지 않는지 `[확인 필요]`

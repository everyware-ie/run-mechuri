# 보관함 저장·삭제 순서 보장

- FRD: [홈과 보관함](../../specs/frd/home-and-library.md) §2 결과물 (`approved`)
- PRD: [러닝 경로 그림 MVP](../../specs/prd/running-drawing-mvp.md) §6 내보낸 다음
- 착수 확인: 2026-10-04 사용자가 안정성 후속 검증·수정을 계속하도록 요청했다. TestFlight 배포는 보류한다.

## 확인 범위

결과물 추가와 삭제가 같은 보관함 목록을 읽어 각각 덮어쓰는 구조를 점검한다. 호출한 순서대로 읽기·수정·저장을 마친 뒤 다음 요청을 처리해 새 결과물 유실과 삭제 항목 복원을 막는다. 한 작업 실패는 호출자에게 전달하되 다음 작업은 계속한다. 기존 저장 키와 형식, 정렬·옛 저장분의 기본값 보완은 유지한다.

## 구현과 검증

`frontend/src/lib/results-store.ts`의 목록 읽기·추가·삭제를 하나의 대기열에서 호출 순서대로 처리한다. 추가·삭제는 목록 읽기와 쓰기 전체를 한 작업으로 묶는다. 대기열 내부에서는 별도 읽기 함수를 사용해 자기 작업을 기다리는 교착을 피한다. 조회도 앞선 저장·삭제를 기다려 최신 목록을 읽는다.

결과물 추가는 요청 시점에 직렬화해 대기 중 입력 객체가 바뀌어도 요청한 편집값을 보존한다. 작업의 실패는 해당 호출자에게 반환하지만 대기열을 끊지 않아 이후 요청은 계속한다. 저장 공간 부족이나 앱 강제 종료까지 해결하는 것은 아니다. 이미 사라진 결과물을 복구하는 변경도 아니다.

- 수정 전 모의 저장소 검사에서 6개 실패를 재현했다: 동시 추가, 추가·삭제의 두 순서, 동시 삭제, 느린 저장 중 조회, 입력 객체 변경.
- 수정 후 저장소 검사 11개 통과. 위 사례 외에도 같은 항목 추가·삭제의 두 순서, 저장·조회 실패 뒤 다음 요청, 기존 키·정렬·옛 데이터 보완을 확인했다.
- 전체 테스트 166개(18개 묶음) 통과. 린트 오류 0개, 기존 경고 32개. 타입·문서 정합성 검사도 통과했다.
- 실제 iOS에서 저장 완료와 삭제가 겹친 것을 관측한 결과는 아니다. 앱 계층의 순서 보장을 모의 저장소로 확인했다. 네이티브 코드·패키지·저장 키·파일 형식은 바꾸지 않았다. 인코딩 자체를 병렬화하거나 느리게 만드는 작업도 아니다.

## 남은 실기기 확인

결과물 생성이 끝난 후 홈과 상세에 새 결과물이 나타나는지, 기존 결과물 삭제 후 목록에 다시 나타나지 않는지 확인한다. 다른 결과물의 재편집과 사진 배경 참조가 남는지도 확인한다. 앱 설치·실기기 영상 생성·TestFlight 배포는 수행하지 않는다.

## 어긋남 기록

제품 정책 변경은 없다. 기존 보관 원칙을 지키는 안정성 수정이다.

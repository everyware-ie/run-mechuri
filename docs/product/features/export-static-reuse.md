# 고정 요소 재사용 실험 보고서

2026-09-28 · 실험 완료, 이번 방식 미채택

근거: [내보내기·공유 FRD](../../specs/frd/export-and-share.md) §2-5 앱 전환·화면 잠금 중 인코딩, [경로 렌더링 FRD](../../specs/frd/route-rendering.md) §9 출력 규격. 사용자가 고정 요소 재사용 실험과 결과 보고서 작성을 승인했다.

## 범위와 비교 원칙

기존 출력 규격·내부 배율·폰트·그림자·색상·동적 숫자·진행 속도를 유지한다. 매 프레임 반복하는 희미한 전체 경로와 고정 문자열의 그림을 재사용한다. 영상 한 편 안에서만 캐시하고 작업 종료 시 해제한다. 문자열 캐시는 16MiB로 제한하고 넘는 항목은 기존 방식으로 그린다.

병렬 처리는 끈 상태에서 기존 직렬 방식과 비교한다. 동일 Release 바이너리·동일 합성 입력을 사용한다. 전체 360프레임과 프레임 시각을 비교하며, 픽셀 차이가 생기면 단순히 같은 해상도라는 이유로 동등 품질로 처리하지 않는다. 효과가 작거나 품질 유지 조건을 만족하지 못하면 제품 기본 경로에는 넣지 않는다.

## 실험 구현

[소스 생성 스크립트](../../../frontend/scripts/export-static-reuse-experiment.py)는 [병렬 실험 소스 생성기](../../../frontend/scripts/export-frame-parallel-experiment.py)가 만든 임시 모듈을 입력받는다. 같은 바이너리에서 실행 인자 `--static-reuse`만 추가해 기존 직렬 방식과 비교한다. `--parallel-frames`와 동시에 사용하면 실패 처리한다. 문자열 캐시는 단일 렌더 큐에서만 접근한다.

- 불빛 러너·구간 점등의 희미한 전체 경로를 배경과 한 번 합성한다. 기본 경로 그림에는 이 레이어가 없어 생략한다.
- 일반 문자열 그리기 함수에서 문구·날짜·장소·심박·라벨을 캐시한다. 글자 내용·폰트·크기·색상·위치·그림자 종류가 같을 때만 재사용한다. 큰 숫자와 단위를 따로 그리는 함수는 기존 방식을 유지한다.
- 글자별 그림은 원래 좌표의 소수점 위치를 유지하고 그림자 여백을 포함한다. 원래 순서대로 합성한다.
- 캐시 크기는 실제 이미지 행 바이트 수×높이로 계산하고 16MiB를 넘는 항목은 보관하지 않는다. 이 제한은 문자열 이미지에 대한 것이며 전체 프로세스 메모리 상한이 아니다.
- 측정 후 제품 모듈과 AppDelegate를 복원했다. 일반 앱 기본 렌더러에는 반영하지 않았다.

## 측정 조건

iPhone 11 Pro / iOS 26.6.2, 동일한 Release 바이너리, 전경·미러링 종료. 1,000점 합성 경로, 4032×3024 합성 JPEG, 불빛 러너·글래스·동적 숫자·한글 문구를 사용했다. 실제 GPS와 개인 사진은 사용하지 않았다.

프로세스를 다시 실행해 기존 직렬 1회 → 고정 요소 재사용 1회를 비교했다. 각 시작·종료 시 thermalState는 0(nominal), 저전력 모드는 꺼져 있었다. 네이티브 생성 시간이며 JS 요청 전달·보관함 등록은 제외한다. 내부 렌더 배율 3, 271프레임 그리기·360프레임 인코딩을 유지했다.

## 결과

| 항목 | 기존 직렬 | 고정 요소 재사용 |
|---|---:|---:|
| 네이티브 전체 | 44.1407초 | 45.3188초 |
| 프레임 그리기 | 31.051초 | 31.140초 |
| 복사·축소 | 11.968초 | 13.095초 |
| writer 대기 | 0.370초 | 0.370초 |
| 배경 준비 | 0.1776초 | 0.1991초 |
| 최대 resident | 336.8MiB | 427.2MiB |
| 종료 시 footprint | 136.8MiB | 212.3MiB |

이번 비교는 1.1781초(2.7%) 더 걸렸다. 반복 1쌍이므로 2.7% 자체를 확정적인 회귀 폭으로 보지는 않는다. 다만 단축 효과가 관찰되지 않았고 최대 resident는 90.4MiB(26.8%) 증가했다. 발열 상태가 동일했다는 사실만으로 모든 실행 조건이 완전히 같았다고 해석하지 않는다.

문자열 캐시는 13개 그림, 6,462,144바이트(약 6.16MiB)를 보관했고 2,155회 재사용했다. 캐시가 작동하지 않은 실험은 아니다. 재사용 횟수가 많아도 전체 생성이 빨라지는 것은 아니었다. 추가 이미지 보관·합성 비용이 절약분을 상쇄했을 가능성이 있지만, 세부 비용을 분리 측정하지 않아 정확한 원인으로 확정하지 않는다. 배경 중간 이미지의 수명도 메모리 증가를 줄일 후속 검토 항목이지만 이번 속도 결과만으로 최적화를 계속 확대하지 않는다.

### 영상 비교

[전체 프레임 비교 도구](../../../frontend/scripts/check-rendered-clips.swift)로 두 파일을 검사했다.

- 두 영상 모두 1080×1920·30fps·12초·360프레임이며 대응 프레임 시각이 일치했다.
- RGB 픽셀이 다른 프레임: **360/360**.
- 최대 채널 차이: **46/255**.
- 전체 RGB 채널의 평균 절대 차이: **0.0139649/255**.

평균 차이는 작지만 기존 출력과 픽셀 일치는 실패했다. 캐시 합성과 H.264 압축 영향을 분리하지 않았으므로 이 수치만으로 육안 품질 저하 정도를 단정하지 않는다. 동시에 품질이 동일하다고 선언하지도 않는다.

## 판단

**이번 고정 요소 비트맵 재사용 방식은 미채택한다.** 속도 이득이 관찰되지 않았고 메모리가 증가했으며 픽셀 일치도 만족하지 못했다. 사용자의 성과가 작으면 중단하라는 조건에 따라 반복 실험·병렬 결합·제품 적용을 확대하지 않는다. 고정 요소 재사용의 모든 구현이 효과 없다는 결론은 아니다.

현재 유지할 후보는 [두 프레임 병렬 생성](export-frame-parallel.md)이며 메모리·실제 앱·백그라운드 검증이 남는다. 추가 큰 폭 단축 후보는 CPU에서 고배율 이미지를 반복 생성하는 작업 자체를 줄이는 GPU 합성과 영상 버퍼 출력 구조다. 새 후보는 별도 실험으로 비교하며, 이번 결과를 10초 이내 달성 근거로 사용하지 않는다.

## 검증과 재현

- 실험용 Swift 코드의 iOS Release 빌드 성공. 일반 제품 소스에 실험 코드가 남지 않은 것을 확인했다.
- 문자열 재사용 단독 실기기 측정, 파일 규격·프레임 시각 검사 완료. 픽셀 일치 검사는 실패했으며 위에 수치로 기록했다.
- 타입 검사, 문서 링크·frontmatter 검사와 diff 공백 검사 통과. `eslint src/ modules/`는 오류 0개·기존 경고 21개다. 이전 `npm run lint`의 16개에 modules의 기존 경고 5개가 포함된 범위다.
- 실제 앱 UI와 동시 실행, 다른 프리셋·사진·경로, 취소·잠금·메모리 경고 검증은 미실행이다. 미채택하므로 제품 검증 범위로 확대하지 않았다.

재현 시 깨끗한 모듈 → 병렬 실험 생성기 → 고정 요소 생성기 순으로 임시 소스를 만든다. [측정 진입 절차](export-preparation.md)에 따라 로컬 빌드 후 소스를 복원한다. `--export-preparation-benchmark`만 주면 기존 방식, `--static-reuse`를 추가하면 이번 후보다. 각 실행 결과를 다음 실행 전에 회수한다.

원본 파일은 측정 Mac의 `/private/tmp/runary-static-control.log`, `/private/tmp/runary-static-trial.log`, `/private/tmp/runary-static-pixels.log`와 같은 접두어의 mp4다. 임시 경로이므로 위 조건과 표를 영구 기록으로 남긴다.

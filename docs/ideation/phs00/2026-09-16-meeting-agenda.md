## 1. 심사가 리젝되면 어떻게 할까 (10분)

**리젝되면 시계가 두 번 돈다.** 고치는 시간 + 재심사 시간. 엿새 안에 두 번이 들어가면 9/22가 흔들린다.

### 무엇을 정하나

| | |
|---|---|
| **누가 심사 상태를 보나** | 결과 메일은 계정 주인에게 간다. **보는 사람과 알리는 사람을 정해둔다** |
| **리젝 사유별로 누가 손대나** | 문서 문제면 phs00, 앱 동작이면 개발. 사유를 보고 정하면 반나절이 날아간다 |
| **어디까지 기다렸다 손절하나** | 9/19(금)까지 안 나오면 어떻게 할지 |

PRD §1에서 **9/22 출시를 "TestFlight 공개 링크"로 정의**했다. 못 열면 그 정의를 건드리는 것이라 팀이 정해야 한다.

## 3. 어디까지 외부에 보여줄까 (10분)

**외부 테스터는 받지 않기로 했다.** 그래서 남는 질문은 하나다. **만든 것을 어디까지 내보일 것인가.**

### 둘은 다른 이야기다

| | |
|---|---|
| **결과물만 보여준다** | 클립을 스레드나 인스타에 올린다. 반응을 본다. **앱 링크는 주지 않는다** |
| **앱을 쓰게 한다** | 링크를 받은 사람이 설치해서 직접 만든다 |

**앞의 것만으로도 볼 수 있는 것이 있다.** PRD §5가 이번에 검증하겠다고 한 것은 "직접 측정하지 않더라도 **공유를 목적으로 예쁜 드로잉 결과물을 얻고 싶어하는 니즈**가 있는지"다. **결과물을 보고 "나도 해보고 싶다"가 나오는지가 그 답이다.** 앱을 쥐여주지 않아도 나온다.

### 정할 것

| | |
|---|---|
| **어디까지 올릴까** | 스레드 팀 계정, 각자 인스타 스토리, 러닝 커뮤니티 |
| **"나도 써보고 싶다"가 나오면 어떻게 할까** | **이게 진짜 질문이다.** 안 준다 / 아는 사람까지는 준다 / 그때 다시 정한다 |
| **누가 올리나** | 각자 알아서인지, 팀 계정으로 모으는지 |

### 출시 정의를 다시 봐야 한다

PRD §1은 **9/22 출시를 "TestFlight 공개 링크 공개"로 정의**했다. 외부 테스터를 안 받으면 그 정의와 어긋난다.

| | |
|---|---|
| **열되 뿌리지 않는다** | 링크는 살아 있고 우리가 안 퍼뜨린다. **정의는 유지된다** |
| **아예 안 연다** | 9/22에 무엇을 출시라고 부를지 다시 정해야 한다 |

**앞쪽이면 §1의 마지막 질문과 이어진다.** 심사를 통과시켜 두는 것 자체가 "9/22에 배포할 수단을 확보한다"는 원래 목적이었다.

## 5. QA에서 정할 것 (남는 시간)

**출시를 막는 것은 없다.** 다만 쌓아두면 다음 라운드가 무거워진다.

**시간이 모자라면 5-1만 보고 나머지는 넘긴다.** 5-1은 지응의 한 마디로 갈린다.

### 5-1. 장소 각인이 네 프리셋에서 안 나온다

> 지응 9/14: "코너, 레일, 스탯바, 원라인은 장소를 클릭해도 표출이 안 됨. **장소만 넣는다고 되어 있을 때 아예 표출이 안 되네**"

| 프리셋 | 장소 |
|---|---|
| 스택 · 글래스 · 간결 | **나온다** |
| 코너 · 레일 · 스탯바 · 원라인 | **안 나온다** |

코드를 봤다. 안 나오는 넷은 그릴 항목을 직접 적어 두었고 거기 장소가 없다.

**9/2에 시안 여섯 종을 옮길 때 날짜는 여섯 다 넣고 장소만 하나도 안 넣었다.** 장소는 그때 이미 코드에 있었다. 없어서 못 넣은 게 아니다.

**먼저 물을 것: 지응, 의도였나 빠뜨린 것인가.**

| | 답이 이거라면 | 무엇을 하나 | FRD |
|---|---|---|---|
| **A** | "빠뜨렸다" | 빠진 넷에 **장소를 넣는다.** 날짜 자리 옆에 붙이면 된다 | 그대로 |
| **B** | "의도적으로 뺐다" | **프리셋마다 구성이 다른 것을 인정하고**, 그 프리셋에 들어 있는 항목 중에서만 고르게 한다 | **두 곳 개정** |

B는 [경로 렌더링 §6 프리셋이 정하는 것은 자리뿐이다](../../specs/frd/route-rendering.md)와 반대 방향이다. 바꾸는 것 자체는 문제가 아니고, 회의에서 정하고 문서를 함께 고치면 된다.

### 5-2. 각인을 만질 수 있다는 걸 어떻게 알릴까

> 지민 9/8: "각인을 누르면 바꿀 수 있구나. **몰랐어**"
> 지민 9/12: "각인 버튼이 보여서 움직일 수 있을 것 같은데 실제로는 안 돼서, **아예 각인을 숨기는 건 별론가?**"

**기능이 없는 게 아니라 되는 줄 모른다.**

| 누가 | 의견 |
|---|---|
| 지민 | 드로잉 단계에선 각인을 감추고 **각인 탭에 들어가야 보이게** 하자 |
| 현수 | 각인도 움직일 수 있다. 크기·위치 다 된다 |
| phs00 | **완성된 모습을 먼저 볼 수 있어야 한다.** 배경 선택에선 각인을 포함해 보여주고, 편집에 들어간 뒤로는 각인 탭에서만 |

**먼저 확인할 것이 있다.** 화면의 각인을 직접 눌러 고르는 기능이 **9/11 PR #51에 들어갔다.** 지민이 9/12에 말한 것이 그 빌드에서였는지 그 전이었는지에 따라 논의가 달라진다. **이미 되고 있다면 감출 이유가 없다.**

**감추면 문제가 옮겨간다.** FRD는 "상단 완료는 어느 단계에서도 사용할 수 있다"고 정했다. 드로잉만 만지고 완료하면 **각인을 한 번도 못 본 채 결과물이 나온다.**

| | 지금 | 감추면 |
|---|---|---|
| 사용자가 겪는 것 | 보이는데 안 만져진다 | **모르던 게 나왔다** |

### 5-3. 제스처 안내가 눈에 안 들어온다

> 지민 9/12: "설명 눈에 안 보여서 첨 보는 사람은 인지하기 어려울 듯. **프레임 위에 보이게 하는 건 어때**"
> 현수 9/12: "난 **위에 있으면 더 안 보일 거 같긴 한데**"

**의견이 갈렸다.** 지금 구현은 FRD대로(도구 내용 안)이고, 올리려면 FRD를 함께 고친다.

### 5-4. 간결 프리셋을 뺄까

> 지응 9/14: "간결은 빼도 되지 않을까. **원라인이랑 비슷한 거 같아서**"
> 지민 9/12: "간결은 개인적으로 구려서.. 첫 순서로 보이기엔 아쉬움"

**둘 다 낮게 보는데 빼자고까지 말한 건 지응뿐이다.** 일곱이 다 필요한지 본다.

### 5-5. 화면에 쓰는 말

**둘이 따로 같은 이야기를 했다.**

| 어디 | 지금 | 제안 | 누가 |
|---|---|---|---|
| 각인 안의 탭 | 넣을 것 | **러닝 데이터** | 지응 9/14 |
| 단계 탭 | 드로잉 | **경로 꾸미기** | 지민 9/14 |
| 미리보기 버튼 | 스토리 영역 | **인스타라고 말하는 편이 낫다** | 지민 9/12 |

**"각인"을 바꾸자고 한 사람은 없다.** 그런데 드로잉과 각인은 나란한 단계 탭이라, 드로잉만 바꾸면 한쪽은 사용자의 말이고 한쪽은 우리 말이 된다. **각인을 어떻게 할지도 함께 정해야 한다.**

세 번째 건에는 문서와 구현이 갈라진 흔적이 있다.

> 지응 9/14: "frd에 그렇게 되어 있었는데 내가 인스타 스토리 영역으로 바꿔놨었는데 다시 수정됐나 봄"

**낱개로 바꾸면 또 갈라진다. 한 번에 본다.**

### 5-6. 목록이 비었을 때 무엇을 말할까

**경로가 없는 기록을 목록에서 빼기로 했다**(phs00 결정). 실기기에서 고를 수 있는 것과 없는 것이 하나 걸러 하나씩 차 있었고, 진짜로 뛴 기록이 막혀 있고 0.1km 찌꺼기가 열려 있는 날도 있었다.

**그래서 목록이 비는 경우가 하나 늘어난다.**

| 경우 | 앱이 아는가 |
|---|---|
| 권한 거부 | **모른다.** iOS가 읽기 거부를 안 알려준다 |
| 기록이 정말 없다 | **모른다** |
| 기록은 있는데 전부 좌표가 없어 걸러졌다 | **안다** |

**앞의 둘은 한 화면이 같이 감당하고 세 번째만 따로 말할 수 있다.** 세 번째 문구를 정한다.

> **그릴 수 있는 기록이 없어요**
> 러닝 기록 **4개**를 찾았지만 경로 좌표가 저장돼 있지 않아 그림을 만들 수 없어요.
> 실외 달리기로 기록하면 경로가 함께 저장됩니다.

**찾은 개수를 보여주는 것이 핵심이다.** 없으면 "기록이 없다"로 읽혀서 사용자가 앱을 의심한다.

### 5-7. 팀 작업 규칙을 이대로 쓸지

**카톡에서 정하고 레포에 안 적힌 것이 넷 있었다.** 문체(8/24), 조사 문서의 출처(8/25), 회의 운영(8/20), 애플 계정 구조(8/22).

더 큰 문제가 있었다. **`CLAUDE.md`는 Claude만 읽는다.** codex 같은 다른 도구는 `AGENTS.md`를 찾는데 그 파일이 없었다. **그 도구로 작업하면 FRD 규칙도 문서 정합성 규칙도 아무것도 안 걸린다.**

그래서 만들어 뒀다. **마음에 안 들면 버려도 된다.**

| 파일 | 무엇 |
|---|---|
| [AGENTS.md](../../../AGENTS.md) | **도구 무관 정본.** 작업 흐름과 규칙 |
| [.claude/conventions/writing.md](../../../.claude/conventions/writing.md) | 문체 규칙 |

**새로 만든 규칙은 없다.** 이미 합의됐거나 CLAUDE.md에 있던 것을 모아 도구를 안 가리게 옮겼다.

### 5-8. 코드 안정성 장치를 무엇부터 둘까

**개발하는 사람 판단이 필요하다.**

작동하는 장치가 셋인데 **전부 문서 쪽이다.** 구현 노트 없이 편집 못 하게, approved 아닌 FRD로 PR 못 만들게, 문서 정합성 깨지면 커밋 못 하게.

**코드가 도는지 확인하는 장치는 하나도 없다.**

| | |
|---|---|
| 테스트 파일 | **0개** |
| 테스트 도구 | **설치 안 됨** |
| CI | **없음** |
| 타입 체크 | npm script에도 없다. 외워서 쳐야 한다 |

**타입 에러가 있는 채로 머지해도 아무도 안 막는다.**

제안하는 순서다.

1. **CI 한 장** - `tsc --noEmit` + `eslint` + `check-docs.py`를 PR마다. **이미 있는 명령을 자동화하는 것뿐이다**
2. **npm script 정리** - 외워서 치는 명령은 결국 안 친다
3. **순수 로직 단위 테스트** - `frontend/src/lib/` 아래만. 회귀가 가장 잘 나고 테스트하기 쉽다

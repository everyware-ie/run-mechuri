## 왜 이 순서인가

제약 셋이 순서를 거의 강제한다.

1. **8/25까지 코어 루프 관통**이 마감선이다. 여기가 밀리면 9/1 베타 심사가 밀리고, **베타가 유일한 심사 관문**이라 9/22가 함께 흔들린다 (9/22 출시는 TestFlight 공개 링크로 정의됐다)
2. **스택이 없으면 아무도 코드를 못 쓴다.** 리서치 → 셋이 모여 결정 → 그 다음이 셋업이다. **리서치와 결정 사이에 텀이 생긴다**
3. **서버 작업이 없어 백엔드 2명이 둘 다 iOS를 한다.** 팀에 앱 경험자가 없어 학습 곡선이 일정 안에 들어온다

### 스택 리서치: 질문은 하나, 리서치는 둘

**질문은 하나다. RN이냐 Swift냐.** 각도를 나누지 않고 **둘 다 같은 질문을 본다.**

이유는 **아무도 두 스택에 충분한 경험이 없기 때문**이다. 한 사람의 판단에 걸면 근거가 아니라 베팅이 된다. 두 사람이 각자 [갱신된 PRD](../../specs/prd/running-drawing-mvp.md)를 근거로 독립적으로 결론을 내고, **갈리는 지점이 나오면 거기가 진짜 쟁점**이다. 같은 결론이면 그대로 확정하면 된다.

산출물은 각자 `docs/ideation/<닉네임>/`에 노트 하나. **회의 전에 서로 읽는다.**

#### 이미 확인된 것: 내보내기 경로는 스택을 가르지 않는다

`AVFoundation`은 **RN에서도 쓸 수 있다.** 네이티브 모듈로 감싸 브릿지로 호출하는 구조이고, JiEung2가 08-16에 이미 그 구조를 제안했다("UI는 React/웹뷰, 영상 뽑는 요청만 네이티브로"). HealthKit과 인스타 공유 API(`UIPasteboard` + URL scheme)도 마찬가지로 네이티브 코드가 필요하지만, RN이라고 막히는 것이 아니라 **브릿지를 거칠 뿐이다.**

**그래서 "무엇을 할 수 있나"로는 갈리지 않는다.** 갈리는 것은 비용과 속도 쪽이다.

#### 같이 볼 만한 항목

리서치를 시작할 지점이지 정답 목록이 아니다.

| 항목 | 왜 |
|---|---|
| **학습 곡선** | 팀에 앱 경험자가 없다. AI 보조를 전제할 때 어느 쪽이 빨리 붙나. **5주 일정에서 가장 큰 변수** |
| **RN이면 결국 Swift도 쓰게 되는가** | 브릿지 네이티브 모듈을 직접 짜야 한다면 **두 스택을 다 배우는 상황**이 될 수 있다. Swift 단독이면 배울 것이 하나다 |
| UI 구현 속도 | 화면 5개 + 편집 슬라이더. 웹/React 생태계에 익숙하다면 RN이 유리할 수 있다 |
| 안드로이드 확장 | RN은 구조적 이점. Swift 단독은 "AI로 변환한다"가 전제인데 그 전제가 검증되지 않았다 |
| 빌드·배포 파이프라인 | TestFlight 제출까지의 복잡도. 9/1 베타가 걸려 있다 |
| 라이브러리와 레퍼런스 양 | AI 보조 개발이면 **학습 데이터가 많은 쪽이 실제로 빠르다** |

### 드로잉 기능 테스트에 붙는 조건

**합성 좌표가 아니라 실제 러닝 데이터로 한다.** [PRD §12](../../specs/prd/running-drawing-mvp.md)에 "실제 GPX가 목업만큼 예쁘지 않다"가 2주차 판정 리스크로 잡혀 있다. 렌더링 완성도가 "우와"의 유일한 레버이므로, 여기서 안 예쁘다는 게 드러나면 **스택보다 훨씬 큰 문제**다. 지금 알면 대응할 시간이 있다.

## 텀은 저절로 메워진다

리서치가 끝나고 결정이 나기까지 비는 구간이 생긴다. **각자의 두 번째 작업이 스택을 안 가리기 때문에 그 구간이 그대로 메워진다.** 따로 뭘 배치할 필요가 없다.

| 담당 | 텀에도 굴러가는 작업 | 왜 스택과 무관한가 |
|---|---|---|
| jminkkk | 디자인 요소 세팅 | 산출물이 **코드가 아니라 토큰·스펙·목업**이면 스택을 안 가린다. 결정 후 그대로 코드로 옮겨진다 |
| jminkkk | 계정 등록 | 승인 대기가 붙어 일찍 시작할수록 좋다 |
| JiEung2 | 드로잉 기능 테스트 (실제 데이터 샘플 확보 + 경로 다듬기 검증) | 순수 좌표 계산이라 언어를 안 가린다 |
| phs00 | FRD, 배경 이미지 선정 | 문서 작업 |

**조건은 하나. 디자인 세팅의 산출물이 코드가 아닐 것.** 스택이 안 정해졌으니 SwiftUI 컴포넌트는 못 만든다. 토큰과 스펙과 목업이어야 결정 후 버려지지 않는다.

### 디자인 시스템은 FRD를 다 기다리지 않는다

| 부분 | 필요한 선행 | 언제 |
|---|---|---|
| 기반 토큰 (색·타이포·간격·다크 모드) | 없음 | 지금 |
| 핵심 컴포넌트 (버튼·선택 카드·슬라이더·시트) | PRD §6 코어 루프면 충분 | 지금 |
| 화면별 상세 레이아웃 | FRD | FRD 나오는 대로 |

화면이 다섯뿐이다(기록 선택 → 배경 선택 → 프리셋 선택 → 미리보기·편집 → 공유). FRD가 더하는 것은 각 화면의 규칙과 수치이지 컴포넌트 목록이 아니다.

**다만 이 제품에서 디자인의 승부처는 UI 크롬이 아니라 렌더링 결과물이다.** PRD P2가 "렌더링 완성도가 우와를 만드는 유일한 레버"라고 못박았고, 사용자가 인스타에 올리는 것은 우리 UI가 아니라 그 클립이다. **디자인 시스템은 결과물을 방해하지 않을 만큼만 만들고**, 힘은 미리보기·편집 화면에 몰아주는 편이 낫다. 5주 일정에서 디자인 시스템 과투자가 가장 흔한 실패 경로다.

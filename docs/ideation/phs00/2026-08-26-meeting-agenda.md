## 1. 기술 스택 투표 (20분) — 가장 급하다

이것이 안 정해져서 아무도 코드를 못 쓴다.

### 무엇을 고르는가

"RN"이 순수 JS 앱을 뜻하지 않는다. HealthKit·AVFoundation·인스타 공유는 **어느 쪽을 골라도 Swift로 짠다.**

| | UI 5화면 + 편집 | 네이티브 API 3개 |
|---|---|---|
| RN 안 | RN / TypeScript | Swift 브릿지 |
| Swift 안 | Swift | Swift |

**갈리는 것은 UI 부분 하나**인데 그게 전체 작업량의 절반 이상이다.

### 지응님 결론: RN 우세 (개인 판단)

근거의 강약을 스스로 구분해 적었다.

| 근거 | 강도 |
|---|---|
| AI 보조 개발 속도가 RN이 빠르다 | **약함.** "방법론 불명확한 블로그 실측"이라고 본인이 명시 |
| 핫 리로드 개발 루프가 RN이 안정적이다 | **강함.** AI와 무관한 구조적 차이 |

### 새로 닫힌 것 둘

- **"RN이면 결국 Swift도 쓰게 되나"** → 예. 다만 브릿지가 **함수 3~4개**뿐이다
- **"RN은 성능이 불리하다"**(08-18 회의 관점) → **구 브릿지 아키텍처 기준일 가능성.** RN 0.76부터 New Architecture가 기본이고 0.82에서 구 아키텍처가 제거됐다. **08-18 결정문의 판단 근거 하나가 낡았을 수 있다**

### 실제 쟁점

지응님 노트의 마지막 문장이 핵심을 짚는다.

> 팀에 앱 경험자가 없는 상황에서 "언어·디버깅 모델을 하나로 통일"하는 것 자체의 인지 부하 절감 효과가 실제로는 두 속도 이득의 합보다 클 수도 있다.

**"속도가 빠른 쪽" vs "헷갈릴 일이 적은 쪽"** 의 선택이다.

**일정도 판단에 넣어야 한다.** 9/1 베타 제출이 걸려 있고 팀에 Xcode 경험자가 없다면 빌드·배포 난이도 항목의 가중치가 올라간다.

`[확인 필요]` **jminkkk 님의 리서치 노트가 아직 없다.** 두 사람이 독립적으로 보고 갈리는 지점을 찾자는 방식이었는데 한쪽만 있다.

`[확인 필요]` **팀의 React 경험 수준.** UI 구현 속도 판단이 여기 걸린다.

## 2. 범위: 3탭 구조로 갈 것인가 (10분)

지민님 디자인 시안 셋이 **모두 하단 탭 3개**로 그려져 있다.

> 보관함 · 달리기 · 발견

우리 FRD에는 탭이 없다. **홈 하나에 선형 루프**다. 이건 시각 선택이 아니라 정보 구조 선택이고, 디자인 시스템 몫이 아니다.

**두 구조는 서로를 요구한다.** 탭이 셋이려면 "달리기"(자체 측정)와 "발견"이 있어야 하고, 우리 범위대로 그 둘을 빼면 남는 탭이 보관함 하나라 **탭 자체가 필요 없어진다.**

| 시안에 있는 것 | 우리 문서 |
|---|---|
| 달리기 (자체 GPS 수집) | **PRD §5 제외 목록** |
| 발견 | 문서에 없음. 로드맵에도 없음 |
| 배경 선택 화면 | **없음** (시안 셋 다) |
| 러닝 기록 선택 화면 | **없음** (시안 셋 다) |

**"탭을 쓸까"가 아니라 "범위를 넓힐까"의 질문이다.** 넓히면 PRD를 고쳐야 하고 5주 일정이 흔들린다.

## 3. 디자인 컨셉 (15분)

지민님이 세 방향을 뽑았다.

| 시안 | 성격 |
|---|---|
| **1a 야간 네온** | 어두운 캔버스, 경로가 빛으로 그려진다. 코랄 글로우 |
| **1b 종이 갤러리** | 흰 종이에 잉크 드로잉. 여백 위주, Instrument Serif |
| **1c 리소 포스터** | 2색 인쇄 포스터. 오렌지·블루 듀오톤, 큰 타입 |

### 판단 기준 하나를 제안한다

우리 결과물은 **사진 배경 위에 경로가 얹힌 9:16 클립**이다. 그런데 세 시안은 배경을 디자인 요소로 쓴다.

| 시안 | 사진 배경 위에서 성립하나 |
|---|---|
| 1a | **성립한다.** 어두운 배경 위 발광은 사진 위에서도 산다 |
| 1b | **어렵다.** 종이 질감이 곧 배경이라 사진이 들어갈 자리가 없다 |
| 1c | **어렵다.** 듀오톤이 배경을 덮는다 |

1b는 출력이 **PRINT · 4:5**로 되어 있다. 인스타 피드 비율이고 우리는 스토리 9:16이다.

**1b·1c가 안 예쁘다는 뜻이 아니다.** 완성도는 오히려 높다. 다만 **그 아름다움이 배경을 비워야 성립**하는데 우리는 사용자 사진을 배경에 깔기로 했다.

**컨셉만 정하고 고도화는 이후에 한다.** 다만 배경 개념과의 관계는 지금 확인해야 한다. 1b·1c로 가려면 배경 결정을 다시 봐야 한다.

### 시안에서 가져올 만한 것 둘

- **결과물 이름** (1b): "한강 고리, 8월의 저녁", "성수 격자". 지금 목록은 날짜·거리·프리셋뿐이다. 이름이 붙으면 찾기 쉽고 애착이 생긴다
- **슬라이더 단위 표기** (1b): 직선 다듬기 40%, **코너 반경 16m**. 코너를 미터로 보여주면 R2("이 그림을 보고 같은 길을 다시 뛸 수 있는가")와 직접 연결된다

|---|---|

**좌표가 없으면 GPX가 "여유 시"에서 "필수"로 격상된다.**

같이 볼 것: **실내 러닝 기록이 있는지.** 있으면 빈 상태 문구 판단에 쓴다.

**팀 3명이 모두 아이폰을 쓰는지도** 확인한다. 아니면 W5 실사용이 성립하지 않는다.

### 6-2. "예쁘다"의 기준

지응님이 **실제 GPX로 보는 테스트 도구**를 만들었다. 각자 뽑아온 GPX를 넣고 셋이 같은 화면을 보며 정한다.

- 잠정 기준은 **B~C 수준**이다(A 원본 / B 가벼운 정리 / C 양식화)
- **수치에 얽매이지 않는다.** 드로잉 담당이 시도하며 바뀔 수 있다. 출발점이지 통과 기준이 아니다
- **왕복 분리**(겹친 구간을 두 줄로 벌리기)를 실제 왕복 코스로 켜보고 판단한다. 지금은 MVP 제외다
- **실제 템포 vs 일정 속도**를 비교한다. 우리 FRD는 일정 속도가 전제인데, 도구에 실제 템포 토글이 있다(경로 렌더링 §5-4의 열린 질문)

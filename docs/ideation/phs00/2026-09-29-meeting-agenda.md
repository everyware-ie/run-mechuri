## 1. 열고 나서 무엇을 봤나 (15분)

### 무엇을 확인하려던 것이었나

PRD §5 검증 항목이 이번 라운드에서 확인하려는 것이다.

> 직접 측정하지 않더라도 **공유를 목적으로 예쁜 드로잉 결과물을 얻고 싶어하는 니즈**가 있는지

**결과물을 본 사람이 "나도 해보고 싶다"고 하는지가 답이다.**

### 가져올 것

한 주 동안 무엇이 있었는지 각자 들고 온다.

| | 어디서 보나 |
|---|---|
| **설치 수, 사용 횟수, 크래시** | App Store Connect의 TestFlight 탭. 계정이 지민 것이라 **지민이 캡처해 오면 가장 빠르다** |
| **인스타에 올린 반응** | 각자 올린 스토리의 조회, 답장, "이거 뭐야" 류의 DM |
| **지인 반응** | 영업한 사람이 깔았는지, 써봤는지, 뭐라고 했는지 |

**숫자가 작아도 괜찮다.** 몇 명이 깔았는지보다 **깐 사람이 결과물을 만들어서 어디에 올렸는지**가 이번 검증에 더 가깝다.

### 정할 것

**반응을 어디에 모을까.** 9/22에 안건으로 올렸는데 논의가 이어지지 않았다. 카톡에서 흘러가면 다음 회의 때 기억에 의존하게 된다.

| | 장점 | 단점 |
|---|---|---|
| **A. QA 기록에 "반응" 절을 둔다** | 이미 쓰고 있는 문서라 새로 만들 것이 없다 | 버그와 반응이 한 문서에 섞인다 |
| **B. 노션에 반응 페이지를 따로 둔다** | 셋 다 편하게 붙여 넣을 수 있다 | 레포 밖이라 문서 흐름에서 빠진다 |

**스레드에 무엇을 올릴까.** 지난주 숙제였다. 세 번째 글 자리가 계속 비어 있다.

## 2. 결과물 생성이 느리다 (15분)

결과물을 만드는 데 **40초대**가 걸린다. 쓰면서 길다는 말이 나와서 현수가 codex로 개선안 네 가지를 먼저 실험해 봤다. **자세한 것은 [실험 정리](2026-09-28-meeting-agenda.md)와 [결과 보고서](../../topics/2026-09-28-export-performance-results.md)에 있다.**

### 해본 것

| 방법 | 결과 |
|---|---|
| 편집하는 동안 재료를 미리 준비 | 준비에 드는 시간이 0.2초도 안 돼서 **효과가 없었다** |
| **두 장면을 동시에 그리기** | **43초 → 30초.** 영상은 똑같이 나왔다. **대신 메모리를 약 145MiB 더 쓴다** |
| 매번 같은 배경·글자를 한 번만 그리기 | 44초 → 45초. **빨라지지 않았다** |
| 크기 줄이는 일을 GPU에 맡기기 | 43초 → 50초. **오히려 느려졌다** |

**효과가 있던 것은 하나다.** 아직 앱에 넣지 않았다.

### 먼저 짚을 것: 화면을 끄면 3~4분이다

**이번 실험은 전부 화면을 켜 두고 기다린 경우다.** 그런데 9/13 기록에는 **화면을 잠갔을 때 약 224초**가 걸린 적이 있다. 입력이 달라 직접 비교는 못 하지만, 자릿수가 다르다.

**40초를 30초로 줄이는 것과 3분을 줄이는 것은 다른 문제다.** 사용자가 결과물을 만들어 놓고 폰을 내려놓는다면 이번 개선은 거의 느껴지지 않는다.

그래서 먼저 물어야 한다. **우리가 실제로 기다린 건 어느 쪽이었나.** 화면을 보면서 40초를 기다렸나, 폰을 내려놨다가 한참 뒤에 확인했나.

### 선택지

| | 무엇을 하나 | 얻는 것과 부담 |
|---|---|---|
| **A. 동시 그리기를 앱에 넣을 수 있는지 검증** | 실제 편집 화면이 켜진 상태의 메모리, 여러 입력, 취소·앱 전환·잠금 확인 | 약 30% 단축 가능성. 메모리가 모자라 앱이 꺼질 위험을 먼저 확인해야 한다 |
| **B. 더 크게 줄이는 구조 실험** | 경로와 빛을 처음부터 GPU로 그리거나 중간 이미지 복사를 줄인다 | 얼마나 줄지는 모른다. 구현 비용이 크고 화면 잠금 시 GPU 제약도 봐야 한다 |
| **C. 기다리는 느낌을 줄인다** | 정지 이미지를 먼저 보여주고 영상은 뒤에서 완성한다 | 실제 시간은 그대로지만 **공유는 먼저 할 수 있다.** PRD §12의 폴백으로 이미 적혀 있던 안이다 |
| **D. 잠시 멈춘다** | 지금대로 두고 실사용 대기 시간만 모은다 | 개발 시간을 아낀다. 느린 것은 그대로다 |

**A와 C는 같이 할 수 있다.** A는 실제 시간을, C는 기다리는 느낌을 줄인다.

### 누가 하나

**성능 개선 리서치는 [9/8에 지응·지민이 맡았다.](../../decisions/2026-09-08-scope-and-roles.md)** 이번 실험은 현수가 먼저 돌려 본 것이다. 이어서 누가 할지 정한다.

### 정할 것

- **무엇부터 하나** (A·B·C·D)
- **누가, 언제까지.** 실험에 쓸 시간 한도도 함께
- **목표를 무엇으로 잡나.** "화면 켜고 30초"인지 "잠갔을 때 1분"인지. 목표가 정해져야 언제 멈출지 안다

## 3. 흰 사진 위에서 글씨가 안 보인다 (10분)

9/22에 나온 QA다. **배경 사진이 밝으면 러닝 데이터 글씨가 묻힌다.** 테두리를 넣자는 제안이 함께 나왔다.

### 지금 어떻게 그리고 있나

**고를 수 있는 프리셋 전부가 옅은 검정 그림자 하나만 쓴다.** 투명도 55%, 흐림 6이다. 어두운 사진에서는 충분하지만 흰 사진에서는 글씨 주변에 희미한 얼룩이 생기는 정도라 **글씨를 사진에서 떼어 내지 못한다.**

### 이미 한 번 겪은 일이 있다

**9/2에 진한 처리를 뺀 적이 있다.** "안쪽만 빛나고 겉은 새까맣게 되어 구리다"는 실기기 피드백 때문이었다. 테두리를 진하게 넣으면 그때 문제가 돌아올 수 있다.

**그래서 이 건은 취향과 가독성 사이의 판단이다.**

### 선택지

| | 어떻게 보이나 | 부담 |
|---|---|---|
| **A. 그림자를 조금 진하게** | 지금 모양 그대로, 글씨 주변만 어두워진다 | 흰 사진에서 충분할지 모른다. 너무 올리면 9/2 문제가 돌아온다 |
| **B. 얇은 외곽선** | 글씨 테두리가 또렷하게 선다. 스티커 같은 인상 | 가장 확실하게 읽힌다. **모양이 달라진다** |
| **C. 사진 밝기를 보고 자동으로** | 밝은 사진에서만 진해진다 | 사진 한 장 안에도 밝은 데와 어두운 데가 섞여 있어 **"밝은 사진"을 하나로 판단하기 어렵다** |

**C는 권하기 어렵다.** 러닝 데이터가 놓인 자리만 밝을 수도 있고, 사진 전체 평균은 어두운데 글씨 밑만 하얀 경우를 못 잡는다.

**A를 먼저 시도하고, 부족하면 B로 가는 것**이 가장 덜 흔들린다. 모양을 바꾸지 않고 해결되면 그게 제일 낫다.

### 같이 볼 것

**코너 프리셋에서 날짜 위치가 애매하다**는 제보도 9/22에 있었다. `[확인 필요]` **어떻게 애매한지가 기록에 없다.** 제보한 사람이 화면을 보여주면 고칠 방향이 나온다.

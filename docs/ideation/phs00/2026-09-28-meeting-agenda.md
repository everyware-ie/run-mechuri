# 다음 회의 안건 후보: 결과물 생성 시간을 얼마나 줄일 것인가

2026-09-28 작성 · phs00 · 회의 날짜 미정 · 팀 결정 전

## 회의 전에 읽을 요약

결과물을 만드는 시간이 길다는 실사용 의견으로 네 가지 개선 후보를 실험했다. **효과가 확인된 것은 두 장면을 동시에 만드는 방식 하나다. 약 43초에서 30초로 줄었지만 메모리를 더 쓴다.** 아직 일반 앱에 적용하거나 TestFlight로 배포하지 않았다. 이번 PR의 머지는 실험 기록 공유이며 개선 기능의 채택이나 배포를 뜻하지 않는다.

아이폰 한 대에서 합성 입력으로 측정했다. 실제 사용자가 누르는 순간부터 저장 완료까지의 시간과 화면 잠금 상태는 이번 비교에 포함하지 않았다. “모든 아이폰에서 30초”, “백그라운드도 30% 개선”, “10초 이내 가능”으로 안내하면 안 된다.

전체 수치와 한계는 [결과 보고서](../../topics/2026-09-28-export-performance-results.md)에 있다. 이 안건은 다음 회의 전체 안건을 대체하지 않는 제안이다.

## 무엇을 해봤나 (5분 공유)

| 방법 | 쉽게 말하면 | 결과와 판단 |
|---|---|---|
| 편집 중 사전 준비 | 사진과 경로 재료를 먼저 준비 | 준비 자체가 약 0.1~0.2초라 이번 목표에는 효과가 작아 중단 |
| 두 프레임 병렬 생성 | 영상에 들어갈 두 장면을 동시에 만듦 | 약 43초 → 30초. 비교 영상 픽셀 동일. 최대 메모리 약 145MiB 증가로 적용 보류 |
| 고정 요소 재사용 | 같은 배경·글자를 반복해서 그리지 않음 | 약 44초 → 45초. 이번 구현 미채택 |
| GPU 축소·변환 | 그린 이미지를 영상 크기로 줄이는 일을 GPU에 맡김 | 약 43초 → 50초. 이번 구현 미채택 |

효과가 없는 후보를 중단한 것이며, 모든 캐시나 GPU 방식이 무효라는 결론은 아니다. 경로 그림과 글로우를 처음부터 GPU에서 그리는 방식은 아직 실험하지 않았다.

## 회의에서 정할 것 (15분 논의)

| 선택지 | 다음 작업 | 얻을 수 있는 것과 부담 |
|---|---|---|
| A. 병렬 생성의 제품 적용 가능성부터 검증 | 실제 편집 화면이 켜진 상태의 메모리, 여러 입력, 취소·앱 전환·잠금을 확인 | 관찰된 약 30% 개선을 활용할 가능성. 메모리 부족 시 중단될 위험을 확인해야 함 |
| B. 더 큰 단축을 위한 구조 실험 우선 | 중간 이미지·버퍼 재사용 또는 GPU 직접 그리기 중 하나를 선정해 제한된 실험 | 추가 단축 가능성은 미확인. 구현 비용과 화질·백그라운드 호환성 검토가 큼 |
| C. 성능 실험을 잠시 보류 | 현재 동작을 유지하고 실사용 대기 시간을 수집 | 개발 시간을 아끼지만 대기 시간은 그대로 |

제안은 A를 먼저 검증하고, 더 큰 단축이 필요하면 B의 실험 범위를 정하는 것이다. 팀 합의가 아니며 담당자·기간도 정해지지 않았다.

회의가 끝날 때 다음을 남긴다.

- 우선 진행할 선택지와 담당자·실험 시간 한도.
- 목표 대기 시간과 측정 조건: 전경/앱 전환/잠금, 대상 기기와 입력.
- 품질·메모리·취소·복구의 채택 조건과 성과가 부족할 때의 중단 기준.

## 여러 개선을 함께 적용할 수 있나

가능하다. 예를 들어 중간 이미지 복사를 줄이는 개선과 두 프레임 병렬 생성은 조합 후보가 된다. 다만 같은 비용을 줄이는 방식은 효과가 겹치고 메모리 사용도 달라진다. 단독으로 효과를 확인한 뒤 조합 상태에서 다시 속도·화질·안정성을 측정해야 한다. **이번에는 조합을 측정하지 않았고, 단축률을 더할 수 없다.**

## 다음 안건 정리 시 이어받을 내용

Claude Code를 포함한 다음 문서 작성자는 이 항목을 **미결 안건 후보**로 참고한다. 회의 전 최신 결정·PR·배포 기록을 확인하고 이미 해결됐다면 중복 상정하지 않는다. 실험 완료, 제품 채택, TestFlight 배포를 구분한다. 회의에서 정해지면 기존 문서 흐름대로 회의 종합 → 결정문 → 필요한 PRD·FRD 및 구현 노트로 연결한다. 이 원문은 당시 제안으로 보존한다.

# mp4 내보내기 스파이크 테스트: 실시간 캡처 방식 실패, 오프라인 프레임 렌더링으로 전환 필요

*2026-08-16 · JiEung2 개인 조사+테스트 원문 · 1주차(8/12~8/18) 담당 항목 "렌더링+내보내기" 관련*

> 성격: 회의 전 개인 스파이크 테스트 원문. **결론은 JiEung2 개인 판단**이며, 방향 전환(오프라인 렌더링 채택) 여부는 화요일 회의에서 확정 필요. 배포형태(웹/네이티브) 결정과도 강하게 얽혀 있음.

## 배경

"내보내기가 지금 최대 리스크, 안 되면 제품 자체가 성립 안 됨"이 1주차 담당 지시였음. 시간 부족하면 내보내기부터 검증하라는 원칙에 따라, 크루 레이어/프리셋보다 먼저 mp4 내보내기 가능 여부를 실제 기기에서 테스트함.

## 테스트 방법

Canvas에 (1) 가짜 경로를 따라 이동하는 애니메이션(불빛 이동 연출), (2) 배경 영상 루프를 합성해서 그리고, `canvas.captureStream(30)` + `MediaRecorder`로 실시간 녹화해서 mp4/webm 파일이 실제로 나오는지 확인. 아이폰 사파리에서 로컬 서버로 서빙해서 실기기 테스트.

## 테스트 결과

1. **배경 영상 없이 단순 라인 애니메이션만 캡처 — 성공.**
2. **배경 영상을 `display:none`으로 숨긴 채 합성 — 검은 화면만 녹화됨.** 사파리(WebKit)가 `display:none` 상태의 `<video>`는 디코딩 파이프라인을 사실상 멈춰서, 재생 중이라는 상태값과 무관하게 캔버스에 그려지는 프레임이 빈 화면이었던 것으로 추정. `position:fixed`로 화면 밖에 배치하는 방식으로 수정 후 이 증상은 해결.
3. **수정 후에도 배경 영상 합성 시 0바이트 파일(재생 자체 불가) 발생.** `MediaRecorder`에 에러 핸들러가 없어 원인이 안 보였던 상태 — 에러 핸들러·`dataavailable` 바이트 로깅·강제 webm 전환 옵션을 추가해 재현 중.

## 결론 (개인 판단)

**"화면을 실시간으로 재생하면서 그걸 옆에서 녹화하는" 방식(`captureStream`+`MediaRecorder`) 자체가 구조적으로 불안정하다고 판단.** 배경 영상 디코딩 + 캔버스 합성 + mp4 실시간 인코딩을 한 기기에서 동시에 처리해야 해서, 부하가 걸리는 순간 인코딩 파이프라인이 죽는 것으로 보임(코드 버그라기보다 이 접근 자체의 한계). 크루 레이어가 늘어나면 부하가 더 커지므로 악화될 가능성이 높음.

**오프라인/프레임 단위 렌더링 방식으로 전환이 필요하다고 판단.** 실제 영상편집 툴(프리미어, CapCut 등)이 쓰는 방식 — 프레임을 하나씩 계산해서 인코더에 순서대로 밀어넣는 구조. 재생 속도와 무관해서, 한 프레임 계산이 오래 걸려도 결과물이 깨지지 않음. 두 가지 구현 경로:

- **웹 유지 시**: `WebCodecs API`(`VideoEncoder`+`VideoFrame`) + `mp4-muxer` 같은 muxing 라이브러리. Chrome 94+/Safari 16.4+ 지원. `MediaRecorder`보다 구현 코드가 늘어남(디코딩·컴포지팅·인코딩·무싱을 직접 구현).
- **네이티브 셸 채택 시**: `AVFoundation`(`AVMutableComposition` + `AVVideoCompositing` + `AVAssetExportSession`). CapCut·VLLO·InShot 등 실제 영상편집 앱이 쓰는 애플 정식 프레임워크로, WebCodecs보다 검증 사례가 많고 안정적일 것으로 판단. 아이폰 실기기 없이 Xcode 시뮬레이터에서 반복 테스트 가능하다는 것도 장점(하드웨어 의존 기능이 아님).

**개인 추천(팀 결정 아님)**: 이미 HealthKit·인스타 스토리 공유 때문에 네이티브 셸이 필요하다고 판단했던 흐름과 맞춰, 렌더링/내보내기도 AVFoundation으로 네이티브 셸에서 처리하는 쪽으로 가는 게 리스크가 낮아 보임. UI(크루 화면, 프리셋 선택 등)는 계속 React/웹뷰로 만들고, "이 데이터로 영상 뽑아줘" 요청만 네이티브로 넘기는 브릿지 구조.

## 부록: 인스타그램 스토리 직접 공유 — 가능함 (공식 API)

Meta의 "Sharing to Stories" API로 원클릭 스토리 공유 가능. `instagram-stories://share` URL scheme 호출 전에 `UIPasteboard`에 `com.instagram.sharedSticker.backgroundVideo` 키로 mp4 데이터를 담아두면, 인스타그램이 열리면서 그 영상이 스토리 배경으로 자동 삽입된 편집 화면이 뜸. 네이티브 API(`UIPasteboard`/`canOpenURL`)라 웹뷰 JS 단독으로는 불가 — 네이티브 셸 코드 필요(위 AVFoundation 브릿지에 자연스럽게 얹을 수 있음). 릴스(피드용)는 공식 원클릭 API가 없어 "카메라롤 저장 → 사용자가 직접 업로드"가 현실적 선.

## `[미결]` — 회의에서 확인할 질문

- AVFoundation 네이티브 셸 채택 시 배포형태가 사실상 "네이티브 앱(또는 최소 네이티브 셸)"로 좁혀짐 — 지민 님의 웹/앱/웹먼저→앱나중 검토 결과와 맞춰봐야 함.
- WebCodecs로 웹을 유지할지, AVFoundation으로 네이티브 셸을 갈지 — 두 경로 다 이번 주 안에 완전히 검증하긴 어려움. 회의에서 방향만 정하고, 다음 주에 더 깊게 스파이크하는 것으로 갈지 논의 필요.
- 0바이트 실패의 정확한 원인(에러 로그)은 아직 재현 확인 중 — 회의 전까지 로그 확보되면 이 노트에 후속 노트로 추가 예정.

실제 GPX로 다시 보는 경로 보정 수준

phs00의 보정 수준 비교 도구가 합성 좌표로 만든 것과 같은 보정 알고리즘(직선 다듬기·코너 반경 분리·겹침 벌리기)을 그대로 재사용하되, 코스를 합성 대신 내가 직접 불러온 GPX 파일로 바꿨다. §8 판정 축은 같다 — "이 그림을 보고 같은 길을 다시 뛸 수 있는가."

GPX 확보 방법. 애플 건강 앱은 개별 워크아웃 GPX 내보내기가 없다. 08-16 조사에서 실사용 검증한 서드파티 앱을 쓴다.
  1. 아이폰에 GPX Export(무료) 설치 → 건강 앱 권한 허용
  2. 실외 달리기 워크아웃 선택 → GPX로 내보내기 → 파일 앱에 저장
  3. 아래로 드래그하거나 눌러서 불러오기 (여러 개 한 번에 가능, 파일은 브라우저 밖으로 전송되지 않는다)
다양성이 핵심이다. 최소 세 유형을 챙긴다 — 닫힌 고리(공원 등), 왕복(강변 등), 직각 코너가 많은 도심. phs00 도구의 코스 세 종류와 대응시켜야 같은 기준으로 비교된다.

phs00 도구와 다른 점

  • "실제로 뛴 거리(정답)" 줄이 없다. 합성 좌표는 노이즈를 얹기 전 진짜 경로를 알지만, 실제 GPX는 기록된 좌표 자체가 유일한 원본이다. 대신 건강 앱이 보고한 공식 거리를 입력하면 참고용으로 나란히 보여준다.
  • 따라서 각 패널의 "원본 대비 이탈"은 기록된 원본(raw GPX) 대비이지 진짜 경로 대비가 아니다. 절대 왜곡량이 아니라 세 코스 유형 사이에서 상대적으로 얼마나 다듬어야 하는지를 보는 도구다.
  • 슬라이더 기본값(직선 55 / 코너 22m)은 phs00 도구의 출발점과 같게 맞췄다. 여기서 값을 바꿔보고, 실제 데이터에서도 버티는지 확인하는 게 이 도구의 목적이다.

무엇을 판정하나 (PRD §8과 동일 기준)

  • 실제로 지나가지 않은 길이 보이는가. 직선을 펴다가 없는 지름길이 생기면 안 된다.
  • 코너가 실제 길모퉁이만큼만 깎였는가. 직각 교차로가 둥글게 뭉개지면 "그 길"처럼 안 보인다.
  • 왕복 구간이 실제보다 심하게 겹치거나 뭉치는가. 합성 좌표보다 실제 GPS 노이즈가 더 클 수 있다 — 여기가 PRD §12 리스크("실제 GPX가 목업만큼 예쁘지 않다")의 실측 지점이다.

이 도구가 끝나면

셋이 합의한 슬라이더 값을 PRD §8의 "현재 제안값(팀 합의 대기)" 자리에 채운다. 좌표 수가 지나치게 적은 짧은 기록을 하나 넣어보면 기록 선택 FRD §5의 "그릴 수 있는 트랙의 하한"도 같이 감이 잡힌다.

불빛 속도 기준 — 다음 회의 안건 (2026-08-23 추가)

처음엔 점 인덱스로 진행을 계산했는데, 다듬기 후 점 밀도가 구간마다 달라져서(직선은 성기고 코너는 빽빽) 직선에서 순간이동하듯 끊기고 코너에서 부자연스럽게 느려지는 문제가 있었다. 거리(호 길이) 기준으로 바꿔서 고쳤다. 다듬기 강도와 무관하게 항상 일정한 속도로 보인다.

여기에 더해 "실제로 뛴 템포 그대로 보여줄지, 완전히 무관하게 일정 속도로만 갈지"를 사용자가 클릭 하나로 고를 수 있게 하면 어떤가라는 아이디어가 나왔다. 위 "불빛 속도 기준" 토글로 시험 구현해뒀다 — GPX에 시각 정보가 있으면 실제 템포를 눌러서 신호 대기 구간에서 빛도 잠깐 멈칫하는지 확인할 수 있다. route-rendering FRD §5-4에 열린 질문으로 남겨뒀다 — 팀 결정 아님.

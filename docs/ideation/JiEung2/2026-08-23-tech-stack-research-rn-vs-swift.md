## 결론 요약

**질문은 하나다. RN이냐 Swift냐.** 다만 "RN"을 고른다는 것이 "브릿지가 아예 없는 순수 JS 앱"을 뜻하진 않는다 — HealthKit·AVFoundation 영상 렌더링·인스타 공유는 네이티브 API라서 RN을 고르든 안 고르든 이 셋은 어차피 Swift로 짠다. 그래서 **"RN 안"의 정확한 정의는 "화면 UI는 RN, 네이티브 API가 강제하는 부분만 Swift 브릿지"**이고, **"Swift 안"은 "화면 UI부터 전부 Swift"**다. 두 안을 아래에서 정면으로 비교한다.

**개인 판단(팀 결정 아님): RN 안을 더 우세하게 본다.** 근거는 둘이다. ① 5주 일정에서 가장 큰 변수로 phs00이 지목한 "AI 보조를 전제할 때 어느 쪽이 빨리 붙나"에서 RN이 실측 기준 우세하다(다만 근거가 약하다 — 아래 "이 결론이 무너지는 조건" 참고). ② **AI와 무관하게 성립하는 더 단단한 근거로, RN의 핫 리로드 개발 루프가 SwiftUI Previews보다 안정적이라는 사실**이 있다 — 이건 특정 실측 보고 하나에 기대지 않는, 두 생태계의 잘 알려진 구조적 차이다. "네이티브를 어차피 배워야 한다"는 단점은 두 안 모두에 존재해서 차별점이 아니다. 근거는 아래 기준별 비교와 §New Architecture 절에.

## 옵션 A: React Native (+ 불가피한 Swift 네이티브 모듈 3개)

**UI 5화면 + 편집 슬라이더는 RN/TypeScript. HealthKit 읽기·AVFoundation 렌더링/내보내기·인스타 공유만 Swift 네이티브 모듈로 뺀다.** (08-16 mp4 스파이크 노트에서 이미 잡은 방향 — "UI는 React/웹뷰, 영상 뽑는 요청만 네이티브로" — 을 이번 리서치로 다시 확인한 것에 가깝다.)

### 장점

- **AI 보조 개발 속도.** 2026년 실측 비교에서 Claude Code 같은 도구는 RN/TypeScript 학습 데이터가 압도적으로 많아 모호한 프롬프트로도 첫 시도 완성도가 높다는 보고. UI 5화면+슬라이더가 전체 작업량의 절반 이상을 차지하는데, 이 부분에서 가장 크게 이득을 본다
- **개발 반복 속도(핫 리로드) — AI 보조와 별개로 성립하는 더 단단한 근거.** RN의 Fast Refresh는 코드를 저장하면 시뮬레이터를 다시 켜지 않고 즉시 반영된다. SwiftUI Previews도 비슷한 걸 지향하지만 **미리보기가 자주 stale해지거나 알 수 없는 이유로 크래시한다는 보고**가 있고, Previews 밖에서 실제 동작을 확인하려면 결국 풀 빌드+시뮬레이터 재기동이 필요하다. 5주 안에 화면 5개+슬라이더를 계속 눈으로 확인하며 만들어야 하는 이번 프로젝트에는 이 반복 주기 차이가 누적으로 크다
- **New Architecture(Fabric+TurboModules, RN 0.76+ 기본값)로 예전 "RN은 느리다" 평판이 상당 부분 해소됨.** 콜드 스타트 43%, 렌더링 39%, 메모리 20~30% 개선 보고
- **EAS 빌드/배포 파이프라인.** Xcode 인증서·프로비저닝을 CLI가 상당 부분 흡수해줘서, 팀에 Xcode 숙련자가 없어도 `eas build`로 진행 가능. TestFlight 내부 테스트는 업로드 후 10~15분 내 반영
- **네이티브 모듈 3개는 입출력이 좁은 API로 경계를 그을 수 있다.** "이 트랙+배경을 주면 mp4 경로를 콜백으로 받는다" 식이라 프레임 단위로 JS↔네이티브를 오가는 고빈도 통신이 아니다. "요청 한 번-완료 콜백 한 번" 구조라 브릿지가 리스크를 크게 늘리지 않는다
- **팀이 백엔드 출신이라 TypeScript 쪽 진입 장벽이 낮을 가능성.** `[확인 필요]` 실제로 Node/TS 백엔드 경험이 있는지는 회의에서 확인 필요하지만, 만약 그렇다면 RN의 문법 자체는 새로 배우는 비중이 작고 iOS SDK 개념(뷰 생명주기, Auto Layout/SwiftUI 선언형 문법, 앱 샌드박스 등)만 새로 배우면 된다. Swift 단독은 언어와 플랫폼 개념을 동시에 새로 배운다
- **안드로이드 확장 옵션이 공짜로 남는다.** 이번 MVP는 iOS 단독이라 결정 기준은 아니지만, 로드맵상 UI 코드 재사용 가능성이 열려 있다

### 단점

- **"하나만 배운다"는 착각이면 안 된다.** 네이티브 모듈 브릿지(TurboModule, codegen, `@objc` 노출)는 그 자체로 새 개념이고, 결국 RN 문법 + 브릿지 문법 + Swift/AVFoundation을 다 배우게 된다
- **디버깅이 두 세계로 나뉜다.** JS 쪽 에러와 네이티브 쪽 에러가 다른 도구·다른 로그 체계로 나온다. 스택트레이스가 브릿지 경계에서 끊긴다
- **New Architecture 자체가 팀의 첫 경험이라 세팅 난이도가 있다.** TurboModule 설정을 문서만 보고 처음부터 익혀야 한다
- **HealthKit 브릿지 라이브러리(`@kingstinct/react-native-healthkit`)에 대한 의존이 생긴다.** 렌더링·내보내기·인스타 공유는 어차피 직접 짜서 의존이 없지만, HealthKit 읽기는 서드파티 유지보수에 걸린다(다만 활발히 유지되는 라이브러리로 확인됨)
- **코드베이스가 두 언어로 영구히 나뉜다.** 장기적으로 유지보수 인지 부하가 생긴다

## 옵션 B: Swift 단독 (SwiftUI/UIKit 전체)

**화면 5개부터 HealthKit·렌더링·공유까지 전부 Swift 하나로 짠다.** 브릿지 계층 자체가 없다.

### 장점

- **언어·디버깅 모델이 하나로 통일된다.** 앱 경험이 없는 팀에게는 "배울 것의 종류"가 아니라 "배울 것의 개수"가 문제일 수 있는데, 그 개수를 최소화한다
- **브릿지 버그 클래스가 원천 제거된다.** JS↔네이티브 경계에서 나는 문제(직렬화, 타입 불일치, 콜백 타이밍)가 애초에 없다
- **Apple 최신 API에 항상 바로 접근한다.** 서드파티 브릿지 라이브러리의 업데이트를 기다릴 필요가 없다 — 이번 Xcode 26.6부터 Claude Agent가 Xcode에 내장되는 등 네이티브 쪽 AI 지원도 개선되는 중
- **Xcode의 네이티브 디버깅 툴(브레이크포인트, Instruments, 메모리 그래프)을 처음부터 온전히 쓴다**
- **성능 상한이 가장 높다.** 모든 게 네이티브라 브릿지 오버헤드가 없다

### 단점

- **AI 보조 개발 속도가 RN보다 느리다는 2026 실측 보고.** Swift/SwiftUI는 컴파일·런타임 루프에서 반복 실패가 잦다는 관찰. 화면 5개+슬라이더까지 전부 이 속도로 짜야 한다
- **"네이티브로 짜야 하는 면적"이 압도적으로 넓다.** 렌더링·내보내기·HealthKit·공유는 어차피 네이티브인데, 여기에 UI 전체가 더해진다 — 옵션 A라면 AI가 가장 잘 도와주는 부분(UI)에서 이득을 못 본다
- **빌드·배포를 팀이 Xcode로 직접 다뤄야 한다.** 인증서·프로비저닝 프로파일 설정에 EAS 같은 완충 장치가 없다. 첫 베타 제출(9/1)까지 시간이 촉박한 상황에서 실패 지점이 늘어날 수 있다
- **안드로이드 확장 시 재사용 코드가 사실상 없다.** 이번 MVP 범위 밖이라 지금 결정에 큰 영향은 아니지만, 로드맵 옵션이 소멸한다

## 기준별 검토 (위 표에서 다루지 않은 세부 사항)

`[확인 필요]` 팀(JiEung2·jminkkk) 둘 다 React 경험 수준이 어느 정도인지는 각자 판단이 다를 수 있어 회의에서 맞춰야 한다 — UI 구현 속도 항목에 영향.

### 빌드·배포 파이프라인 상세

- **RN(Expo/EAS 기준)**: `eas build` → 업로드 후 TestFlight 내부 테스트는 처리 10~15분 내 반영, 외부 테스트 그룹 공개는 Apple 승인까지 보통 몇 시간. 팀에 Xcode 숙련자가 없어도 CLI로 빌드·제출이 가능하다는 게 강점이다.
- **Swift 단독**: Xcode → Archive → App Store Connect 업로드. 표준 경로이고 자료도 많지만, **Xcode 자체의 인증서·프로비저닝 프로파일 설정을 팀이 직접 다뤄야 한다.**
- **네이티브 모듈이 있는 RN이라도 어차피 Xcode가 필요하다.** 다만 인증서·프로비저닝·빌드 트리거는 EAS가 상당 부분 흡수해준다.

**함의(개인 판단).** 9/1 첫 베타 제출이 걸려 있는 상황에서, 팀에 Xcode 경험자가 없다는 점을 고려하면 EAS 쪽이 실패 지점을 줄여준다.

#### EAS 무료 티어로 이번 일정을 감당할 수 있는가

**Free 플랜은 iOS·Android 합쳐 월 30빌드(각 15개)까지 무료다.** 빌드 하나당 45분 타임아웃이 걸리는데, 우리 프로젝트는 의존성이 단순해서(RN 표준 + 자체 네이티브 모듈 3개) 이 안에 들어올 가능성이 높다. 타임아웃을 넘기면 유료 플랜(Starter, 월 $19~) 전환이 필요하다.

**5주 동안 실기기 테스트·CI 빌드를 자주 돌리면 30개가 빠듯할 수 있다.** 특히 9/1 베타 제출 전까지 반복 제출·수정이 몰리면 여유가 크지 않다. 다만 **로컬 빌드(`eas build --local`)로 우회하면 무료 한도와 무관하게 빌드할 수 있다** — Xcode가 설치된 맥에서 직접 빌드하는 방식이라, 클라우드 큐를 안 쓸 뿐 EAS의 다른 이점(인증서 관리 등)은 그대로 못 쓴다.

**Swift 단독은 이 제약 자체가 없다.** Xcode 로컬 빌드는 빌드 횟수 제한이 없다(대신 팀이 인증서·프로비저닝을 직접 관리해야 하는 비용은 위에서 다룬 그대로다).

### 라이브러리와 레퍼런스 양 상세

- **HealthKit**: `@kingstinct/react-native-healthkit`가 활발히 유지되는 TS 지원 라이브러리로 존재(JiEung2 2026-08-16 조사에서 확인). `getWorkoutRoutes`로 경로 데이터 직접 접근 가능.
- **AVFoundation 오프라인 프레임 렌더링(배경 합성 + mp4 인코딩)**: **이 부분은 RN이든 Swift든 기존 라이브러리가 없다.** 우리 렌더링 방식(프리셋별 커스텀 오버레이 애니메이션)이 범용 라이브러리가 커버하는 영역 밖이라, 결국 `AVMutableComposition`/`AVAssetExportSession`을 직접 짜야 한다. **레퍼런스 유무는 이 기준에서는 스택을 안 가른다.**
- **인스타 스토리 공유**: 네이티브 API(`UIPasteboard`+URL scheme) 예제가 Swift 기준으로 많이 나와 있다(JiEung2 08-16 조사). RN 래퍼 라이브러리도 존재하나 커스텀 데이터를 다루려면 결국 얇은 네이티브 모듈을 직접 짜는 게 낫다.

### 네이티브 모듈 3개의 실제 규모 — 감으로만 말하지 않기 위해

"면적을 좁힌다"는 게 추상적이라, 각 모듈이 실제로 어떤 API 경계를 가질지 스케치해봤다. 요지는 **셋 다 JS 쪽에서 부르는 함수가 1~2개뿐**이라는 것이다.

| 모듈 | JS에서 보이는 API (안) | Swift 쪽 작업량 |
|---|---|---|
| HealthKit 읽기 | `getRuns(): Promise<Run[]>` 하나 | 대부분 `@kingstinct/react-native-healthkit`가 이미 감싸줌. 우리가 짤 Swift 코드는 거의 없음 |
| AVFoundation 내보내기 | `renderClip(track, background, preset): Promise<string>` (mp4 경로 반환) + 진행률 이벤트 하나 | **가장 크다.** `AVMutableComposition`/`AVAssetExportSession` 기반 오프라인 프레임 렌더링을 직접 짜야 한다(§ 라이브러리 절 참고). 다만 이건 Swift 단독을 선택해도 똑같이 짜야 하는 양이라 옵션 간 차이가 아니다 |
| 인스타 공유 | `shareToStories(videoPath): Promise<void>` 하나 | `UIPasteboard` 세팅 + URL scheme 호출, 수십 줄 수준 |

**즉 RN↔Swift 경계에서 실제로 "새로 배워야 할 브릿지 문법"은 앞뒤로 3~4개의 얇은 함수 시그니처 정도지, 복잡한 양방향 프로토콜이 아니다.** TurboModule 코드젠은 이 함수들의 타입을 선언하는 스펙 파일(`NativeXxx.ts`) 하나를 각 모듈마다 만드는 정도의 반복 작업이라, 한 번 패턴을 익히면 세 번째부터는 거의 복붙 수준이 된다.

**이게 §"단점"의 "브릿지 자체가 새 개념"을 완전히 무효화하진 않는다.** 처음 한 번(HealthKit 모듈)은 TurboModule 설정 자체를 배우는 비용이 있다. 다만 그 이후 두 개(내보내기, 공유)는 반복이라 비용이 줄어든다는 뜻이다.

### New Architecture 관련 확인 사항 (2026 시점)

`[확인 필요]`였던 부분을 이번에 조사로 닫는다.

- RN의 New Architecture(Fabric + TurboModules + JSI)가 **0.76부터 기본값, 0.82부터 구 브릿지 아키텍처가 완전히 제거됐다.** 즉 지금 RN 프로젝트를 새로 시작하면 자동으로 New Architecture 위에서 시작하고, 네이티브 모듈은 TurboModule로 짜게 된다.
- 콜드 스타트 43%, 렌더링 속도 39%, 메모리 20~30% 개선이 보고되는 등 **성능·안정성이 2026년 기준으로는 "실험 단계"를 지나 프로덕션 레디로 보고된다.**
- **함의(개인 판단)**: "RN은 성능이 불리하다"는 논거(08-18 회의에서 나온 관점 중 하나)가 구 브릿지 아키텍처 기준의 이야기일 가능성이 있다. New Architecture 기준으로 다시 판단할 필요가 있다.

## 이 결론이 무너지는 조건

**"AI 보조 개발이 RN에서 실제로 더 빠르다"는 전제의 근거는 방법론 불명확한 블로그 실측이다(§출처).** 이 부분만 놓고 보면, 이 전제가 무너질 경우 결론의 절반이 무너진다.

**다만 결론이 이 전제 하나에만 기대는 건 아니다.** 핫 리로드 개발 루프 차이(위 §"개발 반복 속도")는 AI 도구 유무와 무관하게 성립하는 구조적 차이라 더 안정적인 근거다. 그래서 "AI 보조 속도" 주장이 흔들려도 RN 우위 결론 전체가 무너지진 않는다 — 다만 **우위의 폭은 줄어든다.**

그리고 팀에 앱 경험자가 없는 상황에서 "언어·디버깅 모델을 하나로 통일"하는 것 자체의 인지 부하 절감 효과가 실제로는 두 속도 이득의 합보다 클 수도 있다 — 이건 회의에서 두 사람이 각자 판단해볼 지점이다.

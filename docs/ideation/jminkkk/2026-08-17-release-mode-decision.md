## 결론 요약

1. **"출시"를 App Store 정식 등재로 정의하면 9/22는 리젝 1회까지만 버틴다.** 2회면 깨진다([08-17 노트 §5](2026-08-17-appstore-release-feasibility.md)).
2. **팀 목표에 배포 형태는 중립적이다.** 목표는 *"인스타 스토리에 올렸을 때 '우와' 1회 이상"* 이고, 이걸 만드는 건 회의록이 이미 지적한 대로 **렌더링 완성도**다. 앱스토어 등재가 "우와"를 만들지 않는다. → **배포 형태는 "어느 쪽이 렌더링에 시간을 더 남겨주는가"로 판단해야 한다.**
3. **웹 안은 GPX 업로드를 택할 때만 살아남고, 그때도 결정적 약점이 하나 있다** — 인스타 공유 API가 네이티브 전용이라 웹은 "다운로드 후 사용자가 직접 업로드"가 된다(§3-1). 제품의 마지막 한 걸음이 마찰이 된다.
4. **내 추천: iOS 네이티브로 만들고, 9/22의 "출시"를 TestFlight 공개 링크로 정의한다.** App Store 정식 등재는 **9/24(추석 시작) 목표로 분리**한다(§5). 9/22 출시 후 **9/29까지가 검증 기간**이고, 정식 등재는 그 안에서 추석 가족 영입(9/24~27)에 맞추면 된다.
5. **⚠️ 별개의 긴장 하나** — MVP 범위에 서버가 거의 필요 없다. 백엔드 2명 + 기획 1명 팀인데 **백엔드 작업이 사실상 없다**(§7). 이건 배포 형태와 무관하게 회의에서 짚어야 한다.

## 2. 먼저 — 배포 형태는 데이터 확보 방식에 종속된다

이 트랙 단독으로 결론 낼 수 없는 이유가 여기 있다. [08-11 노트 §6](2026-08-11-platform-tech-review.md)이 이미 정리했다:

> **"웹으로 가는 길은 GPX 업로드 경로에서만 살아남는다."** 직접 트래킹이든 HealthKit이든 네이티브가 필요하기 때문이다.

| 데이터 확보 방식 (JiEung2 트랙) | 웹 가능? | 배포 형태 결론 |
|---|---|---|
| **GPX 업로드** | ✅ 가능 | A·C·D 전부 열림 |
| **HealthKit 읽기** | ❌ 네이티브 전용 | **B·D만** |
| **직접 GPS 트래킹** | ❌ 백그라운드 위치가 웹에서 끊김 | **B·D만** |

**즉 조건부 결론은 이렇다:**

- **데이터 방식이 GPX 업로드로 정해지면** → 웹(A)이 후보가 된다. 단 §3-1의 약점을 감수해야 한다
- **HealthKit이나 직접 트래킹으로 정해지면** → **웹은 자동 탈락.** B와 D 중에서만 고른다
- **1주차에 데이터 방식이 안 정해지면** → **D를 택하면 결정을 미룰 수 있다.** 네이티브로 시작하면 세 방식 모두 열려 있기 때문이다

**함의(개인 판단).** 마지막 줄이 D의 숨은 장점이다. **웹으로 시작하면 데이터 방식을 GPX로 못박는 셈**이 되고, 나중에 HealthKit을 쓰고 싶어지면 전면 재작성이다. 반대로 네이티브로 시작하면 GPX 업로드도 그 안에서 된다. **되돌릴 수 없는 선택을 지금 하지 않는 쪽**이 D다.

## 3. 각 안의 MVP 규모

MVP 범위는 회의록 확정안을 그대로 쓴다 — ① 러닝 경로 데이터 확보 ② 영상 위 경로 오버레이 렌더링 ③ 인스타 스토리용 파일 내보내기.

### 3-1. A. 웹 — 마지막 한 걸음이 마찰이 된다

| 항목 | 규모 |
|---|---|
| 데이터 확보 | GPX 파일 업로드 UI. **가장 가벼움** |
| 렌더링 | Canvas/WebGL. JiEung2 목업이 이미 HTML이라 **연속성이 있다** ★ |
| mp4 내보내기 | `MediaRecorder` / `ffmpeg.wasm` / 서버 ffmpeg — JiEung2 트랙의 판정 대상 |
| 배포 | 정적 호스팅. **심사 0 · 계정 0 · $99 0** |
| 앱 학습 비용 | **없음** |

**결정적 약점 — 인스타 공유가 네이티브 API다.** [08-11 노트 §3](2026-08-11-platform-tech-review.md)이 확인한 스토리 공유는 **iOS 커스텀 URL 스킴 + 페이스트보드** / **Android implicit intent** 방식이다. 웹에서는 이 경로를 쓸 수 없다.

→ 웹의 사용자 플로우는 **"결과물 다운로드 → 사진앱에서 찾기 → 인스타 열기 → 스토리 만들기 → 업로드"** 가 된다. 반면 네이티브는 **"공유 누르면 인스타 컴포저가 배경+스티커가 얹힌 상태로 열린다."**

`[확인 필요]` **Web Share API(`navigator.share`)로 파일을 시스템 공유 시트에 넘기는 경로**가 iOS Safari에서 동작할 가능성이 있다. 이게 되면 마찰이 상당히 줄어든다(다운로드·사진앱 단계가 사라짐). 다만 **스티커 레이어를 우리가 제어하는 형태는 아니고**, 단일 파일을 넘기는 수준이다. **검증 값어치가 크다 — 웹 안의 성립 여부가 여기 걸린다.**

**함의(개인 판단).** 제품의 핵심 순간은 "인스타에 올리는 그 순간"이다. 목표 자체가 *"인스타 스토리에 올렸을 때 우와"* 니까. **그 마지막 한 걸음에 마찰을 두는 것이 웹 안의 실질 비용**이고, 개발 공수 절약분과 맞바꾸는 대상이다.

### 3-2. B. iOS 정식 등재 — 심사가 일정에 들어온다

| 항목 | 규모 |
|---|---|
| 데이터 확보 | GPX·HealthKit·직접 트래킹 **전부 가능** |
| 렌더링 | AVFoundation + Core Animation(Swift) 또는 Skia/RN(Expo) |
| mp4 내보내기 | **온디바이스 인코딩이 1급 지원.** 인스타가 로컬 파일을 요구하므로 유리 |
| 인스타 공유 | **API 그대로 사용** — 배경 영상 + 오버레이 스티커 |
| 배포 | **심사 2회**(TestFlight 베타 + 정식) · 계정 · $99 |
| 앱 학습 비용 | **팀에 앱 경험자 0명** ← 가장 큰 미지수 |

일정 영향은 [08-17 노트 §5](2026-08-17-appstore-release-feasibility.md)에 계산해뒀다 — **9/8 제출 마감, 리젝 1회까지 허용.**

### 3-3. C. 웹 먼저 → 앱 나중 — 6주에는 안 맞는다

두 번 만드는 안이다. 웹으로 9/22를 맞추고 앱은 이후.

**함의(개인 판단). 6주 안에서는 추천하지 않는다.** 렌더링 엔진을 웹(Canvas)과 네이티브에서 두 번 짓게 되고, 회의록이 *"프리셋 5개가 전부 같은 렌더러"* 로 설계한 이점이 플랫폼을 옮길 때 사라진다. **9/22 이후에 앱으로 갈 계획이 확실하다면 처음부터 네이티브가 낫다.** 단 — §3-1의 Web Share API가 잘 동작하고 데이터 방식이 GPX로 확정되면, C는 "웹으로 검증하고 앱은 안 만들 수도 있다"는 안으로 바뀌어 재검토 가치가 생긴다.

### 3-4. D. iOS + TestFlight 공개 링크 — B와 개발이 동일하고 관문만 낮다

개발 범위는 **B와 완전히 같다.** 다른 건 9/22에 무엇을 "출시"라 부르는가뿐이다.

| 항목 | B (정식 등재) | D (TestFlight) |
|---|---|---|
| 심사 | 베타 + **정식 2회** | **베타 1회** |
| 리젝 리스크 | 정식 심사 리젝이 9/22를 직격 | 베타만 통과하면 9/22가 확보된다 |
| 배포 방법 | App Store 검색·링크 | **공개 링크** (SNS·카톡에 그대로 배포, 최대 10,000명) |
| 설치 마찰 | 없음 | **TestFlight 앱 설치 + 초대 수락 필요** |
| 되돌리기 | — | **정식 등재로 언제든 승격 가능** |

**베타 심사는 첫 빌드에 전체 심사가 걸리고, 같은 버전의 이후 빌드는 심사가 없을 수도 있다.** 공식 원문: *"The first build you submit requires a full review, but later builds for the same version **might not**."* ([08-17 노트 §4-2](2026-08-17-appstore-release-feasibility.md))

→ **첫 빌드를 W3(~9/1)에 통과시켜 두면, 9/22에 배포할 수단을 8월 말에 확보하게 된다.** 이후 빌드가 심사를 건너뛸지는 `might not` 이라 보장되지 않는다.

`[확인 필요]` **베타 심사가 정식 심사보다 관문이 낮은지는 공식 근거를 찾지 못했다.** 통념일 뿐이다. 다만 D의 근거는 "베타가 쉽다"가 아니라 **첫 심사를 8월에 끝내둔다**는 시점에 있으므로, 이 통념이 틀려도 근거는 유지된다.

## 4. "출시"의 정의 — 목표를 쪼개면 답이 갈린다

회의록의 목표는 둘이다:

1. **"인스타 스토리에 처음 올렸을 때 주변인에게 '우와' 소리 1회 이상 듣기"** (9/22~)
2. **추석(9/24~27) 가족 영입** — 9/22 출시 후 **9/29까지가 검증 기간**이고, 그 안에 들어 있다

**이 둘은 배포 형태에 대한 요구가 다르다.**

| | 목표 1 ("우와") | 목표 2 (가족 영입) |
|---|---|---|
| 누가 앱을 써야 하나 | **우리 3명만.** 스토리를 본 사람은 앱을 설치할 필요가 없다 | **가족이 설치해야 한다** |
| TestFlight로 되나 | ✅ **완전히 된다** | ⚠️ 된다. 단 TestFlight 앱 설치 마찰 |
| 웹으로 되나 | ⚠️ 된다. 단 업로드 마찰(§3-1) | ✅ 링크만 열면 됨 |
| App Store 정식 | ✅ | ✅ |

**함의(개인 판단). 목표 1은 배포 형태를 거의 가리지 않는다.** "우와"는 스토리를 **보는 사람**의 반응이고, 그 사람은 우리 앱을 설치하지 않는다. 그러니 **9/22 시점에 필요한 건 "우리 3명이 결과물을 만들어 올릴 수 있는 상태"** 이고, TestFlight로 충분하다.

**설치 마찰이 실제로 걸리는 건 목표 2(추석)뿐이고, 그건 9/24~27이다.** 즉 **9/22에 정식 등재를 못 해도 9/24까지 승격되면 목표 2도 지켜진다.** 이틀의 여유가 더 있다.

→ 이것이 D를 추천하는 핵심 근거다. **"출시"를 정식 등재로 정의하면, 우리가 통제할 수 없는 심사 리젝이 목표 1의 달성 여부까지 결정한다.** 정의를 TestFlight로 두면 목표 1은 우리가 통제할 수 있는 범위에 남고, 정식 등재는 목표 2를 위한 후속 작업이 된다.

## 5. 내 추천

> **iOS 네이티브로 만들고, 9/22의 "출시"를 TestFlight 공개 링크로 정의한다.**
> **App Store 정식 등재는 9/24(추석 시작) 목표로 분리한다.**

### 근거

1. **되돌릴 수 없는 선택을 미룬다** — 네이티브로 시작하면 데이터 방식 세 가지가 다 열려 있다. 웹으로 시작하면 GPX로 못박힌다(§2)
2. **목표 1("우와")이 우리가 통제할 수 있는 범위에 남는다** — 심사 리젝이 목표 달성 여부를 결정하지 않는다(§4)
3. **9/22에 배포할 수단을 8월 말에 확보한다** — 첫 베타 심사를 W3(~9/1)에 통과시켜 두면, **정식 심사가 실패해도 TestFlight 공개 링크가 남는다**([08-17 노트 §5-4](2026-08-17-appstore-release-feasibility.md))
4. **제품의 핵심 순간에 마찰이 없다** — 인스타 공유 API를 그대로 쓴다(§3-1)
5. **mp4 온디바이스 인코딩이 1급 지원** — 인스타가 로컬 파일을 요구하는 구조와 맞는다. JiEung2 트랙의 가장 큰 리스크(*"mp4 내보내기 실현가능성 — 안 되면 제품이 성립하지 않는다"*)를 줄이는 방향이다

### 감수하는 것

| 비용 | 완화 |
|---|---|
| **앱 학습 곡선 (팀 경험자 0명)** ← 가장 큰 리스크 | 완화책 없음. **정직하게 이게 D의 최대 약점이다.** §6에 미검증으로 남김 |
| $99 + 계정 등록 | 8/18 착수하면 병목 아님 |
| TestFlight 설치 마찰 | 목표 2에만 영향. 9/24 정식 승격으로 해소 |
| 웹 대비 개발 공수 증가 | 렌더링 시간을 깎는다 — **회의록이 "우와의 유일한 레버"라 한 그 렌더링** |

**마지막 줄이 이 추천의 아픈 지점이다.** 앱 학습에 쓰는 시간은 렌더링 완성도에서 빼오는 시간이다. **§6의 실기기 검증이 안 된 상태에서 이 트레이드오프의 크기를 모른다.**

### 5-1. D를 택했을 때의 일정 — 정식 등재 역산

[08-17 노트 §5-2](2026-08-17-appstore-release-feasibility.md)의 역산표는 **B안(9/22 정식 등재)** 기준이다.

## 6. 기술 스택 제안

배포 형태가 D(또는 B)로 갈 경우의 제안이다. 웹으로 가면 이 절은 무효다.

### 6-1. Swift/SwiftUI (iOS 전용) — 추천

| 근거 | 내용 |
|---|---|
| Android는 어차피 나중 | [08-11 노트 §2](2026-08-11-platform-tech-review.md)가 이미 "iOS 먼저"로 결론. **크로스플랫폼의 이점(양 플랫폼 동시)이 지금 필요 없다** |
| HealthKit·Core Location | 1급 지원. 래퍼 계층의 불확실성이 없다 |
| **mp4 인코딩** | **AVFoundation + Core Animation이 정확히 이 용도**다. 영상 위 레이어 합성이 표준 경로 |
| 인스타 공유 | URL 스킴 + 페이스트보드. 예제가 많다 |

**함의.** 크로스플랫폼은 **두 플랫폼을 동시에 낼 때** 이득이다. 우리는 iOS만 내므로 **이점 없이 래퍼의 리스크만 진다.**

### 6-2. Expo / React Native — 대안

| 항목 | 평가 |
|---|---|
| 진입 장벽 | 팀이 웹·JS에 익숙하면 Swift보다 빠를 수 있다 ← **이 전제가 맞는지 확인 필요** |
| 백그라운드 위치 | `expo-location` + `expo-task-manager` 경로 존재. 단 [Android 이슈 리포트](https://github.com/expo/expo/issues/22445) — **iOS만이면 이 리스크는 빠진다** |
| **mp4 인코딩** | ⚠️ `[확인 필요]` **여기가 약하다.** RN의 대표 인코딩 라이브러리였던 `ffmpeg-kit`이 **2025년에 지원 종료**됐다. 대체 경로 미확인 |
| JiEung2 목업 재사용 | 목업이 HTML/Canvas라 **웹 렌더링 코드를 일부 옮길 여지**가 있다 ★ |

**함의(개인 판단).** **6-1과 6-2의 선택은 mp4 인코딩 경로에서 갈린다.** 그리고 그건 JiEung2 트랙의 판정 대상(*"MediaRecorder / ffmpeg.wasm / 서버 사이드 ffmpeg 중 무엇이 되는지"*)과 겹친다. → **두 트랙이 만나는 지점이므로 회의에서 함께 봐야 한다.**

### 6-3. 서버 — 거의 필요 없다

MVP 범위(데이터 확보 → 렌더 → 내보내기)는 **전부 온디바이스에서 끝난다.** 인스타 공유가 로컬 파일을 요구하므로 서버 렌더링은 오히려 "결과물을 기기로 내려받는 단계"를 추가한다(회의록이 이미 `[확인 필요]`로 지적).

MVP에서 서버가 필요할 수 있는 곳:
- 없음. **로그인·저장·공유 링크가 전부 MVP 제외**다
- 그룹 드로잉·코스 공유는 **다음 라운드로 제외 확정**

→ §7로 이어진다.

### 6-4. 하이브리드(네이티브 + 웹뷰) — 되지만 지금은 아니다

> 팀에서 나온 안이다: *"건강 정보는 HealthKit으로 네이티브가 잡고, 꾸미기는 디자인이 자주 바뀌니
> 웹으로 두면 배포가 쉽지 않나?"*

**기술적으로는 표준 패턴이다.** `WKWebView` + JS 브릿지(`WKScriptMessageHandler`)로 네이티브 셸 안에
웹 화면을 띄우고, HealthKit·Core Location은 네이티브가 잡아 결과를 브릿지로 넘긴다.

심사도 통과 가능하다. `[확인 필요]` App Review Guidelines가 실행 코드 다운로드를 금지하면서
**WebKit에서 실행되는 JavaScript는 예외**로 두는 것으로 알려져 있다 — CodePush·Expo Updates가
합법인 근거다. **정확한 조항 번호는 확인하지 못했다.** 웹뷰만 있는 앱은 4.2(Minimum Functionality)로
리젝되지만, HealthKit·위치가 붙어 있으면 방어된다.

#### 급소 — "꾸미기"가 무엇이냐에 따라 갈린다

| "꾸미기"의 범위 | 성립? |
|---|---|
| 프리셋 **선택 UI** (색상·폰트 고르는 화면) | ✅ 성립. 단 **웹으로 뺄 값어치가 작다** — 그 정도 화면은 네이티브도 쉽게 바꾼다 |
| **오버레이 디자인 자체 = 렌더링** | ⚠️ **여기가 문제** |

렌더링이 웹에 있으면 **mp4를 어디서 만드느냐**가 걸린다. 세 갈래 전부 대가가 있다:

1. **웹 Canvas 프레임 → 네이티브 인코딩** — 프레임 수백 장을 브릿지로 넘겨야 한다. 대역폭에서 무너진다
2. **웹은 프리뷰, 출력은 네이티브** — **렌더러가 두 벌**이 된다. §3-3이 C안(웹→앱)을 반대한 바로 그 이유다
3. **웹에서 렌더+인코딩까지** — 그러면 AVFoundation을 추천한 근거(§6-1)가 통째로 빠진다

그리고 **하이브리드는 네이티브보다 어렵다.** 네이티브도 알아야 하고 웹도 알아야 하고 브릿지까지
설계해야 한다. 앱 경험자 0명인 팀이 복잡도를 올리는 방향이다.

#### 목적만 떼어내면 훨씬 싼 길이 있다

원하는 건 웹뷰 자체가 아니라 **"심사 없이 디자인을 바꾸는 것"** 이다. 그 목적은 웹뷰 없이 달성된다.

> **프리셋 정의를 코드가 아니라 데이터(JSON)로 빼고, 원격에서 받아온다.**

렌더러는 네이티브 하나만 유지한다. 대신 *"선 두께 4px · 글로우 #FF6B00 · 폰트 32 · 경로 애니메이션 1.2초"*
같은 **스펙을 서버에서 내려받는다.** 디자인 변경 = 서버 JSON 교체 = **심사 없음.**

회의록이 *"프리셋 5개가 전부 같은 렌더러"* 로 설계했다면 이 구조와 정확히 맞는다.
렌더러는 하나고 파라미터만 다섯 벌이기 때문이다.

**함의(개인 판단).** 6주 MVP에는 하이브리드를 넣지 않는 쪽을 지지한다. 다만 **프리셋 데이터 원격화는
넣을 값어치가 있다** — 목적을 달성하면서 비용이 훨씬 싸고, **§7의 긴장까지 일부 푼다.**
9/22 이후 디자인 이터레이션이 실제로 잦아지면 그때 하이브리드를 재검토하면 된다.

## 7. ⚠️ 배포 형태와 무관한 긴장 — 백엔드 2명이 할 일이 없다

**팀은 기획 1(phs00) + 백엔드 2(JiEung2, jminkkk)다.** 그런데 MVP는:

- 서버가 필요 없다 (§6-3)
- 클라이언트 렌더링·인코딩이 작업의 대부분
- 아무도 해본 적 없는 영역 (앱 + 그래픽스)

**즉 이 프로젝트는 팀의 강점을 쓰지 않는다.** [08-11 노트 §6](2026-08-11-platform-tech-review.md)에서 *"팀에 앱 개발 경험자가 없다"* 를 일정 변수로 지적했는데, 더 정확히는 **"팀의 기존 역량이 MVP 범위와 겹치지 않는다"** 다.

**함의(개인 판단).** 이건 배포 형태를 어떻게 정해도 남는 문제이고, 두 가지 중 하나를 골라야 한다고 본다:

1. **받아들인다** — 6주를 학습 프로젝트로 정의한다. 사이드 프로젝트의 목적이 학습이라면 합리적이다
2. **MVP 범위를 팀 역량 쪽으로 옮긴다** — 예: 그룹 드로잉(서버·동기화 필요)을 MVP에 넣는다. 단 회의록이 이미 제외 확정한 항목이라 **되돌리는 결정**이다
3. **프리셋 데이터 원격화를 넣는다**(§6-4) — 렌더링 파라미터를 JSON으로 빼서 서버에서 내려받는다.
   **MVP 범위를 되돌리지 않으면서 서버가 생긴다**

**3번을 함께 제안한다.** 규모가 작고(JSON 서빙 + 버전 관리) 6주에 부담이 안 되면서,
백엔드 둘이 잡을 명분이 된다. 무엇보다 **이건 억지로 만든 일이 아니라 실제로 필요한 일**이다 —
디자인이 자주 바뀔 것이고, 바뀔 때마다 심사를 받는 것은 비용이다.

**1을 지지한다(jminkkk).** 회의록의 MVP 범위 판단(*"렌더링 완성도가 우와의 유일한 레버"*)이 맞다고 보며, 범위를 흔드는 비용이 더 크다. 다만 **"팀이 해본 적 없는 영역을 3주에 한다"는 전제를 명시적으로 합의하고 시작해야** 3주차에 흔들리지 않는다.

5. **§7의 긴장을 명시적으로 합의할 것인가** — "6주를 학습 프로젝트로 본다"에 셋이 동의하는지
6. **스택** — 1·2가 정해지면 §6이 거의 따라온다. 남는 건 Swift vs Expo이고 mp4 인코딩(§8-4)에서 갈린다
7. **프리셋 데이터 원격화를 MVP에 넣을 것인가**(§6-4·§7) — "심사 없이 디자인 변경"을 웹뷰 없이
   달성하는 안. 백엔드 작업이 생긴다는 부수 효과가 있다

# 2026-10-06 회의 제안: 쓰는 사람이 어디서 빠지는지 보자

*2026-10-06 · jminkkk · 개인 제안이고 팀 결정이 아니다*

**공개 링크를 연 지 2주가 됐다.** 반응은 카톡과 스레드로 들어오지만, 앱을 연 사람이 결과물까지 가는지는 아무도 모른다. 지금 볼 수 있는 것은 "누가 뭐라고 했다"뿐이다.

그래서 아래 넷을 제안한다. 순서대로 서로 걸려 있다.

| | 무엇을 | 왜 지금 |
|---|---|---|
| 1 | 행동 로그를 남긴다 | 이게 없으면 2와 4를 못 한다 |
| 2 | 단계별로 어디서 빠지는지 본다 | 핵심 흐름이 끝까지 돈다. 다음에 무엇을 고칠지 정할 근거가 필요하다 |
| 3 | 들어온 반응을 나눠 적는다 | 반응을 레포에 모으기로 이미 정했다. 나눌 기준만 더하면 된다 |
| 4 | 지표를 한두 개 정한다 | 성능 개선 리서치가 나아졌는지 잴 기준이 없다 |

---

## 1. 행동 로그를 남긴다

**앱에는 지금 분석 도구가 없다.** `frontend/package.json`에 분석 SDK가 없고 코드에도 이벤트를 보내는 곳이 없다 (2026-10-06 확인).

처음에는 이벤트를 적게 잡는다. 2의 단계를 볼 수 있는 만큼이면 된다.

| 이벤트 | 언제 |
|---|---|
| 앱 열기 | 홈에 들어왔을 때 |
| 기록 선택 | 러닝 기록을 하나 골랐을 때 |
| 편집 진입 | 편집 화면이 열렸을 때 |
| 생성 완료 | 영상이 다 만들어졌을 때 |
| 공유 | 인스타 스토리로 넘기거나 저장했을 때 |

**도구를 고르기 전에 정할 것이 있다.**

- 처리방침을 고쳐야 한다. 지금 공개본은 수집하는 정보를 적어 두었으므로, 사용 기록을 모으면 그 내용을 추가해야 한다. 어디까지 고쳐야 하는지는 `[확인 필요]`
- 고친 처리방침이 심사에 영향을 주는지 `[확인 필요]`
- 도구는 아직 고르지 않았다. 후보 비교는 회의에서 하자고 하면 그다음에 한다

## 2. 단계별로 어디서 빠지는지 본다

1의 이벤트를 차례로 세면 이런 그림이 나온다.

```
앱 열기 → 기록 선택 → 편집 진입 → 생성 완료 → 공유
```

**가장 많이 빠지는 칸이 다음에 고칠 곳이다.** 지금은 생성이 느리다는 이야기가 많아서 그쪽을 고치고 있다. 실제로 그 칸에서 가장 많이 빠지는지는 아직 모른다.

**지금 사용자 수로는 숫자가 흔들린다.** 몇 명이 빠졌는지 정도로만 보고, 비율로 판단하지 않는다.

## 3. 들어온 반응을 나눠 적는다

[QA 기록](../../ops/qa-log.md)과 [9/29 결정](../../decisions/2026-09-29-weekly-content-and-reactions.md)으로 반응을 레포에 모으고 있다. 여기에 두 칸만 더하자고 제안한다.

| 칸 | 값 |
|---|---|
| 종류 | 버그 / 불편 / 바라는 것 / 칭찬 |
| 처리 | 바로 고침 / 정해야 함 / 안 함 |

**같은 이야기가 몇 번 나왔는지 보이게 하는 것이 목적이다.** 지금은 한 번 나온 말과 다섯 번 나온 말이 똑같이 한 줄이다.

## 4. 지표를 한두 개 정한다

후보는 둘이다.

| 지표 | 무엇을 말해 주나 |
|---|---|
| 생성 완료율 (편집 진입 대비 생성 완료) | 만들다 그만두는지. 성능 개선이 효과가 있었는지 |
| 주간 공유 수 | [PRD](../../specs/prd/running-drawing-mvp.md) §5의 검증 질문, "공유를 목적으로 예쁜 결과물을 얻고 싶은 니즈가 있는가"에 가장 가까운 숫자 |

**목표 수치는 아직 정하지 않는다.** 처음 2주 동안 재 본 다음에 정한다.

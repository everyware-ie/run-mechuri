# 2026-10-06 회의 안건: 초기 사용자 검증 제안

*2026-10-06 · jminkkk · 개인 제안이며 팀 결정이 아님*

TestFlight 공개 링크를 연 지 2주가 됐다. 카톡과 스레드로 사용자 반응이 들어오고 있지만, 앱을 연 사용자가 결과물 생성과 공유까지 진행하는지는 확인할 수 없다.

지금은 첫 사용자가 제품의 가치를 느끼는지 확인하는 0→1 단계다. 자기 러닝 결과물을 실제로 게시하고, 다음 러닝에서도 다시 사용하는 사람이 있는지 확인하자고 제안한다. 행동 로그와 사용자 대화를 함께 활용한다.

## 제안 배경

지금은 사용자 피드백과 디자인 검토를 바탕으로 앱을 개선하고 있다. 생성이 느리다는 피드백에 따라 장면을 둘씩 동시에 렌더링하기로 했고([9/29 결정](../../decisions/2026-09-29-export-parallel-rendering.md)), 시안을 검토한 뒤 편집 화면을 바꾸기로 했다([10/4 결정](../../decisions/2026-10-04-story-style-editor.md)). 두 개선 모두 이유가 있지만, 사용자가 실제로 어느 단계에서 이용을 중단하는지는 확인하지 못했다.

[PRD](../../specs/prd/running-drawing-mvp.md)의 §5 MVP 범위의 검증 항목에는 "직접 측정하지 않더라도 공유를 목적으로 예쁜 경로 그림 결과물을 얻고 싶어하는 니즈가 있는지"라는 질문이 있다. 현재 근거는 지인 몇 명의 반응뿐이다. 앱을 설치하고 사용하지 않거나, 사용하다 그만둔 사람이 반응을 남기지 않으면 그 이유를 알기 어렵다.

[9/8 결정](../../decisions/2026-09-08-scope-and-roles.md)으로 두 사람이 성능 개선 리서치를 맡았다. 앱을 다듬는 단계인 만큼, 눈에 띄는 문제뿐 아니라 실제 이용 현황을 보고 개선 순서를 정할 필요가 있다.

다음 기능을 선택할 때도 근거가 필요하다. PRD의 §10 로드맵에 있는 그룹 드로잉은 서버와 계정이 필요한 큰 작업이다. 사용자가 혼자 만든 결과물을 얼마나 공유하는지 확인하면, 그룹 드로잉에 투자할지 판단할 때 참고할 수 있다.

## 제안하는 활동

1. 주요 단계의 행동 로그를 수집한다.
2. 단계별 이용 현황과 이용 중단 지점을 확인한다.
3. 사용자 피드백을 종류와 처리 상태에 따라 정리한다.
4. 첫 결과물 생성, 실제 게시, 반복 사용을 확인한다.
5. 사용 전 인터뷰와 첫 사용성 테스트를 진행하고, 다음 러닝 후 다시 확인한다.

행동 로그는 이용 중단 지점을 찾는 데 쓰고, 실제 게시 여부와 재사용 이유는 사용자에게 직접 확인한다. 분석 도구 도입 전에도 소수 사용자의 첫 사용과 다음 러닝을 따라가며 관찰할 수 있다. 피드백 정리는 이미 레포에 모으고 있는 반응에 분류 기준을 추가하는 작업이다.

## 1. 주요 단계의 행동 로그 수집

현재 앱에는 분석 도구가 없다. `frontend/package.json`에 분석 SDK가 없고, 코드에도 이벤트를 전송하는 부분이 없다(2026-10-06 확인).

단계별 이용 현황을 확인할 수 있도록 다음 행동을 기록한다.

| 행동 | 기록 시점 |
|---|---|
| 앱 열기 | 홈에 들어왔을 때 |
| 기록 선택 | 러닝 기록을 하나 골랐을 때 |
| 편집 진입 | 편집 화면이 열렸을 때 |
| 생성 완료 | 영상 생성이 완료됐을 때 |
| 인스타그램 전달 | 결과물을 인스타그램 스토리로 넘겼을 때 |
| 파일 저장 완료 | 결과물을 기기에 저장했을 때 |

인스타그램 전달과 파일 저장은 실제 게시와 구분한다. 실제 게시 여부는 사용자에게 직접 확인하며, 로그만으로 게시했다고 판단하지 않는다. 반복 사용을 확인할 때는 같은 러닝 기록의 재생성과 다른 기록의 생성을 구분한다. 이를 위한 기록 구분 방식과 수집 범위는 도구 비교 시 검토하며, 경로 좌표나 건강 수치를 분석용으로 보내는 것은 이번 제안에 포함하지 않는다.

개인정보 처리방침에 사용 기록 수집 내용을 추가해야 한다. 수정 범위와 수정된 처리방침이 심사에 영향을 주는지는 [확인 필요]다. 분석 도구는 아직 정하지 않았으며, 회의에서 로그 수집을 진행하기로 하면 후보를 비교한다.

## 2. 단계별 이용 현황 확인

확인할 흐름은 다음과 같다.

앱 열기 → 기록 선택 → 편집 진입 → 생성 완료 → 인스타그램 전달 또는 파일 저장

기록 선택부터 결과물 공유까지 핵심 기능은 구현됐다. 이제 이용을 중단한 사용자가 많은 단계를 확인하고 원인을 살펴보면, 다음 개선 대상을 정할 때 참고할 수 있다. 현재는 생성이 느리다는 피드백에 따라 성능을 개선하고 있지만, 생성 단계에서 이용 중단이 가장 많은지는 아직 모른다.

현재 사용자 수가 적어 비율은 몇 명의 행동에도 크게 달라질 수 있다. 우선 단계별 이용 중단 인원을 확인하고, 비율만으로 판단하지 않는다.

## 3. 사용자 피드백 정리

[QA 기록](../../ops/qa-log.md)에 제보를 모으고 있으며, [9/29 결정](../../decisions/2026-09-29-weekly-content-and-reactions.md)에 따라 사용자 반응도 레포에 기록하고 있다. 여기에 다음 두 항목을 추가하자고 제안한다.

| 항목 | 분류 |
|---|---|
| 피드백 종류 | 버그 / 불편 / 요청 / 칭찬 |
| 처리 상태 | 바로 수정 / 논의 필요 / 반영하지 않음 |

같은 의견이 몇 번 나왔는지 파악하려는 목적이다. 현재는 한 번 나온 의견과 다섯 번 나온 의견이 모두 한 줄로 기록돼 반복된 정도를 알기 어렵다.

## 4. 첫 사용과 반복 사용을 확인할 지표

PRD의 §5 MVP 범위에 있는 검증 질문을 기준으로 다음 네 가지를 확인한다. 비율만 적지 않고, 처음 사용한 사람과 각 행동을 한 사람의 수를 함께 기록한다. 팀원과 외부 사용자의 결과는 나눠서 본다.

| 확인할 질문 | 지표 | 확인 방법 |
|---|---|---|
| 혼자서 첫 결과물을 만들 수 있나? | 첫 결과물 생성 인원 | 처음 사용한 사람 중 도움 없이 생성한 사람을 기록한다. 기록이 없어서 못 만든 경우와 조작·오류로 막힌 경우를 구분한다 |
| 결과물이 실제로 게시할 만큼 마음에 드나? | 실제 게시 인원 | 결과물을 만든 사람 중 실제 스토리에 게시한 사람을 직접 확인한다. 인스타그램 전달·파일 저장과 구분한다 |
| 한 번 체험하고 끝나는가? | 다른 러닝 기록으로 다시 만든 인원 | 첫 생성 이후 다른 기록으로 결과물을 만든 사람을 확인한다. 같은 기록의 재편집·재생성은 제외한다 |
| 다시 쓸 기회가 있었는데도 안 쓰는가? | 다음 러닝 후 재사용 인원 | 첫 사용 후 다시 달린 사람 중 Runary로 결과물을 다시 만든 사람을 확인한다. 초기에는 다음 러닝 여부와 재사용 여부를 직접 물어본다 |

대표 지표로는 **다른 러닝 기록으로 다시 만들어 실제 게시한 사람 수**를 제안한다. 첫 게시에는 호기심이나 지인의 권유가 섞일 수 있다. 다른 기록으로 만들고 게시하는 행동이 반복되면, 제품을 계속 쓰는 이유가 있다는 근거로 볼 수 있다. 다만 이 숫자만으로 제품 수요가 검증됐다고 판단하지 않는다.

생성 완료율(편집 진입 대비 생성 완료)은 사용 과정의 문제를 찾는 보조 지표로 둔다. 생성하지 못한 사람에게는 어디서 멈췄는지, 생성했지만 게시하지 않은 사람에게는 왜 올리지 않았는지, 다음 러닝 후 사용하지 않은 사람에게는 그 이유를 확인한다. 결과를 칭찬했는지보다 실제 행동과 그 이유를 기록한다.

### 처음 2주 동안 할 일

외부 사용자 5~10명의 첫 사용과 다음 러닝을 따라가며 확인하자고 제안한다. 5~10명은 성공 기준이 아니라 관찰할 범위다. 기간 안에 다시 달리지 않은 사람은 재사용 실패로 분류하지 않고, 아직 재사용 기회가 없었다고 기록한다.

사용자별로 첫 생성 여부, 도움 여부, 게시 여부, 다음 러닝 여부, 재사용·재게시 여부와 중단 이유를 정리한다. 예를 들어 아래처럼 기록할 수 있다. 실제 측정 결과는 아니다.

> 처음 사용한 외부 사용자 5명 중 2명은 게시했다. 2명은 결과물이 마음에 들지 않아 게시하지 않았고, 1명은 생성에 실패했다. 이후 다시 달린 3명 중 1명이 다른 기록으로 결과물을 만들어 게시했다.

목표 비율은 아직 정하지 않는다. 2주간의 관찰 결과를 보고 사용을 막는 문제와 반복해서 쓰는 이유를 논의한다. 초기에는 사용자와 직접 대화하며 무엇을 만들어야 하는지 확인한다는 [YC의 조언](https://www.ycombinator.com/blog/ycs-essential-startup-advice/)을 참고했다. 위 지표와 관찰 범위는 Runary에 맞춘 제안이며, 외부 기준 수치를 가져온 것은 아니다.

## 5. 인터뷰와 사용성 테스트

혼자 사용할 수 있는지와 사용할 이유가 있는지를 함께 확인한다. 테스트에서 결과물을 만드는 데 성공해도, 실제 러닝 후 다시 사용할지는 별도로 살펴봐야 한다. 로그 도입을 기다리지 않고 진행할 수 있다.

앞서 제안한 외부 사용자 5~10명 중 앱을 처음 쓰는 실외 러너 5명 정도를 대상으로 한 차례 시작한다. 본인 기기에서 사용할 수 있는 러닝 기록이 있는지 미리 확인하고, 모집할 때 최근 러닝과 공유 경험을 함께 기록한다. 공유 경험이 다른 참여자의 반응을 구분해 본다. 소수 참여자로 같은 사용자군의 사용 문제를 찾는 방식은 [NN/g의 사용성 테스트 안내](https://www.nngroup.com/articles/usability-testing-101/)를 참고했다. 이 인원으로 수요나 성공률을 일반화하지 않는다.

### 사용 전 인터뷰(약 10분)

앱을 설명하기 전에 최근의 실제 행동을 묻는다. 앱을 먼저 소개하고 사용 의향을 물으면, 참여자가 제안에 맞춰 답할 수 있다.

- 가장 최근에 달린 뒤 기록을 공유했나요? 어떻게 올렸나요?
- 올리기 전에 사진이나 기록을 따로 편집했나요?
- 공유하려다 안 올린 적이 있나요? 그때는 왜 그랬나요?

### 첫 사용성 테스트(약 20~30분)

버튼 위치나 사용 순서를 설명하지 않고 다음 과제를 준다.

> 최근 러닝 기록으로 본인이 원하는 결과물을 만들어주세요. 실제 게시할지는 자유입니다.

| 관찰할 부분 | 확인할 것 |
|---|---|
| 첫 화면 | 무엇을 만드는 앱인지 이해하는가 |
| 기록 선택 | 본인 러닝 기록을 찾아 편집에 들어갈 수 있는가 |
| 편집 | 원하는 모양으로 바꾸는 도구를 찾을 수 있는가 |
| 생성 대기 | 무엇이 진행되고 있는지 이해하는가 |
| 내보내기 | 저장하거나 인스타그램으로 넘길 수 있는가 |

진행자는 막힌 지점에서 바로 답을 알려주기보다 "지금 무엇을 하려고 했나요?"라고 묻는다. 도움을 줬다면 어느 지점에서 어떤 도움을 줬는지 기록한다. 관찰 중 진행자가 덜 말하는 원칙은 [YC의 사용자 관찰 가이드](https://www.ycombinator.com/blog/practical-design-user-observation)를 참고했다. 화면이나 음성을 녹화한다면 참여자의 동의를 받고 진행한다.

### 테스트 직후와 다음 러닝 후 확인

테스트 직후에는 만든 결과물을 평소 러닝 게시물과 비교하며 묻는다.

- 이 결과물을 올린다면 기존 게시물 대신 올리나요, 같이 올리나요?
- 올리지 않는다면 가장 큰 이유는 무엇인가요?
- 결과물에서 꼭 바꾸고 싶은 부분이 있나요?

그다음에는 §4 첫 사용과 반복 사용을 확인할 지표에 따라, 2주 동안 다음 러닝과 실제 재사용을 확인한다. 테스트 과제로 만든 결과물은 자발적으로 만든 결과물과 구분한다. 재사용을 요청하거나 알림을 보냈다면 그 사실도 기록해, 요청 없이 다시 사용한 경우와 구분한다.

### 결과를 다음 개선으로 연결하기

관찰 사실, 원인 가설, 다음 행동을 나눠 정리한다. 원인 가설을 사용자가 실제로 한 말이나 확인된 사실처럼 적지 않는다. 아래는 기록 방식의 예시이며 실제 테스트 결과는 아니다.

| 관찰 사실 예시 | 원인 가설 | 다음 행동 |
|---|---|---|
| 5명 중 3명이 생성 버튼을 찾지 못했다 | 완료 동작이 눈에 띄지 않는다 | 버튼을 수정한 뒤 다시 테스트한다 |
| 결과물을 생성했지만 연출이 과하다고 말하며 게시하지 않았다 | 원하는 표현과 기본 연출이 다르다 | 해당 사용자의 기존 게시물과 비교한다 |
| 다음 러닝 후 기존 앱의 캡처를 게시했다 | 기존 방식을 바꿀 이점이 부족하다 | 기존 방식이 더 나았던 이유를 확인한다 |

회의에서는 사용을 막는 문제와 결과물을 원하지 않는 이유를 구분해 다음 행동을 정한다. 제품 정책이나 기능을 바꿀 결론이 나오면 결정문과 PRD·FRD에 반영한 뒤 구현한다.

## 이번 제안에서 제외하는 작업

| 작업 | 검토 시점 |
|---|---|
| 세분화한 코호트 분석, A/B 테스트 | 관찰 수와 사용 기회가 충분히 쌓인 뒤. 소수 사용자의 반복 사용 여부와 이유는 지금부터 확인한다 |
| 유입 경로별 성과 비교(스레드·카톡·지인) | 유입 출처를 추적할 수단이 생긴 뒤 |
| 리포트 자동화 | 수작업으로 리포트를 세 번 정도 작성한 뒤 |

## 회의에서 정할 것

- 외부 사용자 5~10명의 첫 사용과 다음 러닝을 2주 동안 확인할지, 누가 맡을지
- 그중 첫 사용성 테스트에 참여할 5명 정도를 어떻게 모집하고, 진행과 기록을 누가 맡을지
- 관찰 결과를 언제 함께 검토하고, 다음 개선 대상을 어떤 근거로 정할지
- 다른 러닝 기록으로 다시 만들어 실제 게시한 사람 수를 대표 지표로 볼지
- 주요 단계의 행동 로그를 수집할지
- 수집한다면 로그 수집과 개인정보 처리방침 수정을 각각 누가 맡을지
- QA 기록에 피드백 종류와 처리 상태를 추가할지
